# LCD1602: как заставить микроконтроллер говорить с человеком

До этого момента наш микроконтроллер уже умел многое.

Он мог включать светодиод, читать кнопку, считать время, генерировать PWM, общаться по UART, I2C и SPI. Но была одна проблема: почти вся эта работа оставалась невидимой для человека.

Микроконтроллер мог знать текущее время, состояние кормушки или положение сервопривода, но пользователь об этом не знал.

Нам понадобился экран.

Не графический дисплей, не сенсорная панель и не сложная библиотека с готовым интерфейсом. Для начала достаточно простого LCD1602 — символьного дисплея, способного показывать две строки по 16 символов.

Но просто подключить провода и передать строку:

```c
LCD_Print("Hello");
```

недостаточно.

Чтобы эта строка появилась на экране, микроконтроллер должен:

1. Настроить GPIO.
2. Правильно инициализировать контроллер дисплея.
3. Сообщить, передаёт он команду или данные.
4. Разделить каждый байт на две половины.
5. Выставить четыре бита на линиях данных.
6. Дать дисплею сигнал, что данные готовы.
7. Подождать, пока команда будет выполнена.

Именно этот путь мы и реализуем.

---

# 1. Постановка задачи

Нам нужен драйвер, который позволит приложению работать с дисплеем на понятном уровне:

```c
LCD_Init();

LCD_SetCursor(0, 0);
LCD_Print("Pet Feeder");

LCD_SetCursor(1, 0);
LCD_Print("Ready");
```

Верхняя часть программы не должна знать:

* на каких конкретно выводах подключены `D4–D7`;
* каким уровнем управляется `RS`;
* как сформировать импульс `E`;
* как байт делится на два nibble;
* какие задержки требует контроллер LCD.

Приложение должно просто сказать:

> Выведи этот текст в эту позицию.

Вся техническая работа должна остаться внутри драйвера.

---

# 2. Что такое LCD1602

LCD1602 — это символьный жидкокристаллический дисплей.

Число `1602` обычно означает:

```text
16 символов в строке
2 строки
```

Пример:

```text
┌──────────────────┐
│ Pet Feeder       │
│ Time: 14:35      │
└──────────────────┘
```

Каждая позиция предназначена для одного символа.

Дисплей не получает готовое изображение буквы `A` от микроконтроллера. Мы передаём код символа, а контроллер дисплея уже знает, как этот символ нарисовать.

Например:

```c
LCD_PrintChar('A');
```

Символ `'A'` в C представлен числовым кодом.

Драйвер передаёт этот байт LCD, а контроллер дисплея самостоятельно отображает нужную матрицу точек.

---

# 3. Почему недостаточно просто подключить восемь бит данных

У дисплея есть линии данных:

```text
D0
D1
D2
D3
D4
D5
D6
D7
```

Можно было бы передать целый байт сразу:

```text
1010 0110
│       │
D7      D0
```

Это 8-битный режим.

Но тогда только для данных нам потребовалось бы восемь выводов микроконтроллера.

Для маленького AVR это довольно дорого.

Поэтому мы используем 4-битный режим и подключаем только:

```text
D4
D5
D6
D7
```

Один байт приходится передавать в два этапа.

Например:

```text
Исходный байт:

1010 0110
```

Сначала передаём старшую половину:

```text
1010
```

Затем младшую:

```text
0110
```

Половина байта из четырёх бит называется **nibble**.

Таким образом:

```text
Байт
  │
  ├── старший nibble
  │
  └── младший nibble
```

Мы экономим четыре вывода микроконтроллера, но каждая передача теперь требует двух этапов.

---

# 4. Линии RS и E

Одних линий `D4–D7` недостаточно.

Контроллер должен понимать:

* что именно находится на этих линиях;
* когда ему нужно их считать.

Для этого используются управляющие сигналы.

## RS — данные или команда

На одних и тех же линиях LCD получает как команды, так и символы.

Например:

```text
0x01
```

может означать команду очистки экрана.

А:

```text
0x41
```

может означать символ `A`.

Чтобы LCD понимал назначение байта, используется линия `RS`.

```text
RS = 0 → команда

RS = 1 → данные
```

Поэтому внутри нашего драйвера есть такая логика:

```c
if (isData)
{
    LCD_RS_PORT |= (1 << LCD_RS_PIN);
}
else
{
    LCD_RS_PORT &= ~(1 << LCD_RS_PIN);
}
```

Теперь один общий механизм передачи может использоваться и для команд, и для текста.

---

## E — данные готовы

Сначала микроконтроллер выставляет нужные логические уровни на:

```text
D4
D5
D6
D7
```

Но контроллер LCD ещё не знает, когда именно ему нужно считать эти значения.

Для этого существует линия `E`, или `Enable`.

Упрощённо процесс выглядит так:

```text
Микроконтроллер:

1. Выставляет данные на D4–D7
2. Формирует импульс на E
3. LCD фиксирует состояние линий
```

Наша функция выглядит так:

```c
static void LCD_PulseEnable(void)
{
    LCD_E_PORT |= (1 << LCD_E_PIN);
    _delay_us(1);

    LCD_E_PORT &= ~(1 << LCD_E_PIN);
    _delay_us(1);
}
```

Можно представить это как команду:

> Данные уже стоят на линиях. Считай их сейчас.

Важно понимать: импульс `E` не создаёт сами данные. Они уже были выставлены заранее.

Он сообщает дисплею момент, когда эти данные нужно зафиксировать.

---

# 5. Выставляем четыре бита на GPIO

Начинаем с самого нижнего уровня нашего драйвера.

```c
static void LCD_WriteNibble(uint8_t nibble)
{
    if (nibble & (1 << 0))
    {
        LCD_D4_PORT |= (1 << LCD_D4_PIN);
    }
    else
    {
        LCD_D4_PORT &= ~(1 << LCD_D4_PIN);
    }

    if (nibble & (1 << 1))
    {
        LCD_D5_PORT |= (1 << LCD_D5_PIN);
    }
    else
    {
        LCD_D5_PORT &= ~(1 << LCD_D5_PIN);
    }

    if (nibble & (1 << 2))
    {
        LCD_D6_PORT |= (1 << LCD_D6_PIN);
    }
    else
    {
        LCD_D6_PORT &= ~(1 << LCD_D6_PIN);
    }

    if (nibble & (1 << 3))
    {
        LCD_D7_PORT |= (1 << LCD_D7_PIN);
    }
    else
    {
        LCD_D7_PORT &= ~(1 << LCD_D7_PIN);
    }
}
```

Функция получает четыре младших бита значения `nibble`.

Соответствие выглядит так:

```text
nibble bit 0 → LCD D4
nibble bit 1 → LCD D5
nibble bit 2 → LCD D6
nibble bit 3 → LCD D7
```

Например:

```text
nibble = 1010
```

Получаем:

```text
D7 = 1
D6 = 0
D5 = 1
D4 = 0
```

Здесь происходит самый настоящий физический уровень драйвера: мы непосредственно меняем состояние выводов микроконтроллера.

---

# 6. Как передать целый байт через четыре линии

Теперь построим следующий уровень:

```c
static void LCD_WriteByte(uint8_t data, bool isData)
{
    if (isData)
    {
        LCD_RS_PORT |= (1 << LCD_RS_PIN);
    }
    else
    {
        LCD_RS_PORT &= ~(1 << LCD_RS_PIN);
    }

    uint8_t highNibble = data >> 4;
    LCD_WriteNibble(highNibble);
    LCD_PulseEnable();

    uint8_t lowNibble = data & 0b00001111;
    LCD_WriteNibble(lowNibble);
    LCD_PulseEnable();
}
```

Допустим:

```text
data = 1010 0110
```

Сначала выполняем:

```c
uint8_t highNibble = data >> 4;
```

Получаем:

```text
0000 1010
```

Передаём:

```text
1010
```

И формируем импульс `E`.

Затем:

```c
uint8_t lowNibble = data & 0b00001111;
```

Получаем:

```text
0000 0110
```

Передаём:

```text
0110
```

И снова формируем импульс `E`.

Полный процесс:

```text
1010 0110
    │
    ├── 1010 → D4–D7 → E
    │
    └── 0110 → D4–D7 → E
```

После двух импульсов LCD получает полный байт.

---

# 7. Команды и данные

Теперь можно сделать две отдельные функции:

```c
static void LCD_WriteCommand(uint8_t command)
{
    LCD_WriteByte(command, false);
    _delay_us(50);
}
```

и:

```c
static void LCD_WriteData(uint8_t data)
{
    LCD_WriteByte(data, true);
    _delay_us(50);
}
```

Обе передают один байт.

Различие только в назначении.

Для команды:

```text
RS = 0
```

Для символа:

```text
RS = 1
```

Таким образом:

```c
LCD_WriteCommand(0x01);
```

означает:

> Выполни команду очистки.

А:

```c
LCD_WriteData('A');
```

означает:

> Выведи символ `A`.

Это важный принцип.

Байт сам по себе ничего не объясняет. Его значение зависит от контекста, в котором он передаётся.

# 8. Почему инициализация LCD выглядит странно

На первый взгляд хотелось бы написать:

```c
LCD_WriteCommand(0b00101000);
```

и сразу начать работать в 4-битном режиме.

Но проблема в том, что после включения нельзя просто слепо полагаться на текущее состояние контроллера дисплея.

Поэтому используется специальная последовательность инициализации:

```c
_delay_ms(20);

LCD_WriteCommandNibble(0x03);
_delay_ms(5);

LCD_WriteCommandNibble(0x03);
_delay_us(150);

LCD_WriteCommandNibble(0x03);
_delay_us(150);

LCD_WriteCommandNibble(0x02);
_delay_us(150);
```

Сначала трижды передаётся:

```text
0x03
```

Затем:

```text
0x02
```

Упрощённо смысл последовательности можно представить так:

```text
После включения
      ↓
Привести контроллер
к известному состоянию
      ↓
0x03
0x03
0x03
      ↓
Переключить на 4-bit mode
      ↓
0x02
```

Здесь важно не запоминать последовательность как магический ритуал.

Инженер открывает datasheet, находит рекомендуемую процедуру инициализации и следует ей с соблюдением временных требований.

---

# 9. Настройка режима работы

После перехода в 4-битный режим мы отправляем обычную полную команду:

```c
LCD_WriteCommand(0b00101000);
```

Она задаёт:

```text
4-битный режим
2 строки
шрифт 5×8
```

Формат команды можно представить так:

```text
DB7 DB6 DB5 DB4 DB3 DB2 DB1 DB0
 0   0   1   DL  N   F   X   X
```

Где:

```text
DL = 0 → 4-битный интерфейс
DL = 1 → 8-битный интерфейс

N = 0 → 1 строка
N = 1 → 2 строки

F = 0 → 5×8
F = 1 → 5×10
```

Наш байт:

```text
0010 1000
```

Разбирается так:

```text
0 0 1 0 1 0 0 0
      │ │ │
      │ │ └── F = 0 → 5×8
      │ └──── N = 1 → 2 строки
      └────── DL = 0 → 4-bit
```

Это хороший пример того, почему не стоит запоминать `0x28` как готовую магическую константу.

Гораздо важнее уметь открыть описание команды и самостоятельно собрать нужное значение из полей.

# 10. Остальные команды инициализации

Следующая команда:

```c
LCD_WriteCommand(0b00001100);
```

означает:

```text
дисплей включён
курсор выключен
мигание выключено
```

Далее:

```c
LCD_WriteCommand(0b00000110);
```

задаёт поведение адресного счётчика:

```text
после вывода символа переходить вправо
```

И наконец:

```c
LCD_Clear();
```

очищает экран.

Полная инициализация:

```c
void LCD_Init(void)
{
    LCD_RS_DDR |= (1 << LCD_RS_PIN);
    LCD_E_DDR  |= (1 << LCD_E_PIN);
    LCD_D4_DDR |= (1 << LCD_D4_PIN);
    LCD_D5_DDR |= (1 << LCD_D5_PIN);
    LCD_D6_DDR |= (1 << LCD_D6_PIN);
    LCD_D7_DDR |= (1 << LCD_D7_PIN);

    LCD_RS_PORT &= ~(1 << LCD_RS_PIN);
    LCD_E_PORT  &= ~(1 << LCD_E_PIN);

    _delay_ms(20);

    LCD_WriteCommandNibble(0x03);
    _delay_ms(5);

    LCD_WriteCommandNibble(0x03);
    _delay_us(150);

    LCD_WriteCommandNibble(0x03);
    _delay_us(150);

    LCD_WriteCommandNibble(0x02);
    _delay_us(150);

    LCD_WriteCommand(0b00101000);
    LCD_WriteCommand(0b00001100);
    LCD_WriteCommand(0b00000110);

    LCD_Clear();
}
```

# 11. Почему команда Clear требует особого ожидания

Большинство команд выполняется относительно быстро:

```c
_delay_us(50);
```

Но очистка экрана занимает больше времени:

```c
void LCD_Clear(void)
{
    LCD_WriteCommand(0x01);
    _delay_ms(2);
}
```

Причина не в том, что микроконтроллеру сложно отправить `0x01`.

Передача самого байта происходит быстро.

Больше времени требуется внутреннему контроллеру LCD для выполнения операции.

Если микроконтроллер отправит следующую команду раньше, чем дисплей закончит предыдущую, результат может оказаться неправильным:

```text
пропущенный символ
неверное положение курсора
необработанная команда
странное содержимое экрана
```

Есть два распространённых подхода:

```text
1. Читать Busy Flag
2. Использовать гарантированные задержки
```

Мы выбрали второй вариант.

Он проще:

```text
Отправили команду
        ↓
Подождали достаточное время
        ↓
Продолжили
```

Недостаток — процессор блокируется на время `_delay_us()` или `_delay_ms()`.

Для нашего проекта это приемлемый компромисс.

# 12. Вывод одного символа

После того как нижние уровни готовы, вывод одного символа становится простым:

```c
void LCD_PrintChar(char c)
{
    LCD_WriteData(c);
}
```

Например:

```c
LCD_PrintChar('A');
```

Цепочка вызовов:

```text
LCD_PrintChar('A')
        ↓
LCD_WriteData('A')
        ↓
RS = 1
        ↓
LCD_WriteByte()
        ↓
старший nibble
        ↓
E
        ↓
младший nibble
        ↓
E
        ↓
символ появляется на дисплее
```

Верхний уровень ничего не знает о GPIO.

Именно этого мы хотим добиться от хорошего драйвера.

# 13. Вывод строки

Теперь используем указатели из предыдущей части книги:

```c
void LCD_Print(const char *text)
{
    while (*text != '\0')
    {
        LCD_PrintChar(*text);
        text++;
    }
}
```

Допустим:

```c
LCD_Print("Hello");
```

Строка в памяти выглядит примерно так:

```text
'H'  'e'  'l'  'l'  'o'  '\0'
 ↑
text
```

`text` содержит адрес первого символа.

Выражение:

```c
*text
```

получает символ по текущему адресу.

После:

```c
text++;
```

указатель переходит к следующему символу.

Получаем:

```text
'H' → вывести
'e' → вывести
'l' → вывести
'l' → вывести
'o' → вывести
'\0' → остановиться
```

Здесь указатели перестают быть абстрактной темой языка C.

Они решают реальную задачу Embedded-разработки.

# 14. DDRAM и положение курсора

Дисплей показывает символы не просто «в строках».

Внутри контроллера есть память **DDRAM — Display Data RAM**.

Условно её можно представить так:

```text
Первая строка:

Адрес:  00 01 02 03 04 ... 0F
Символ:  H  e  l  l  o


Вторая строка:

Адрес:  40 41 42 43 44 ... 4F
Символ:  W  o  r  l  d
```

Для нашего LCD1602:

```text
первая строка начинается с 0x00
вторая строка начинается с 0x40
```

Поэтому функция:

```c
void LCD_SetCursor(uint8_t row, uint8_t column)
{
    uint8_t line = 0x00;

    if (row == 1)
    {
        line = 0x40;
    }

    if (column > 15)
    {
        column = 15;
    }

    LCD_WriteCommand((1 << 7) | (line + column));
}
```

сначала выбирает базовый адрес строки.

Для первой:

```text
0x00
```

Для второй:

```text
0x40
```

Затем добавляется номер столбца.

Например:

```c
LCD_SetCursor(1, 5);
```

Получаем:

```text
0x40 + 5 = 0x45
```

То есть курсор должен перейти к адресу DDRAM `0x45`.

---

# 15. Почему устанавливается седьмой бит

Команда установки адреса DDRAM имеет следующий общий вид:

```text
DB7 DB6 DB5 DB4 DB3 DB2 DB1 DB0
 1   AC6 AC5 AC4 AC3 AC2 AC1 AC0
```

Старший бит:

```text
DB7 = 1
```

сообщает:

> Это команда установки адреса DDRAM.

Остальные биты содержат адрес.

Поэтому мы пишем:

```c
LCD_WriteCommand((1 << 7) | (line + column));
```

Например:

```text
line   = 0x40
column = 5

address = 0x45
```

Команда:

```text
0x80 | 0x45 = 0xC5
```

После её выполнения следующий символ будет записан в выбранную позицию.

# 16. Печать двух цифр

Для отображения времени нам понадобилось выводить значения вроде:

```text
05
09
14
23
```

Поэтому появилась функция:

```c
void LCD_Print2Digits(uint8_t value)
{
    LCD_PrintChar((value / 10) + '0');
    LCD_PrintChar((value % 10) + '0');
}
```

Например:

```text
value = 37
```

Десятки:

```text
37 / 10 = 3
```

Единицы:

```text
37 % 10 = 7
```

Но числа `3` и `7` ещё не являются символами `'3'` и `'7'`.

Поэтому используется:

```c
+ '0'
```

Получаем:

```text
3 + '0' → '3'
7 + '0' → '7'
```

На дисплей выводится:

```text
37
```

# 17. Архитектура нашего драйвера

Наш драйвер построен слоями:

```text
LCD_Print()
    ↓
LCD_PrintChar()
    ↓
LCD_WriteData()
    ↓
LCD_WriteByte()
    ↓
LCD_WriteNibble()
    ↓
GPIO
```

Для команд:

```text
LCD_Clear()
или
LCD_SetCursor()
    ↓
LCD_WriteCommand()
    ↓
LCD_WriteByte()
    ↓
LCD_WriteNibble()
    ↓
GPIO
```

Каждый уровень отвечает только за свою задачу.

## `LCD_Print()`

Работает со строкой.

## `LCD_PrintChar()`

Работает с одним символом.

## `LCD_WriteData()`

Сообщает, что передаётся именно пользовательская информация.

## `LCD_WriteCommand()`

Сообщает, что передаётся команда.

## `LCD_WriteByte()`

Делит байт на две половины.

## `LCD_WriteNibble()`

Управляет физическими выводами.

## `LCD_PulseEnable()`

Даёт дисплею команду зафиксировать данные.

Это и есть разделение ответственности.

---

# 18. Почему нельзя написать всё в одной функции

Технически можно было создать огромную функцию:

```c
LCD_Print()
```

которая сама:

* проходила бы по строке;
* определяла символы;
* делила каждый байт;
* управляла `RS`;
* переключала GPIO;
* формировала `E`;
* создавала задержки.

Но тогда одна функция знала бы слишком много.

Любое изменение нижнего уровня затронуло бы весь код.

В нашей архитектуре:

```text
Приложение
не знает о nibble

LCD_Print()
не знает о GPIO

LCD_WriteByte()
не знает о строках

LCD_WriteNibble()
не знает, что передаётся:
символ, цифра или команда
```

Каждая функция решает одну понятную задачу.

Так код становится проще:

* читать;
* тестировать;
* отлаживать;
* изменять;
* использовать повторно.

# 19. Полный путь символа до экрана

Рассмотрим:

```c
LCD_SetCursor(1, 3);
LCD_Print("Hi");
```

Сначала:

```c
LCD_SetCursor(1, 3);
```

Определяется адрес:

```text
0x40 + 3 = 0x43
```

Формируется команда установки DDRAM:

```text
0x80 | 0x43
```

Команда передаётся через:

```text
LCD_WriteCommand()
        ↓
LCD_WriteByte()
        ↓
старший nibble
        ↓
E
        ↓
младший nibble
        ↓
E
```

Теперь курсор находится на второй строке в четвёртой позиции, если считать столбцы с нуля.

Далее:

```c
LCD_Print("Hi");
```

`text` указывает на:

```text
'H'
```

Вызывается:

```c
LCD_PrintChar('H');
```

Далее:

```text
LCD_WriteData()
      ↓
RS = 1
      ↓
LCD_WriteByte()
      ↓
передача двух nibble
```

На экране появляется:

```text
H
```

Затем:

```c
text++;
```

Указатель переходит к:

```text
'i'
```

Символ передаётся тем же путём.

Поскольку после предыдущего символа адресный счётчик переместился вправо, `i` появляется в соседней позиции.

Результат:

```text
┌──────────────────┐
│                  │
│   Hi             │
└──────────────────┘
```

# 20. Что происходит внутри микроконтроллера

Когда вызывается:

```c
LCD_Print("Hi");
```

процессор не отправляет дисплею высокоуровневую команду «напиши Hi».

В действительности происходит последовательность операций:

```text
Процессор получает адрес строки
        ↓
читает первый символ из памяти
        ↓
устанавливает RS = 1
        ↓
делит байт на две части
        ↓
меняет значения PORT-регистров
        ↓
на физических ножках появляются 0 и 1
        ↓
формируется импульс E
        ↓
LCD фиксирует nibble
        ↓
операция повторяется для второй половины
        ↓
LCD собирает полный байт
        ↓
контроллер дисплея интерпретирует его как символ
        ↓
символ появляется на экране
```

Высокоуровневая строка кода:

```c
LCD_Print("Hi");
```

скрывает десятки низкоуровневых операций.

Именно для этого мы строим драйвер.

# 21. Типичные ошибки

## Ошибка 1. Перепутать старший и младший nibble

Правильно:

```text
сначала high nibble
потом low nibble
```

В нашем коде:

```c
uint8_t highNibble = data >> 4;
uint8_t lowNibble = data & 0b00001111;
```

---

## Ошибка 2. Не формировать импульс E после каждого nibble

В 4-битном режиме один байт передаётся за два этапа.

Следовательно, требуется два события фиксации:

```text
high nibble → E
low nibble  → E
```

---

## Ошибка 3. Забыть установить RS

Если `RS` имеет неправильное значение, команда может быть воспринята как символ, а символ — как команда.

```text
RS = 0 → command
RS = 1 → data
```

---

## Ошибка 4. Сразу начать передавать полные команды после включения

До перехода в 4-битный режим используется специальная процедура инициализации.

Нельзя просто предполагать, что дисплей уже настроен так, как нам нужно.

---

## Ошибка 5. Не соблюдать задержки

LCD не обязан выполнять команду мгновенно.

Особенно это важно для:

```text
Clear Display
Return Home
```

Следующая команда не должна приходить раньше готовности контроллера.

---

## Ошибка 6. Считать вторую строку продолжением первой

Для нашего LCD1602:

```text
строка 0 → 0x00
строка 1 → 0x40
```

Поэтому переход ко второй строке выполняется через установку соответствующего DDRAM-адреса.

---

## Ошибка 7. Оставить магические числа без понимания

Например:

```c
LCD_WriteCommand(0x28);
```

работает.

Но инженер должен понимать:

```text
DL = 0
N  = 1
F  = 0
```

То есть:

```text
4-bit
2 lines
5×8
```

После изучения LCD1602 инженер должен понимать:

        ↓

# 24. Практическое задание

Самостоятельно расширить драйвер функцией:

```c
void LCD_PrintTime(uint8_t hours,
                   uint8_t minutes,
                   uint8_t seconds);
```

Она должна выводить:

```text
14:07:03
```

При этом однозначные значения должны иметь ведущий ноль:

```text
5 часов → 05
7 минут → 07
3 секунды → 03
```

Используй уже существующую функцию:

```c
LCD_Print2Digits();
```

Перед написанием кода продумай:

```text
Какие функции уже решают часть задачи?
Нужно ли LCD_PrintTime() знать что-нибудь о GPIO?
Должна ли она напрямую вызывать LCD_WriteNibble()?
```

Правильная архитектура должна позволить решить задачу только через публичные функции высокого уровня.

# Итог

LCD1602 стал для нас первым полноценным внешним устройством, где уже недостаточно просто выставить один бит регистра.

Чтобы вывести один символ, мы прошли через несколько уровней:

```text
строка
  ↓
символ
  ↓
байт
  ↓
два nibble
  ↓
GPIO
  ↓
электрические сигналы
  ↓
контроллер дисплея
  ↓
изображение символа
```

Мы не использовали готовую библиотеку.

Мы сами:

* настроили выводы;
* реализовали 4-битную передачу;
* сформировали импульс `E`;
* разделили команды и данные через `RS`;
* выполнили инициализацию;
* научились работать с DDRAM;
* создали вывод символов и строк;
* построили драйвер из нескольких уровней ответственности.

Именно здесь особенно хорошо виден главный принцип Embedded-разработки:

> За простой высокоуровневой командой почти всегда скрывается цепочка очень конкретных операций с памятью, регистрами, битами и физическими сигналами.

Инженер не обязан каждый раз вручную думать обо всей этой цепочке.

Но он должен понимать, что происходит внутри.

Именно для этого мы сначала строим драйвер сами — а уже потом позволяем себе вызвать:

```c
LCD_Print("Hello");
```
