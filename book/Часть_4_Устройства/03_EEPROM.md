# 03. EEPROM — память, которая переживает выключение питания

## История

К этому моменту наша кормушка уже умела многое.

Она могла:

* управлять светодиодом;
* читать кнопку;
* считать время через таймер;
* управлять сервоприводом через PWM;
* общаться по UART;
* работать с I2C и SPI;
* читать настоящее время из DS3231;
* выводить информацию на LCD1602.

Но оставалась одна неприятная проблема.

Представим, что пользователь настроил кормление:

```text
08:00
13:00
18:00
```

Микроконтроллер сохранил это расписание в обычных переменных:

```c
uint8_t feedingHour = 8;
uint8_t feedingMinute = 0;
```

Пока устройство работает, всё хорошо.

Но затем питание отключается.

```text
Питание выключено
        ↓
RAM очищается
        ↓
Настройки потеряны
```

После следующего запуска ATmega8 уже не знает, что пользователь раньше настроил кормление на 08:00.

Значит, нам нужна память, которая умеет хранить данные даже без питания.

Так в проекте появилась EEPROM.

---

# Постановка задачи

Нам нужно уметь сохранить байт данных так, чтобы он пережил:

```text
перезагрузку микроконтроллера
отключение питания
повторное включение устройства
```

То есть мы хотим сделать примерно так:

```c
EEPROM_WriteByte(10, 42);
```

Выключить питание.

Включить его снова.

И затем получить:

```c
uint8_t value = EEPROM_ReadByte(10);
```

Результат:

```text
42
```

Для нашей кормушки EEPROM в будущем может хранить:

```text
расписание кормления
настройки устройства
углы сервопривода
пользовательские параметры
флаги конфигурации
```

Но сначала нужно понять сам принцип работы.

---

# Простое объяснение

Обычную RAM можно представить как доску, на которой микроконтроллер пишет маркером.

Пока питание есть — всё видно.

Питание исчезло — доску стёрли.

```text
RAM

Питание есть:
[ 42 ]

Питание выключено:
[ ? ]
```

EEPROM ведёт себя иначе.

Она сохраняет записанные данные даже после отключения питания.

```text
EEPROM

Записали:
[ 42 ]

Питание выключено:
[ 42 ]

Питание включено снова:
[ 42 ]
```

То есть EEPROM — это энергонезависимая память.

Она не предназначена для постоянных быстрых изменений, как RAM.

Её задача другая:

> Хранить небольшие данные, которые должны пережить выключение устройства.

---

# RAM и EEPROM решают разные задачи

RAM удобна для данных, которые постоянно меняются во время работы программы.

Например:

```c
uint8_t seconds;
uint32_t systemTicks;
bool buttonPressed;
```

EEPROM нужна для данных, которые должны сохраняться надолго.

Например:

```text
время кормления
настройка громкости
последний выбранный режим
калибровочный коэффициент
серийный номер
```

Можно представить так:

```text
RAM
│
├── быстро
├── часто изменяется
└── теряется без питания


EEPROM
│
├── медленнее
├── записывается реже
└── сохраняется без питания
```

---

# Что происходит внутри ATmega8

Внутри ATmega8 уже есть собственная EEPROM.

То есть нам не нужно обязательно подключать отдельную микросхему памяти.

Микроконтроллер предоставляет специальные регистры для работы с ней.

Нас интересуют три основных регистра:

```text
EEAR
EEDR
EECR
```

Проще всего запомнить их так:

```text
EEAR → где?

EEDR → что?

EECR → что делать?
```

---

# Регистр EEAR

`EEAR` — EEPROM Address Register.

Он хранит адрес ячейки EEPROM, с которой мы хотим работать.

Например:

```c
EEAR = 10;
```

означает:

> Следующая операция будет выполняться с ячейкой номер 10.

Условно EEPROM можно представить как массив:

```text
Адрес    Значение

0        ?
1        ?
2        ?
3        ?
...
10       ?
11       ?
...
```

Мы выбираем конкретную ячейку через:

```c
EEAR = address;
```

---

# Регистр EEDR

`EEDR` — EEPROM Data Register.

Он содержит сами данные.

Если мы хотим записать значение `42`, то делаем:

```c
EEDR = 42;
```

Идея такая:

```text
EEAR = 10
↓
работаем с ячейкой 10

EEDR = 42
↓
работаем со значением 42
```

Вместе:

```text
Записать 42 по адресу 10.
```

---

# Регистр EECR

`EECR` — управляющий регистр EEPROM.

Через его биты микроконтроллер понимает, какую операцию мы хотим выполнить.

В нашей реализации используются:

```text
EERE
EEMWE
EEWE
```

И у каждого своя задача.

---

# Чтение одного байта

Наша функция:

```c
uint8_t EEPROM_ReadByte(uint16_t address)
{
    while (EECR & (1 << EEWE))
    {
    }

    EEAR = address;

    EECR |= (1 << EERE);

    return EEDR;
}
```

Разберём по шагам.

---

# Шаг 1. Ждём окончания предыдущей записи

```c
while (EECR & (1 << EEWE))
{
}
```

Пока бит `EEWE` установлен, EEPROM занята записью.

Мы ждём:

```text
EEPROM занята?
    │
    ├── Да → ждём
    │
    └── Нет → продолжаем
```

Это важно, потому что мы не должны начинать новую операцию, пока предыдущая запись ещё не завершена.

---

# Шаг 2. Указываем адрес

```c
EEAR = address;
```

Теперь EEPROM знает, с какой ячейкой нужно работать.

Например:

```c
EEAR = 10;
```

означает:

```text
Выбрать ячейку 10.
```

---

# Шаг 3. Запускаем чтение

```c
EECR |= (1 << EERE);
```

Установка бита `EERE` запускает операцию чтения.

После этого содержимое выбранной ячейки EEPROM попадает в `EEDR`.

Схема:

```text
EEAR
 ↓
выбран адрес

EERE
 ↓
запустить чтение

EEPROM[address]
 ↓
EEDR
```

---

# Шаг 4. Возвращаем данные

```c
return EEDR;
```

Теперь функция отдаёт прочитанный байт вызывающему коду.

Полная логика:

```text
Ждём окончания записи
        ↓
Указываем адрес
        ↓
Запускаем чтение
        ↓
Данные попадают в EEDR
        ↓
Возвращаем байт
```

---

# Запись одного байта

Теперь рассмотрим:

```c
void EEPROM_WriteByte(uint16_t address, uint8_t data)
{
    while (EECR & (1 << EEWE))
        ;

    EEAR = address;
    EEDR = data;

    EECR |= (1 << EEMWE);
    EECR |= (1 << EEWE);
}
```

Здесь логика уже немного сложнее.

---

# Сначала ждём

```c
while (EECR & (1 << EEWE))
    ;
```

Пока предыдущая запись не закончилась, новую не начинаем.

---

# Затем задаём адрес и данные

```c
EEAR = address;
EEDR = data;
```

Например:

```c
EEPROM_WriteByte(10, 42);
```

внутри означает:

```text
EEAR = 10
EEDR = 42
```

То есть:

```text
Куда записать? → 10

Что записать?  → 42
```

---

# Почему нельзя просто установить EEWE

Может возникнуть вопрос:

> Почему бы сразу не сделать:

```c
EECR |= (1 << EEWE);
```

Потому что перед запуском записи нужна специальная последовательность.

Сначала:

```c
EECR |= (1 << EEMWE);
```

А затем:

```c
EECR |= (1 << EEWE);
```

Условно:

```text
EEMWE
↓
«Разрешаю запись»

EEWE
↓
«Начинаю запись»
```

Такой двухэтапный механизм защищает EEPROM от случайной записи.

Если код из-за ошибки случайно затронет один управляющий бит, одной операции недостаточно.

---

# Что значит EEMWE

`EEMWE` можно воспринимать как предварительное разрешение.

Микроконтроллеру сообщают:

> Следующая операция записи действительно запланирована.

После этого уже устанавливается:

```c
EEWE
```

который запускает саму запись.

---

# Что значит EEWE

`EEWE` показывает, что EEPROM выполняет запись.

Пока он установлен:

```text
EEPROM занята
```

Именно поэтому перед следующим чтением или записью мы проверяем:

```c
while (EECR & (1 << EEWE))
{
}
```

---

# Полная последовательность записи

```text
Ждём, пока EEPROM свободна
        ↓
Указываем адрес
        ↓
Записываем данные в EEDR
        ↓
Устанавливаем EEMWE
        ↓
Устанавливаем EEWE
        ↓
Начинается физическая запись
```

---

# Почему появилась EEPROM_UpdateByte

Обычная функция записи:

```c
EEPROM_WriteByte(address, data);
```

записывает значение всегда.

Даже если в этой ячейке уже хранится точно такой же байт.

Например:

```text
Сейчас в ячейке:
42

Хотим записать:
42
```

Обычный `WriteByte` всё равно запустит новую операцию записи.

Но зачем?

Значение ведь уже правильное.

Поэтому мы добавили:

```c
void EEPROM_UpdateByte(uint16_t address, uint8_t data)
{
    if (EEPROM_ReadByte(address) == data)
    {
        return;
    }

    EEPROM_WriteByte(address, data);
}
```

---

# Как работает UpdateByte

Логика очень простая:

```text
Прочитать текущее значение
        ↓
Сравнить с новым
        ↓
Совпадает?
    │
    ├── Да → ничего не делать
    │
    └── Нет → выполнить запись
```

Например:

```c
EEPROM_UpdateByte(10, 42);
```

Если по адресу `10` уже лежит `42`, функция завершится сразу.

---

# Зачем избегать лишних записей

EEPROM имеет ограниченный ресурс циклов записи.

Поэтому нельзя относиться к ней как к обычной RAM и постоянно делать:

```c
while (1)
{
    EEPROM_WriteByte(0, value);
}
```

Даже если `value` не меняется.

Так мы будем снова и снова физически перезаписывать одну и ту же ячейку.

Это бессмысленно и сокращает ресурс памяти.

Поэтому хорошая практика:

```text
Писать только тогда, когда данные реально изменились.
```

Именно для этого существует:

```c
EEPROM_UpdateByte(...)
```

---

# Что произойдёт после отключения питания

Допустим:

```c
EEPROM_WriteByte(10, 42);
```

EEPROM завершила запись.

Затем питание отключили.

После повторного запуска:

```c
uint8_t value = EEPROM_ReadByte(10);
```

Результат:

```text
42
```

Именно поэтому EEPROM называется энергонезависимой памятью.

---

# Простая ASCII-схема

```text
Запись:

address = 10
data    = 42

        ↓

EEAR = 10
EEDR = 42

        ↓

EEMWE
        ↓
EEWE

        ↓

EEPROM[10] = 42
```

После выключения:

```text
Питание OFF
        ↓
EEPROM[10] = 42
```

После включения:

```text
EEPROM_ReadByte(10)
        ↓
42
```

---

# Проектирование драйвера

Наша реализация предоставляет три функции:

```c
uint8_t EEPROM_ReadByte(uint16_t address);

void EEPROM_WriteByte(uint16_t address, uint8_t data);

void EEPROM_UpdateByte(uint16_t address, uint8_t data);
```

Это хороший низкоуровневый интерфейс.

Он отвечает на понятные вопросы:

```text
Прочитай байт

Запиши байт

Обнови байт, если значение изменилось
```

Но важно понимать: драйвер EEPROM не должен знать, зачем эти данные нужны.

Он не должен знать:

```text
это время кормления
это настройка сервы
это громкость
это язык меню
```

Для него существует только:

```text
адрес
значение
```

---

# Почему не стоит работать с адресами прямо из Scheduler

Можно написать так:

```c
EEPROM_UpdateByte(0, hour);
EEPROM_UpdateByte(1, minute);
```

прямо внутри `scheduler.c`.

Это будет работать.

Но архитектурно возникает проблема.

Теперь `Scheduler` знает:

```text
адрес 0 → часы

адрес 1 → минуты
```

Если потом структура хранения изменится, придётся менять `Scheduler`.

Это нарушение разделения ответственности.

---

# Более правильный уровень абстракции

Лучше сделать отдельный модуль:

```c
Settings_SaveFeedingTime(hour, minute);
```

И уже внутри него:

```text
адрес 0 → часы

адрес 1 → минуты
```

Тогда архитектура становится такой:

```text
Scheduler
    ↓
Settings
    ↓
EEPROM
    ↓
EEPROM hardware
```

Ответственности разделены.

---

# EEPROM должна знать только о памяти

Драйвер EEPROM должен знать:

```text
как выбрать адрес
как читать
как записывать
как ждать окончания записи
как избежать лишней записи
```

Он не должен знать:

```text
когда кормить питомца
что такое расписание
что означает число 8
что означает число 18
```

---

# Settings должен знать структуру настроек

Модуль `settings` уже может знать:

```text
адрес 0 → количество кормлений

адрес 1 → час первого кормления

адрес 2 → минута первого кормления
```

И предоставить интерфейс:

```c
Settings_SaveFeedingTime(...);

Settings_LoadFeedingTime(...);
```

---

# Scheduler должен знать только о расписании

`Scheduler` должен думать так:

```text
Какое сейчас время?

Есть ли в расписании кормление?

Пора ли запускать событие?
```

Но не так:

```text
В какую ячейку EEPROM записать часы?
```

Это не его задача.

---

# Архитектура проекта

Идеальная цепочка:

```text
Application
    ↓
Scheduler
    ↓
Settings
    ↓
EEPROM Driver
    ↓
EEPROM hardware
```

Каждый слой знает только свою часть системы.

---

# Что происходит внутри микроконтроллера при чтении

Когда вызывается:

```c
EEPROM_ReadByte(10);
```

внутри происходит:

```text
1. CPU проверяет EEWE.

2. Если EEPROM занята, ждёт.

3. В EEAR записывается 10.

4. В EECR устанавливается EERE.

5. Контроллер EEPROM читает ячейку 10.

6. Значение помещается в EEDR.

7. CPU возвращает EEDR.
```

Внешний код видит только:

```c
uint8_t value = EEPROM_ReadByte(10);
```

---

# Что происходит внутри при записи

Когда вызывается:

```c
EEPROM_WriteByte(10, 42);
```

происходит:

```text
1. CPU ждёт освобождения EEPROM.

2. В EEAR записывается адрес 10.

3. В EEDR записывается 42.

4. Устанавливается EEMWE.

5. Затем устанавливается EEWE.

6. Контроллер EEPROM начинает запись.

7. После завершения EEWE сбрасывается.
```

---

# Что происходит внутри UpdateByte

```c
EEPROM_UpdateByte(10, 42);
```

Сначала:

```text
EEPROM_ReadByte(10)
```

Допустим, получили:

```text
42
```

Сравнение:

```text
42 == 42
```

Результат:

```text
Запись не нужна.
```

Если было бы:

```text
41
```

то функция вызвала бы:

```c
EEPROM_WriteByte(10, 42);
```

---

# Типичные ошибки

## Ошибка 1. Считать EEPROM обычной RAM

Плохо:

```c
while (1)
{
    EEPROM_WriteByte(0, value);
}
```

Так нельзя использовать EEPROM бездумно.

У неё другая задача.

---

## Ошибка 2. Писать одно и то же значение снова и снова

Например:

```text
в ячейке уже 42

записываем 42

снова 42

ещё раз 42
```

Лучше использовать:

```c
EEPROM_UpdateByte(...)
```

---

## Ошибка 3. Не дождаться окончания предыдущей записи

Перед новой операцией нужно убедиться, что:

```text
EEWE == 0
```

Иначе EEPROM ещё может быть занята.

---

## Ошибка 4. Путать EEAR и EEDR

Запомнить просто:

```text
EEAR → address

EEDR → data
```

То есть:

```text
где?

что?
```

---

## Ошибка 5. Забыть последовательность EEMWE → EEWE

Для записи нужно:

```text
сначала разрешить
потом запустить
```

---

## Ошибка 6. Хранить адреса EEPROM прямо в прикладной логике

Плохо:

```c
EEPROM_UpdateByte(0, hour);
EEPROM_UpdateByte(1, minute);
```

из разных мест программы.

Так быстро появляется хаос.

Лучше централизовать структуру данных.

---

## Ошибка 7. Не продумывать карту памяти

Как только данных становится больше, нужна понятная разметка.

Например:

```text
Адрес    Назначение

0        magic value
1        количество кормлений
2        час первого кормления
3        минута первого кормления
4        час второго кормления
5        минута второго кормления
```

Иначе со временем невозможно понять, что где хранится.

---

# Практическое применение

EEPROM полезна там, где настройки должны переживать отключение питания.

Например:

```text
умная кормушка
термостат
система полива
будильник
робот
измерительный прибор
контроллер освещения
настройки меню
калибровочные данные
```

В нашей кормушке логичный сценарий такой:

```text
Пользователь настроил время кормления
        ↓
Settings сохранил его в EEPROM
        ↓
Питание выключилось
        ↓
Кормушка включилась снова
        ↓
Settings загрузил данные
        ↓
Scheduler продолжил работу
```

# Как инженер пришёл к этому решению

Сначала появилась проблема:

> Настройки исчезают после выключения питания.

Мы посмотрели на обычные переменные.

Они находятся в RAM.

RAM теряет данные без питания.

Значит, нужна энергонезависимая память.

У ATmega8 уже есть встроенная EEPROM.

Дальше мы нашли:

```text
EEAR
EEDR
EECR
```

И разделили их роли:

```text
EEAR → адрес

EEDR → данные

EECR → управление
```

Потом появилась ещё одна проблема:

> Можно ли писать в EEPROM постоянно?

Нет, потому что ресурс записи ограничен.

Значит, нужно избегать бессмысленных перезаписей.

Так появилась:

```c
EEPROM_UpdateByte(...)
```

И затем возник уже архитектурный вопрос:

> Кто должен знать, что адрес 0 — это часы, а адрес 1 — минуты?

Не Scheduler.

Для этого лучше создать отдельный слой настроек.

Так из простой задачи чтения и записи байта мы пришли к более правильной архитектуре проекта.

---

# Что должен уметь инженер

После этой главы инженер должен уметь объяснить:

* зачем нужна EEPROM;
* чем EEPROM отличается от RAM;
* почему данные EEPROM переживают выключение питания;
* за что отвечает EEAR;
* за что отвечает EEDR;
* за что отвечает EECR;
* зачем нужен EERE;
* зачем нужен EEMWE;
* зачем нужен EEWE;
* почему перед операцией нужно ждать освобождения EEPROM;
* как читается один байт;
* как записывается один байт;
* зачем нужна `EEPROM_UpdateByte`;
* почему нельзя постоянно писать одно и то же значение;
* почему адреса настроек не должны быть разбросаны по всему приложению;
* зачем нужен отдельный слой `Settings`.

Но важнее понять общий принцип:

> Память — это не просто место, куда можно записать число. Нужно понимать, кто владеет данными, кто знает их структуру и кто отвечает только за физическую работу с памятью.

# Практическое задание

Сохрани в EEPROM два значения:

```text
час кормления
минута кормления
```

Например:

```text
08:30
```

После этого:

1. Отключи питание.
2. Включи микроконтроллер снова.
3. Прочитай оба значения.
4. Убедись, что получил:

```text
08:30
```

Следующий уровень задачи:

Создай модуль:

```text
settings.c
settings.h
```

с интерфейсом:

```c
void Settings_SaveFeedingTime(uint8_t hour, uint8_t minute);

void Settings_LoadFeedingTime(uint8_t *hour, uint8_t *minute);
```

А работу с адресами EEPROM спрячь внутрь `settings.c`.

# Итог

До появления EEPROM наша кормушка могла работать только с теми данными, которые живут до выключения питания.

Теперь она получила память.

Не временную.

А такую, которая может сказать:

> Да, я помню, что было настроено до выключения.

Для этого мы изучили:

```text
EEAR
↓
где работать

EEDR
↓
с какими данными работать

EECR
↓
какую операцию выполнить
```

Разобрались с:

```text
EERE
EEMWE
EEWE
```

Научились читать:

```c
EEPROM_ReadByte(...)
```

Писать:

```c
EEPROM_WriteByte(...)
```

И избегать лишних записей:

```c
EEPROM_UpdateByte(...)
```

Но самое важное — мы снова пришли не просто к регистрам, а к архитектуре.

```text
Scheduler
    ↓
Settings
    ↓
EEPROM Driver
    ↓
EEPROM Hardware
```

Каждый слой отвечает только за своё.

Именно так отдельные функции постепенно превращаются в настоящий Embedded-проект.
