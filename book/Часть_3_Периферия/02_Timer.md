# Timer — когда микроконтроллер учится чувствовать время

## История

Когда я только начинал изучать Embedded, мне казалось, что время — это самая простая вещь в программировании.

Нужно подождать секунду?

```c
_delay_ms(1000);
```

Нужно мигать светодиодом?

```c
while (1)
{
    LED_Toggle();
    _delay_ms(500);
}
```

Работает же.

Проблемы начались тогда, когда устройство стало делать больше одной вещи одновременно.

Я захотел, чтобы кормушка:

* проверяла кнопку;
* поворачивала сервопривод;
* отсчитывала время;
* позже — работала с часами реального времени;
* и при этом продолжала реагировать на пользователя.

Именно в этот момент стало понятно: процессор не может просто «стоять и ждать». Пока он ждёт — он ничего больше не делает.

Значит, нужен другой способ работать со временем.

---

# Постановка задачи

Представим, что нужно открыть заслонку кормушки ровно на одну секунду.

Первое желание выглядит так:

```c
Servo_Open();

_delay_ms(1000);

Servo_Close();
```

На первый взгляд всё правильно.

Но что происходит в эту секунду?

* кнопки не читаются;
* другие устройства не работают;
* программа буквально стоит на месте.

Получается, что микроконтроллер перестаёт быть системой управления и превращается в секундомер.

---

# Почему `_delay_ms()` — плохое решение

Самая большая проблема заключается не в самой функции.

Она делает именно то, что обещает.

Проблема в том, что ожидание полностью блокирует выполнение программы.

Можно представить процессор как одного сотрудника.

Пока ему говорят:

> «Подожди одну секунду и ничего не делай»,

он действительно ничего больше сделать не сможет.

Если в этот момент пользователь нажмёт кнопку, процессор узнает об этом только после окончания задержки.

Для простых примеров это допустимо.

Для настоящих устройств — практически никогда.

---

# Как инженер начинает думать по-другому

Вместо вопроса

> «Как подождать одну секунду?»

инженер начинает задавать другой вопрос:

> «Как узнать, что одна секунда уже прошла?»

Разница кажется небольшой.

Но именно она полностью меняет архитектуру программы.

Вместо ожидания появляется проверка.

Вместо блокировки — выполнение других задач.

---

# Что такое Timer

Внутри микроконтроллера есть специальный аппаратный блок — таймер.

Он умеет самостоятельно считать такты процессора.

Главное слово здесь — **самостоятельно**.

Пока процессор выполняет основной код программы, таймер продолжает считать.

Когда происходит заранее настроенное событие, таймер сообщает процессору об этом через прерывание.

Получается примерно так:

```text
Процессор
│
├── читает кнопку
├── управляет сервой
├── работает с дисплеем
│
└───────────────┐
                │
          Таймер считает время
                │
                ▼
        Произошло событие
                │
                ▼
       Вызывается прерывание
```

Именно поэтому Timer позволяет работать со временем без остановки всей программы.

---

# Что происходит внутри микроконтроллера

Каждый такт таймер увеличивает своё внутреннее значение.

Когда счётчик достигает определённого значения, происходит событие.

В нашем проекте этим событием стало переполнение таймера.

Процессор автоматически прерывает выполнение текущего кода, вызывает обработчик прерывания, после чего продолжает работу с того места, где остановился.

В обработчике мы увеличиваем собственный программный счётчик времени.

Именно так появился `systemTicks`.

---

# Наш программный счётчик времени

Сам аппаратный таймер умеет считать только внутри своего регистра.

Но нам удобнее иметь собственный счётчик, который постоянно увеличивается.

В обработчике прерывания это выглядит очень просто.

```c
systemTicks++;
```

Получается, что `systemTicks` становится единым источником времени для всей программы.

Любой модуль может узнать, сколько времени прошло с момента запуска устройства.

---

# Почему `volatile` обязателен

Переменная `systemTicks` изменяется внутри обработчика прерывания.

Основной код программы её не изменяет.

Если не написать `volatile`, компилятор может решить, что значение никогда не меняется, и сохранить его в регистре процессора вместо повторного чтения из памяти.

Тогда программа будет работать с устаревшим значением времени.

Ключевое слово `volatile` говорит компилятору:

> «Не делай предположений. Каждый раз считывай значение из памяти заново.»

---

# Почему чтение защищается через `cli()` и `sei()`

В нашем проекте `systemTicks` имеет тип `uint32_t`.

Но AVR — восьмибитный микроконтроллер.

Это означает, что четыре байта читаются не одновременно.

Представим ситуацию.

Процессор уже прочитал первые два байта.

В этот момент происходит прерывание.

Обработчик увеличивает `systemTicks`.

После возврата процессор дочитывает оставшиеся два байта.

В результате получится число, которого никогда не существовало.

Часть байтов относится к старому значению, часть — к новому.

Чтобы этого не произошло, чтение выполняется так:

```c
cli();

/* чтение systemTicks */

sei();
```

На несколько инструкций прерывания запрещаются, после чего снова разрешаются.

---

# Почему проверка времени лучше ожидания

Вместо ожидания мы запоминаем момент начала.

```c
uint32_t startTime = Timer_GetTicks();
```

Позже просто спрашиваем:

> «Прошёл ли нужный интервал?»

```c
Timer_HasElapsed(startTime, intervalTicks);
```

Если нет — программа продолжает выполнять другие задачи.

Если да — выполняет нужное действие.

Всё это происходит без единой блокирующей задержки.

---

# Почему функция работает даже после переполнения

На первый взгляд кажется, что переполнение должно сломать программу.

Например:

```text
4294967294
4294967295
0
1
2
```

Но `uint32_t` использует арифметику по модулю `2³²`.

Поэтому выражение

```c
Timer_GetTicks() - startTime
```

корректно вычисляет прошедшее время даже после переполнения счётчика.

Именно поэтому подобный способ измерения времени используется практически во всех Embedded-проектах.

---

# Регистры, которые мы использовали

Во время настройки таймера мы работали с несколькими регистрами.

Каждый из них отвечает только за одну часть работы.

* `TCCR0` — режим работы таймера и источник тактирования.
* `TCNT0` — текущее значение счётчика.
* `TIMSK` — разрешение прерываний таймера.
* `TIFR` — флаги событий таймера.

На этом этапе не стоит пытаться запомнить каждый бит.

Гораздо важнее понимать общую идею:

1. выбрать источник тактирования;
2. разрешить прерывание;
3. обработать событие переполнения.

---

# Проектирование драйвера

Мы решили полностью скрыть работу с регистрами внутри драйвера.

Внешний код ничего не знает о том, какие регистры используются.

Ему доступны только понятные функции.

```text
Timer_Init()

Timer_GetTicks()

Timer_HasElapsed()
```

Такой подход делает проект проще.

Если позже мы перейдём на другой микроконтроллер, большая часть программы вообще не изменится.

---

# Как Timer изменил архитектуру проекта

После появления таймера многие задачи стали использовать один и тот же источник времени.

```text
                Timer
                   │
      ┌────────────┼────────────┐
      │            │            │
      ▼            ▼            ▼
   Кнопка      Сервопривод   Scheduler
      │            │            │
      └────────────┼────────────┘
                   ▼
              Всё устройство
```

Позже в проекте появился модуль часов реального времени DS3231.

Но его задача совсем другая.

DS3231 отвечает на вопрос:

> «Который сейчас час?»

Timer отвечает на вопрос:

> «Сколько прошло времени?»

Эти два устройства не заменяют друг друга, а дополняют.

---

# Типичные ошибки

* Использовать `_delay_ms()` внутри логики программы.
* Забыть объявить `systemTicks` как `volatile`.
* Читать `uint32_t` без отключения прерываний.
* Пытаться самостоятельно обрабатывать переполнение счётчика.
* Привязывать все интервалы к жёстким задержкам.

---

# Практическое применение

Практически каждое встроенное устройство использует таймеры.

Например:

* антидребезг кнопок;
* мигание светодиодов;
* управление сервоприводами;
* работа планировщика;
* измерение времени;
* генерация PWM;
* обмен по некоторым интерфейсам связи.

Без таймеров невозможно представить современную Embedded-разработку.

* почему блокирующие задержки плохо подходят для реальных устройств;
* зачем нужны аппаратные таймеры;
* как работают прерывания;
* зачем используется `volatile`;
* почему чтение многобайтных переменных защищают через `cli()` и `sei()`;
* как измерять интервалы времени без блокировки программы;
* почему выражение `currentTime - startTime` безопасно даже после переполнения счётчика.
