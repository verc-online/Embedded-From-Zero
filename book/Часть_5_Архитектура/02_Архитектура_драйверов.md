# 02. Архитектура драйверов

## История

Когда мы только начинаем работать с микроконтроллером, код обычно выглядит просто.

Например, чтобы включить светодиод, можно написать:

```c
DDRB |= (1 << PB0);
PORTB |= (1 << PB0);
```

Чтобы выключить:

```c
PORTB &= ~(1 << PB0);
```

Чтобы настроить таймер, мы напрямую работаем с:

```c
TCCR0;
TCNT0;
TIMSK;
```

Для PWM появляются:

```c
TCCR1A;
TCCR1B;
ICR1;
OCR1A;
```

Для I2C:

```c
TWBR;
TWCR;
TWSR;
TWDR;
```

Для EEPROM:

```c
EECR;
EEDR;
EEAR;
```

Пока проект маленький, всё это кажется нормальным.

Можно написать:

```c
int main(void)
{
    DDRB |= (1 << PB0);

    TCCR1A |= (1 << WGM11);
    TCCR1B |= (1 << WGM13) | (1 << WGM12);

    OCR1A = 188;

    while (1)
    {
    }
}
```

Код работает.

Но потом в проекте появляются:

```text
кнопка
таймер
сервопривод
I2C
RTC
EEPROM
LCD1602
Scheduler
Menu
```

И `main.c` начинает превращаться в место, где известно всё обо всём.

Он знает:

```text
какой бит отвечает за PWM;
какой регистр запускает TWI;
какой адрес у DS3231;
как устроен BCD;
какой бит EEPROM означает запись;
какие пины подключены к LCD;
под каким углом должна открываться заслонка.
```

Такой проект ещё может работать.

Но поддерживать его становится всё сложнее.

И здесь появляется важный архитектурный вопрос:

> Кто вообще должен знать детали работы конкретного устройства?

Ответ приводит нас к драйверам.

---

# Постановка задачи

Представим, что главному коду нужно повернуть сервопривод на 90 градусов.

Можно написать:

```c
OCR1A = 188;
```

Но что означает число `188`?

Почему именно `OCR1A`?

Почему не `OCR1B`?

Почему значение 188 соответствует примерно 1,5 мс?

Почему период равен 20 мс?

Почему используется Timer1?

Почему нужен Fast PWM?

Почему выбран prescaler 8?

Все эти вопросы относятся к реализации работы сервопривода.

Но должны ли они интересовать `main.c`?

Нет.

Главному коду нужно только выразить намерение:

```c
Servo_SetAngle(90);
```

Именно в этом состоит одна из главных идей драйвера.

Драйвер скрывает аппаратные детали и предоставляет понятный интерфейс для работы с устройством.

---

# Простое объяснение

Представим автомобиль.

Когда водитель хочет повернуть направо, он поворачивает руль.

Он не думает:

```text
сейчас я изменю положение рулевой рейки;
создам механическое усилие;
поверну тяги;
изменю угол поворотных кулаков;
поверну передние колёса.
```

Он просто делает:

```text
Повернуть направо.
```

Руль становится интерфейсом.

А вся внутренняя механика скрыта.

С драйверами происходит то же самое.

Вместо:

```c
OCR1A = 250;
```

мы пишем:

```c
Servo_SetAngle(180);
```

Вместо:

```c
TWCR = (1 << TWINT) |
       (1 << TWSTA) |
       (1 << TWEN);
```

мы пишем:

```c
TWI_Start();
```

Вместо прямой работы с регистрами EEPROM:

```c
EEAR = address;
EEDR = data;
EECR |= (1 << EEMWE);
EECR |= (1 << EEWE);
```

мы пишем:

```c
EEPROM_WriteByte(address, data);
```

То есть драйвер отвечает на вопрос:

> Как выполнить действие на конкретном железе?

А остальная программа отвечает на вопрос:

> Зачем это действие нужно выполнить?

---

# Что такое драйвер

В контексте нашего проекта драйвер — это программный модуль, который управляет конкретной периферией или устройством.

Например:

```text
Timer
Servo
TWI
DS3231
EEPROM
LCD1602
Button
```

Каждый такой модуль имеет свою ответственность.

Например:

```text
Timer
    знает, как настроить аппаратный таймер;
    считает системные тики;
    предоставляет текущее время.

Servo
    знает, как преобразовать угол в PWM.

TWI
    знает, как отправить START;
    как передать байт;
    как получить ACK.

DS3231
    знает адрес RTC;
    знает карту регистров;
    преобразует BCD.

EEPROM
    знает, как читать и записывать энергонезависимую память.

LCD1602
    знает, как отправлять команды и данные дисплею.
```

Главный код не должен повторять эти знания.

---

# Главный принцип: разделение ответственности

Рассмотрим архитектуру кормушки:

```text
main.c
   |
   v
Application
   |
   +---- Feeder
   +---- Scheduler
   +---- Menu
   |
   v
Device drivers
   |
   +---- Servo
   +---- DS3231
   +---- LCD1602
   |
   v
Peripheral drivers
   |
   +---- Timer
   +---- TWI
   +---- EEPROM
   +---- GPIO
```

Каждый уровень решает свою задачу.

Например:

```text
Scheduler
    знает:
        когда должно произойти кормление.

Feeder
    знает:
        как ведёт себя кормушка.

Servo
    знает:
        как повернуть сервопривод.

Timer1
    знает:
        как сформировать PWM.
```

Важно заметить:

`Scheduler` не должен знать про `OCR1A`.

`Feeder` не должен знать про `TCCR1A`.

`Servo` не должен знать, почему его поворачивают.

Timer1 не должен знать, что управляет кормушкой.

Это и называется разделением ответственности.

---

# Путь от регистра к действию

Рассмотрим наш сервопривод.

На самом нижнем уровне происходит работа с регистром:

```c
OCR1A = pulseTicks;
```

Но главному приложению неудобно мыслить тиками.

Оно хочет работать с углами.

Поэтому драйвер предоставляет:

```c
void Servo_SetAngle(uint8_t angle);
```

Внутри происходит преобразование:

```text
Угол
    |
    v
Длительность импульса
    |
    v
Количество тиков Timer1
    |
    v
OCR1A
```

Например:

```text
0°
    |
    v
1 мс
    |
    v
125 тиков
```

```text
90°
    |
    v
1,5 мс
    |
    v
188 тиков
```

```text
180°
    |
    v
2 мс
    |
    v
250 тиков
```

Внешний код видит только:

```c
Servo_SetAngle(90);
```

Драйвер скрывает всё остальное.

Это называется абстракцией.

---

# Абстракция

Абстракция означает, что мы работаем с понятным смыслом, не погружаясь каждый раз во внутреннюю реализацию.

Сравним.

Первый вариант:

```c
OCR1A = 188;
```

Вопросы:

```text
Что такое 188?
Почему OCR1A?
Почему это вообще связано с сервой?
```

Второй вариант:

```c
Servo_SetAngle(90);
```

Смысл виден сразу.

Именно поэтому хороший интерфейс драйвера должен говорить на языке задачи.

Плохо:

```c
Servo_SetOCR1A(uint16_t value);
```

Потому что наружу снова торчит аппаратная реализация.

Лучше:

```c
Servo_SetAngle(uint8_t angle);
```

Теперь пользователь драйвера работает с понятием:

```text
угол
```

а не с понятием:

```text
значение регистра сравнения Timer1.
```

---

# Заголовочный файл как контракт

Обычно модуль состоит из двух файлов:

```text
servo.h
servo.c
```

Файл `servo.h` можно представить как контракт.

Он говорит другим модулям:

> Вот что я умею.

Например:

```c
#ifndef SERVO_H_
#define SERVO_H_

#include <stdint.h>

void Servo_Init(void);
void Servo_SetAngle(uint8_t angle);

#endif
```

Другим частям проекта не нужно знать больше.

Они не должны видеть:

```c
static uint16_t Servo_AngleToTicks(uint8_t angle);
```

или внутренние константы:

```c
#define SERVO_MIN_TICKS 125
#define SERVO_MAX_TICKS 250
```

Если эти детали нужны только внутри `servo.c`, они должны оставаться там.

---

# Публичный и приватный интерфейс

Рассмотрим:

```c
void Servo_Init(void);
void Servo_SetAngle(uint8_t angle);
```

Это публичные функции.

Их могут вызывать другие модули.

Например:

```c
Feeder_Request();
```

внутри вызывает:

```c
Servo_SetAngle(FEEDER_OPEN_ANGLE);
```

Но внутри `servo.c` может быть вспомогательная функция:

```c
static uint16_t Servo_AngleToTicks(uint8_t angle);
```

Она нужна только самому драйверу.

Поэтому мы объявляем её как `static`.

Получается:

```text
Публичный интерфейс:
    Servo_Init()
    Servo_SetAngle()

Внутренняя реализация:
    Servo_AngleToTicks()
    работа с OCR1A
    формула пересчёта
```

Другой модуль не должен иметь доступ к внутренним деталям без необходимости.

---

# Почему это важно

Представим, что сегодня сервопривод работает через Timer1 и `OCR1A`.

Завтра мы решили использовать другой микроконтроллер.

Или другой таймер.

Или внешний PWM-контроллер.

Если приложение напрямую пишет:

```c
OCR1A = 188;
```

нам придётся менять весь проект.

Но если приложение использует:

```c
Servo_SetAngle(90);
```

то меняется только реализация драйвера.

Для остальной программы интерфейс остаётся прежним.

Например:

```text
Было:

Servo_SetAngle()
    |
    v
Timer1
    |
    v
OCR1A
```

Стало:

```text
Servo_SetAngle()
    |
    v
Внешний PWM-контроллер
    |
    v
I2C
```

Приложение всё равно вызывает:

```c
Servo_SetAngle(90);
```

Это важное преимущество хорошей архитектуры.

---

# Драйвер Timer

Рассмотрим наш таймер.

На аппаратном уровне есть:

```text
TCCR0
TCNT0
TIMSK
ISR
```

Но остальная программа не должна думать об этих регистрах.

Она использует:

```c
Timer_Init();
Timer_GetTicks();
Timer_HasElapsed();
```

Например:

```c
stateStartTime = Timer_GetTicks();
```

А затем:

```c
if (Timer_HasElapsed(stateStartTime, FEEDER_WAIT_TICKS))
{
}
```

Модуль `Feeder` знает:

> Мне нужно проверить, прошло ли заданное время.

Но не знает:

```text
какой используется Timer;
какой prescaler;
когда происходит overflow;
как работает ISR;
как защищается uint32_t от разрыва чтения.
```

Это ответственность `Timer`.

---

# Драйвер TWI

На уровне регистров I2C выглядит сложно:

```c
TWCR = (1 << TWINT) |
       (1 << TWSTA) |
       (1 << TWEN);
```

Затем нужно ждать:

```c
while (!(TWCR & (1 << TWINT)))
{
}
```

После этого проверить статус.

Затем отправить адрес.

Затем данные.

Затем STOP.

Если всю эту логику писать прямо в драйвере DS3231, код RTC станет перегруженным.

Поэтому мы разделяем уровни.

Модуль `TWI` знает:

```text
как начать передачу;
как передать байт;
как получить байт;
как завершить передачу.
```

А модуль `DS3231` знает:

```text
адрес устройства;
адреса регистров;
формат времени;
BCD.
```

Получается:

```text
DS3231
   |
   v
TWI
   |
   v
TWBR / TWCR / TWDR / TWSR
```

Это хороший пример слоёв.

---

# Почему DS3231 и TWI — не одно и то же

На первый взгляд можно было бы написать всё в одном файле:

```text
ds3231.c
```

и внутри напрямую работать с:

```c
TWCR;
TWDR;
TWSR;
```

Но тогда DS3231 становится ответственным сразу за две вещи:

```text
1. Работа с I2C.
2. Работа с часами DS3231.
```

Это две разные ответственности.

TWI может использоваться не только с DS3231.

На той же шине могут находиться:

```text
EEPROM
датчик температуры
расширитель GPIO
дисплей
другой RTC
```

Если у нас уже есть универсальный драйвер TWI:

```c
TWI_Start();
TWI_Write();
TWI_ReadAck();
TWI_ReadNack();
TWI_Stop();
```

то каждый новый I2C-девайс может использовать его.

Схема:

```text
             +--> DS3231
             |
Application --> EEPROM I2C
             |
             +--> Sensor
                     |
                     v
                    TWI
                     |
                     v
               Регистры AVR
```

Это повторное использование кода.

---

# Драйвер DS3231

Теперь посмотрим на RTC.

Приложению нужно узнать время.

Плохой вариант:

```c
TWI_Start();
TWI_Write(0xD0);
TWI_Write(0x00);
TWI_Start();
TWI_Write(0xD1);

seconds = TWI_ReadAck();
minutes = TWI_ReadAck();
hours = TWI_ReadNack();

TWI_Stop();
```

Если такой код находится в `Scheduler`, Scheduler начинает знать слишком много.

Он знает:

```text
адрес DS3231;
адрес первого регистра;
формат чтения;
ACK и NACK;
порядок START;
BCD.
```

Но Scheduler должен заниматься расписанием.

Правильнее:

```c
RTC_GetTime(&hours, &minutes, &seconds);
```

Тогда:

```text
Scheduler
    знает текущее время.

DS3231
    знает, как получить текущее время.

TWI
    знает, как передать байты.

AVR
    выполняет операции с регистрами.
```

Каждый слой решает свою задачу.

---

# Драйвер EEPROM

Аналогично с EEPROM.

Приложению нужно сохранить настройку:

```text
Время кормления:
08:30
```

Оно не должно выполнять:

```c
while (EECR & (1 << EEWE))
{
}

EEAR = address;
EEDR = value;

EECR |= (1 << EEMWE);
EECR |= (1 << EEWE);
```

Приложение использует:

```c
EEPROM_UpdateByte(address, value);
```

А ещё лучше — более высокий уровень:

```c
Settings_SaveFeedingTime(hour, minute);
```

Тогда появляется ещё один слой:

```text
Application
    |
    v
Settings
    |
    v
EEPROM
    |
    v
EEAR / EEDR / EECR
```

`Settings` знает:

```text
по каким адресам хранятся настройки;
какие данные нужно сохранять.
```

`EEPROM` знает:

```text
как физически записать байт в память.
```

Это разные задачи.

---

# Драйвер LCD1602

У LCD1602 есть своя аппаратная сложность:

```text
RS
E
D4
D5
D6
D7
```

Данные передаются по 4 бита.

Сначала старшая половина байта:

```c
uint8_t highNibble = data >> 4;
```

Затем младшая:

```c
uint8_t lowNibble = data & 0x0F;
```

Нужно генерировать импульс Enable.

Нужно различать:

```text
команду
данные
```

Нужно учитывать адреса строк.

Но меню не должно знать всё это.

Меню хочет писать:

```c
LCD_SetCursor(0, 0);
LCD_Print("Settings");
```

Именно драйвер LCD превращает удобные действия в последовательность электрических операций.

---

# Уровни абстракции

В проекте можно представить несколько уровней.

Самый нижний:

```text
Регистры
```

Например:

```c
PORTB
OCR1A
TWCR
EECR
```

Выше:

```text
Драйвер периферии
```

Например:

```text
Timer
TWI
EEPROM
GPIO
```

Ещё выше:

```text
Драйвер конкретного устройства
```

Например:

```text
Servo
DS3231
LCD1602
```

Ещё выше:

```text
Логика приложения
```

Например:

```text
Feeder
Scheduler
Menu
Settings
```

И сверху:

```text
main.c
```

Схема:

```text
+-----------------------------+
|           main.c            |
+-----------------------------+
              |
              v
+-----------------------------+
|      Логика приложения      |
|                             |
| Feeder Scheduler Menu       |
+-----------------------------+
              |
              v
+-----------------------------+
|    Драйверы устройств       |
|                             |
| Servo DS3231 LCD1602        |
+-----------------------------+
              |
              v
+-----------------------------+
|   Драйверы периферии MCU    |
|                             |
| Timer TWI EEPROM GPIO       |
+-----------------------------+
              |
              v
+-----------------------------+
|          Регистры           |
|                             |
| OCR1A TWCR EECR PORTB       |
+-----------------------------+
              |
              v
+-----------------------------+
|          Железо             |
+-----------------------------+
```

Чем выше уровень, тем меньше он должен знать об аппаратных деталях.

---

# Что должен знать main.c

Хороший `main.c` должен быть простым.

Например:

```c
int main(void)
{
    Timer_Init();
    Servo_Init();
    TWI_Init();
    RTC_Init();
    LCD_Init();

    Feeder_Init();
    Scheduler_Init();

    sei();

    while (1)
    {
        Feeder_Update();
        Scheduler_Update();
    }
}
```

Он отвечает на вопросы:

```text
Что нужно инициализировать?

Какие модули нужно регулярно обновлять?
```

Он не должен содержать:

```c
TCCR1A |= ...
TWCR = ...
EECR |= ...
PORTD &= ...
```

Иначе `main.c` становится центром всех аппаратных знаний.

---

# Плохой main.c

Представим такой код:

```c
int main(void)
{
    DDRB |= (1 << PB1);

    TCCR1A |= (1 << WGM11);
    TCCR1A |= (1 << COM1A1);

    TCCR1B |= (1 << WGM13);
    TCCR1B |= (1 << WGM12);
    TCCR1B |= (1 << CS11);

    ICR1 = 2500;
    OCR1A = 125;

    TWBR = 2;
    TWCR = (1 << TWEN);

    DDRD &= ~(1 << PD2);
    PORTD |= (1 << PD2);

    while (1)
    {
        if (!(PIND & (1 << PD2)))
        {
            OCR1A = 250;
        }
    }
}
```

Код может работать.

Но `main.c` знает:

```text
как настроить Servo;
как настроить Timer1;
как настроить TWI;
как настроить кнопку;
какой OCR соответствует углу.
```

Проект становится связанным.

Любое изменение заставляет редактировать главный файл.

int main(void)

Но они не пропали из проекта.

# Инкапсуляция

Инкапсуляция означает, что модуль скрывает свои внутренние данные и управляет ими самостоятельно.

Например, внутри `feeder.c`:

```c
static FeederState feederState;
static uint32_t stateStartTime;
```

Другие модули не должны напрямую писать:

```c
feederState = FEEDER_IDLE;
```

Они вызывают:

```c
Feeder_Request();
```

А модуль сам решает:

```text
Можно ли принять запрос?

Нужно ли изменить состояние?

Нужно ли повернуть сервопривод?
```

То же самое с сервой.

Другие модули не должны писать:

```c
OCR1A = 188;
```

Они вызывают:

```c
Servo_SetAngle(90);
```

Драйвер сам управляет своим внутренним механизмом.

---

# Почему нельзя делать всё global

Плохой подход:

```c
uint16_t servoPulse;
uint8_t rtcHour;
uint8_t rtcMinute;
uint32_t systemTicks;
FeederState feederState;
```

Все переменные доступны всему проекту.

Любой модуль может изменить что угодно.

Например:

```c
servoPulse = 9999;
```

или:

```c
feederState = FEEDER_IDLE;
```

или:

```c
systemTicks = 0;
```

Такой код сложно контролировать.

Лучше скрыть данные внутри модулей:

```c
static uint32_t systemTicks;
```

```c
static FeederState feederState;
```

И выдавать доступ через функции:

```c
Timer_GetTicks();
Feeder_IsBusy();
```

Тогда модуль контролирует правила работы со своими данными.

---

# Должен ли каждый файл быть драйвером

Нет.

Это важно.

Не каждый модуль является драйвером.

Например:

```text
servo.c
```

можно считать драйвером устройства.

```text
twi.c
```

драйвером периферии.

Но:

```text
scheduler.c
```

не является драйвером железа.

Он содержит логику приложения.

То же самое:

```text
feeder.c
menu.c
settings.c
```

Это уже модули более высокого уровня.

То есть нужно различать:

```text
Драйвер:
    управляет периферией или устройством.

Модуль приложения:
    принимает решения и реализует поведение.
```

---

# Зависимости между модулями

Рассмотрим:

```text
Feeder
   |
   v
Servo
   |
   v
Timer1
```

Это допустимая зависимость.

`Feeder` использует `Servo`.

Но обратная зависимость была бы плохой:

```text
Servo
   |
   v
Feeder
```

Почему?

Потому что тогда низкоуровневый драйвер начинает знать о высокоуровневой бизнес-логике.

Servo должен быть универсальным.

Он должен уметь:

```c
Servo_SetAngle(0);
Servo_SetAngle(90);
Servo_SetAngle(180);
```

Ему всё равно, где он используется:

```text
в кормушке;
в роботе;
в манипуляторе;
в замке;
в камере.
```

Поэтому зависимости обычно должны идти сверху вниз:

```text
Application
    |
    v
Device Driver
    |
    v
Peripheral Driver
    |
    v
Hardware
```

Но не наоборот.

---

# Почему низкий уровень не должен знать высокий

Представим плохой код:

```c
void Servo_SetAngle(uint8_t angle)
{
    OCR1A = ConvertAngleToTicks(angle);

    if (angle == 180)
    {
        feederState = FEEDER_WAITING;
    }
}
```

Теперь драйвер Servo знает про кормушку.

Это плохо.

Что произойдёт, если ту же серву использовать для другого устройства?

Например:

```text
поворот камеры.
```

Почему поворот на 180 градусов должен менять состояние кормушки?

Драйвер теряет универсальность.

Правильно:

```text
Feeder решает:
    открыть заслонку.

Feeder вызывает:
    Servo_SetAngle(180).

Servo просто выполняет команду.
```

---

# Размер интерфейса

Хороший драйвер не обязан предоставлять десятки функций.

Чем проще интерфейс, тем легче пользоваться модулем.

Например:

```c
void Servo_Init(void);
void Servo_SetAngle(uint8_t angle);
```

Этого может быть достаточно.

Не обязательно писать:

```c
Servo_SetOCR();
Servo_SetPulse();
Servo_SetDuty();
Servo_SetCompareRegister();
Servo_EnableOutputCompare();
Servo_SetTimerMode();
```

Если приложение не должно управлять этими деталями напрямую, их лучше скрыть.

Интерфейс должен предоставлять только то, что действительно нужно внешнему коду.

---

# Но слишком высокий уровень тоже может быть проблемой

Представим функцию:

```c
Servo_OpenFeeder(void);
```

Для модуля Servo это слишком высокий уровень.

Почему?

Потому что сервопривод не знает, что такое кормушка.

Лучше:

```c
Servo_SetAngle(FEEDER_OPEN_ANGLE);
```

А ещё лучше, чтобы только модуль Feeder вообще знал про:

```c
FEEDER_OPEN_ANGLE
```

То есть:

```text
Servo
    знает углы.

Feeder
    знает, какой угол означает открытие кормушки.
```

Схема:

```c
#define FEEDER_OPEN_ANGLE 180
#define FEEDER_CLOSED_ANGLE 0
```

И затем:

```c
Servo_SetAngle(FEEDER_OPEN_ANGLE);
```

Так ответственности остаются разделёнными.

---

# Где должны находиться константы

Рассмотрим:

```c
#define SERVO_MIN_TICKS 125
#define SERVO_MAX_TICKS 250
```

Эти константы относятся к драйверу Servo.

Им место в:

```text
servo.c
```

или в его конфигурации.

А:

```c
#define FEEDER_OPEN_ANGLE 180
#define FEEDER_CLOSED_ANGLE 0
```

относятся к кормушке.

Им место в:

```text
feeder.c
```

Потому что Servo не должен знать:

```text
какой угол означает открытие конкретной заслонки.
```

Это уже логика приложения.

# Как определить, куда поместить код

Полезно задавать вопрос:

> О чём этот код знает?

Например:

```c
OCR1A = pulseTicks;
```

Он знает про аппаратный регистр Timer1.

Значит, это низкий уровень.

```c
Servo_SetAngle(180);
```

Он знает про сервопривод.

Это драйвер устройства.

```c
if (feedingTimeReached)
{
    Feeder_Request();
}
```

Он знает про расписание и кормление.

Это логика приложения.

Ещё один вопрос:

> Если я заменю железо, должен ли этот код измениться?

Если да, вероятно, это драйвер.

Например, при замене DS3231 может измениться:

```text
адрес;
карта регистров;
формат данных.
```

Но Scheduler не должен измениться.

Он всё ещё хочет получить:

```text
часы;
минуты;
секунды.
```

# Типичные ошибки

## Ошибка 1. Регистры используются по всему проекту

Плохо:

```text
main.c пишет в OCR1A
feeder.c пишет в OCR1A
menu.c пишет в OCR1A
scheduler.c пишет в OCR1A
```

Теперь непонятно:

> Кто реально управляет Servo?

Лучше:

```text
Все вызывают Servo_SetAngle()
```

А `OCR1A` изменяет только драйвер Servo.

---

## Ошибка 2. Драйвер знает о бизнес-логике

Плохо:

```c
void Servo_SetAngle(uint8_t angle)
{
    if (feedingTimeReached)
    {
        ...
    }
}
```

Servo не должен знать про расписание кормлений.

---

## Ошибка 3. Application знает аппаратные детали

Плохо:

```c
void Feeder_Request(void)
{
    OCR1A = 250;
}
```

Теперь Feeder привязан к конкретному таймеру.

Лучше:

```c
void Feeder_Request(void)
{
    Servo_SetAngle(FEEDER_OPEN_ANGLE);
}
```

---

## Ошибка 4. Один файл отвечает за всё

Например:

```text
main.c
```

содержит:

```text
GPIO
Timer
PWM
Servo
TWI
RTC
EEPROM
LCD
Menu
Scheduler
Feeder
```

Такой проект быстро становится трудно читать и изменять.

---

## Ошибка 5. Слишком много слоёв

Архитектуру тоже можно переусложнить.

Для включения светодиода не всегда нужно создавать:

```text
LedManager
LedService
LedController
LedRepository
LedFactory
LedProvider
```

Для маленького AVR-проекта это бессмысленно.

Иногда достаточно:

```c
LED_Init();
LED_On();
LED_Off();
```

Архитектура должна решать реальные проблемы, а не создавать новые.

---

## Ошибка 6. Интерфейс раскрывает внутреннюю реализацию

Плохо:

```c
Servo_SetOCR1A(188);
```

Теперь внешний код знает:

```text
какой регистр используется;
какие значения нужно писать.
```

Лучше:

```c
Servo_SetAngle(90);
```

## Ошибка 7. Магические числа

Плохо:

```c
Servo_SetAngle(180);

if (Timer_HasElapsed(start, 120))
{
    Servo_SetAngle(0);
}
```

Лучше:

```c
Servo_SetAngle(FEEDER_OPEN_ANGLE);

if (Timer_HasElapsed(start, FEEDER_WAIT_TICKS))
{
    Servo_SetAngle(FEEDER_CLOSED_ANGLE);
}
```

Названия объясняют смысл.

# Драйвер и Datasheet

Очень важно понимать:

драйвер не освобождает инженера от чтения Datasheet.

Наоборот.

Чтобы написать драйвер, нужно понять:

```text
какие регистры существуют;
какие биты нужно настроить;
какие временные ограничения есть;
какой порядок действий требует устройство;
какие ошибки могут возникнуть.
```

Например, чтобы написать драйвер EEPROM, мы читаем:

```text
Wait until EEWE becomes zero.
```

Чтобы написать TWI:

```text
TWINT
TWSTA
TWSTO
TWEN
```

Чтобы настроить PWM:

```text
WGM13
WGM12
WGM11
COM1A1
CS11
```

Но после того как эти знания превращены в драйвер, остальной проект не должен повторять их снова и снова.

Именно в этом смысл архитектуры.

Плохой подход:

```text
Скопировать код из интернета.
Положить в проект.
Не понимать регистры.
Назвать это драйвером.

Наш подход другой:

Проверить работу.
Спрятать детали за понятным интерфейсом.
```

Именно поэтому порядок обучения важен.

```text

PWM
UART
I2C
SPI

Servo
```

И только теперь говорим об архитектуре драйверов.

Иначе разговор об архитектуре был бы слишком абстрактным.

# Как инженер приходит к драйверам

Сначала инженер пишет:

```c
PORTB |= (1 << PB0);
```

Затем это повторяется несколько раз.

Он создаёт:

```c
void LED_On(void);
```

Потом появляется Servo.

Он пишет:

```c
OCR1A = 188;
```

Но понимает, что другим частям программы удобнее работать с углом.

Появляется:

```c
Servo_SetAngle(90);
```

Затем появляется DS3231.

Инженер видит, что работа с TWI повторяется.

Появляется отдельный модуль:

```text
TWI
```

А DS3231 использует его.

То есть драйверы появляются не ради красоты.

Они появляются, когда проекту становится нужна граница между:

```text
Что нужно сделать?
```

и:

```text
Как это сделать на конкретном железе?
```

# Практическое применение

Допустим, у нас есть датчик температуры.

Плохой код:

```c
ADMUX = ...
ADCSRA = ...

while (ADCSRA & (1 << ADSC))
{
}

uint16_t value = ADC;
```

Если этот код используется прямо в логике термостата, приложение зависит от AVR ADC.

Лучше:

```c
uint16_t ADC_Read(uint8_t channel);
```

Ещё выше:

```c
int16_t TemperatureSensor_GetCelsius(void);
```

Тогда:

```text
Thermostat
    |
    v
TemperatureSensor
    |
    v
ADC
    |
    v
Registers
```

Термостат принимает решения:

```text
если холодно:
    включить нагреватель.
```

Но не знает:

```text
какой ADC канал используется;
какое опорное напряжение;
сколько бит у ADC;
как пересчитать значение.
```

# Что должен уметь инженер

После этой главы инженер должен уметь:

* отличать драйвер от логики приложения;
* понимать, зачем скрывать регистры;
* разделять ответственность между модулями;
* создавать простой публичный интерфейс;
* использовать `.h` как контракт модуля;
* скрывать внутренние функции через `static`;
* не давать низкому уровню знать о высоком;
* строить зависимости сверху вниз;
* отличать драйвер периферии от драйвера устройства;
* понимать, где хранить константы;
* избегать глобальных переменных без необходимости;
* не переусложнять архитектуру;
* понимать, когда нужна абстракция;
* проектировать код так, чтобы замена железа затрагивала минимум модулей.

Главный вопрос инженера должен звучать так:

> Какую ответственность несёт этот модуль и что он действительно должен знать?

# Главное

Архитектура драйверов строится вокруг одной простой идеи:

```text
Высокий уровень говорит:
    Что нужно сделать?

Низкий уровень решает:
    Как это сделать на конкретном железе?
```

Приложение говорит:

```c
Servo_SetAngle(90);
```

Драйвер решает:

```text
какой Timer использовать;
какой PWM режим настроить;
какой prescaler выбрать;
сколько тиков записать в OCR1A.
```

Scheduler говорит:

```text
Получить текущее время.
```

DS3231 решает:

```text
какие регистры прочитать;
как выполнить TWI-транзакцию;
как преобразовать BCD.
```

Feeder говорит:

```text
Открыть заслонку.
```

Servo решает:

```text
какой импульс сформировать.
```

Хорошая архитектура не убирает сложность.

Она помещает каждую сложность туда, где ей место.

Вместо одного файла, который знает всё обо всём, мы получаем систему модулей:

```text
каждый знает только то,
что необходимо для его собственной работы.
```

И именно это позволяет проекту расти, не превращаясь в хаос.
