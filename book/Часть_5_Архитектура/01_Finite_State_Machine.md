# 01. Finite State Machine

## История

Представим простую задачу.

У нас есть автоматическая кормушка. Пользователь нажимает кнопку, после чего сервопривод должен открыть заслонку, немного подождать, чтобы корм успел высыпаться, а затем закрыть её обратно.

На первый взгляд решение кажется очевидным:

```c
Servo_SetAngle(180);
_delay_ms(1000);
Servo_SetAngle(0);
```

И действительно, это будет работать.

Но только до тех пор, пока наша программа не должна делать ничего другого.

Пока выполняется `_delay_ms()`, микроконтроллер буквально стоит на месте и ждёт. Он не проверяет кнопки, не обновляет дисплей, не следит за временем, не работает с меню и не выполняет другие задачи.

Для простого примера это допустимо.

Для настоящего устройства — уже нет.

Нам нужен другой подход.

Мы должны научить программу не ждать окончания действия, а **помнить, что она сейчас делает**.

Именно здесь появляется конечный автомат — **Finite State Machine**, или сокращённо **FSM**.

---

# Постановка задачи

Наша кормушка должна выполнять следующий сценарий:

```text
Поступил запрос на кормление
        |
        v
Открыть заслонку
        |
        v
Подождать некоторое время
        |
        v
Закрыть заслонку
```

Но при этом главный цикл программы должен продолжать работать:

```c
while (1)
{
    Button_Update();
    Feeder_Update();
    Scheduler_Update();
    LCD_Update();
}
```

Мы не хотим писать:

```c
while (1)
{
    if (Button_IsPressed())
    {
        Servo_SetAngle(180);

        _delay_ms(1000);

        Servo_SetAngle(0);
    }
}
```

Потому что во время задержки весь главный цикл остановится.

Значит, нам нужен механизм, который позволит программе сказать:

> Я уже открыла кормушку. Теперь я нахожусь в состоянии ожидания. Когда пройдёт нужное время, я продолжу выполнение следующего шага.

Это и есть задача FSM.

---

# Простое объяснение

FSM — это способ представить работу программы как набор состояний и переходов между ними.

Например, обычная лампа может находиться в двух состояниях:

```text
OFF
ON
```

При нажатии кнопки происходят переходы:

```text
OFF --нажатие--> ON

ON --нажатие--> OFF
```

Кормушка тоже может иметь состояния.

В нашей реализации их два:

```c
typedef enum
{
    FEEDER_IDLE,
    FEEDER_WAITING
} FeederState;
```

Первое состояние:

```text
FEEDER_IDLE
```

означает:

> Кормушка ничего не делает и готова принять новый запрос.

Второе:

```text
FEEDER_WAITING
```

означает:

> Заслонка уже открыта. Теперь нужно дождаться окончания заданного времени.

Схематично:

```text
        Feeder_Request()
              |
              v
+-------------------------+
|                         |
|      FEEDER_IDLE        |
|                         |
+-------------------------+
              |
              | открыть заслонку
              | запомнить время
              v
+-------------------------+
|                         |
|    FEEDER_WAITING       |
|                         |
+-------------------------+
              |
              | прошло нужное время
              | закрыть заслонку
              v
+-------------------------+
|                         |
|      FEEDER_IDLE        |
|                         |
+-------------------------+
```

Главная идея здесь очень простая:

**программа не ждёт внутри функции. Она запоминает своё текущее состояние и проверяет условия перехода при следующих проходах главного цикла.**

---

# Что происходит внутри микроконтроллера

Рассмотрим обычный главный цикл:

```c
while (1)
{
    Feeder_Update();
}
```

Микроконтроллер выполняет `Feeder_Update()`, возвращается в `while`, снова вызывает `Feeder_Update()`, затем снова и снова.

Это происходит очень быстро.

Допустим, сейчас кормушка находится в состоянии:

```text
FEEDER_IDLE
```

Тогда функция обновления практически ничего не делает:

```c
void Feeder_Update(void)
{
    if (feederState == FEEDER_WAITING)
    {
        // Проверка времени
    }
}
```

Пока кормушка находится в `FEEDER_IDLE`, условие ложно.

Функция сразу завершается.

Но в какой-то момент пользователь нажимает кнопку или Scheduler решает, что наступило время кормления.

Вызывается:

```c
Feeder_Request();
```

Внутри происходит несколько действий:

```text
1. Проверить текущее состояние.
2. Открыть заслонку.
3. Запомнить текущее время.
4. Изменить состояние на FEEDER_WAITING.
```

После этого функция завершается.

Главный цикл продолжает работать.

Но теперь при следующем вызове `Feeder_Update()` программа видит:

```text
feederState == FEEDER_WAITING
```

и начинает проверять:

```text
Прошло нужное время или ещё нет?
```

Если нет:

```text
ничего не делать
```

Если да:

```text
закрыть заслонку
вернуться в FEEDER_IDLE
```

Таким образом, ожидание в реальности происходит не внутри одной длинной функции.

Оно растягивается на множество проходов главного цикла.

---

# Состояние — это память программы

Рассмотрим переменную:

```c
static FeederState feederState;
```

Именно она позволяет программе помнить, что происходило раньше.

Без неё каждый новый вызов функции начинался бы как будто с чистого листа.

С FSM программа может рассуждать так:

```text
Я нахожусь в IDLE?
Тогда ничего не делаю.

Я нахожусь в WAITING?
Тогда проверяю время.
```

Можно представить это как память человека.

Допустим, мы поставили чайник.

Мы не стоим возле него три минуты абсолютно неподвижно.

Мы можем заняться чем-то другим, но при этом помним:

```text
Чайник сейчас нагревается.
```

Через некоторое время мы проверяем:

```text
Он уже закипел?
```

Если нет — продолжаем заниматься своими делами.

Если да — переходим к следующему действию.

FSM делает практически то же самое.

---

# Проектирование автомата

Прежде чем писать код, полезно ответить на несколько вопросов.

## Какие состояния существуют?

Для кормушки:

```text
FEEDER_IDLE
FEEDER_WAITING
```

## Что означает каждое состояние?

```text
FEEDER_IDLE
    Кормушка свободна.
    Заслонка закрыта.
    Можно принять новый запрос.

FEEDER_WAITING
    Заслонка открыта.
    Запущен отсчёт времени.
    Новый запрос не принимается.
```

## Какие события вызывают переходы?

Первый переход:

```text
FEEDER_IDLE
    |
    | Feeder_Request()
    v
FEEDER_WAITING
```

Второй:

```text
FEEDER_WAITING
    |
    | прошло нужное время
    v
FEEDER_IDLE
```

И только после этого имеет смысл писать код.

Это важный инженерный принцип.

Сначала:

```text
состояния
события
переходы
```

И только потом:

```text
enum
if
switch
функции
```

# Enum для хранения состояния

Для описания состояний удобно использовать `enum`:

```c
typedef enum
{
    FEEDER_IDLE,
    FEEDER_WAITING
} FeederState;
```

После этого создаём переменную:

```c
static FeederState feederState;
```

Теперь вместо непонятных чисел:

```c
if (feederState == 0)
```

мы можем писать:

```c
if (feederState == FEEDER_IDLE)
```

Это гораздо понятнее.

Сравним.

Плохой вариант:

```c
uint8_t state = 1;

if (state == 1)
{
}
```

Что означает `1`?

Без дополнительного контекста неизвестно.

Хороший вариант:

```c
FeederState state = FEEDER_WAITING;

if (state == FEEDER_WAITING)
{
}
```

Теперь смысл состояния виден прямо из кода.

# Инициализация автомата

При включении питания программа должна знать начальное состояние устройства.

В нашей кормушке логично начать с:

```text
FEEDER_IDLE
```

То есть кормушка свободна и готова к работе.

Инициализация может выглядеть так:

```c
void Feeder_Init(void)
{
    Servo_SetAngle(FEEDER_CLOSED_ANGLE);

    feederState = FEEDER_IDLE;
}
```

Здесь происходят две важные вещи.

Сначала мы физически устанавливаем устройство в известное состояние:

```c
Servo_SetAngle(FEEDER_CLOSED_ANGLE);
```

А затем синхронизируем с ним программное состояние:

```c
feederState = FEEDER_IDLE;
```

Это важно.

Программное состояние и реальное физическое состояние устройства должны соответствовать друг другу.

Нельзя допускать ситуацию:

```text
Программа думает:
FEEDER_IDLE

Физически:
заслонка открыта
```

Потому что тогда логика программы перестанет соответствовать реальному миру.

Для Embedded-разработчика это особенно важно.

Мы управляем не только переменными.

Мы управляем физическими устройствами.

---

# Запрос на кормление

Рассмотрим функцию:

```c
Feeder_Request();
```

Её задача — запустить процесс кормления.

Логика может выглядеть так:

```c
void Feeder_Request(void)
{
    if (feederState != FEEDER_IDLE)
    {
        return;
    }

    Servo_SetAngle(FEEDER_OPEN_ANGLE);

    stateStartTime = Timer_GetTicks();

    feederState = FEEDER_WAITING;
}
```

Разберём по шагам.

Сначала:

```c
if (feederState != FEEDER_IDLE)
{
    return;
}
```

Мы проверяем:

> Свободна ли кормушка сейчас?

Если она уже выполняет кормление, новый запрос игнорируется.

Это защищает автомат от неправильного перехода.

Мы разрешаем только:

```text
IDLE -> WAITING
```

Но не разрешаем:

```text
WAITING -> WAITING
```

Почему это важно?

Допустим, кормушка уже открылась.

Прошло 500 миллисекунд.

И вдруг снова поступает запрос.

Если мы повторно выполним:

```c
stateStartTime = Timer_GetTicks();
```

таймер ожидания начнётся заново.

Тогда заслонка останется открытой дольше, чем планировалось.

Поэтому состояние само защищает нашу логику.

---

# Запоминаем момент перехода

После открытия заслонки мы выполняем:

```c
stateStartTime = Timer_GetTicks();
```

Это означает:

> Запомнить время, когда мы вошли в состояние ожидания.

Допустим:

```text
Timer_GetTicks() = 1500
```

Тогда:

```text
stateStartTime = 1500
```

Главный цикл продолжает работать.

Через некоторое время:

```text
Timer_GetTicks() = 1550
```

Затем:

```text
1600
1650
1700
```

И программа может вычислять:

```text
Сколько времени прошло с момента входа в состояние?
```

То есть FSM часто хранит не только само состояние:

```c
feederState
```

но и данные, связанные с ним:

```c
stateStartTime
```

---

# Обновление автомата

Теперь рассмотрим функцию:

```c
Feeder_Update();
```

Она вызывается постоянно:

```c
while (1)
{
    Feeder_Update();
}
```

В простом варианте:

```c
void Feeder_Update(void)
{
    if (feederState == FEEDER_WAITING)
    {
        if (Timer_HasElapsed(stateStartTime, FEEDER_WAIT_TICKS))
        {
            Servo_SetAngle(FEEDER_CLOSED_ANGLE);

            feederState = FEEDER_IDLE;
        }
    }
}
```

Логика читается почти как обычный человеческий язык:

```text
Если кормушка находится в состоянии ожидания:

    проверить, прошло ли нужное время.

    Если прошло:

        закрыть кормушку;
        перейти в состояние IDLE.
```

Это и есть сила хорошо спроектированного FSM.

Код начинает описывать поведение устройства.

---

# Полная схема работы

Теперь соберём всю последовательность.

После включения:

```text
Feeder_Init()
        |
        v
Servo -> закрыто
        |
        v
FEEDER_IDLE
```

При запросе:

```text
Feeder_Request()
        |
        v
Проверить состояние
        |
        v
Открыть заслонку
        |
        v
Запомнить время
        |
        v
FEEDER_WAITING
```

Главный цикл:

```text
while (1)
    |
    v
Feeder_Update()
    |
    v
FEEDER_WAITING?
    |
    +---- Нет ---> выйти
    |
    +---- Да
           |
           v
    Время прошло?
           |
           +---- Нет ---> выйти
           |
           +---- Да
                  |
                  v
           Закрыть заслонку
                  |
                  v
              FEEDER_IDLE
```

Всё это время процессор не стоит на месте.

Он может выполнять другие задачи.

---

# Почему здесь нельзя использовать delay

Представим блокирующую реализацию:

```c
void Feeder_Request(void)
{
    Servo_SetAngle(180);

    _delay_ms(1000);

    Servo_SetAngle(0);
}
```

Во время `_delay_ms()` процессор не может полноценно выполнять главный цикл.

Например:

```text
Пользователь нажал кнопку
        |
        v
Кормушка открылась
        |
        v
_delay_ms(1000)
        |
        +--> кнопки не обрабатываются
        +--> меню не обновляется
        +--> Scheduler не работает
        +--> дисплей не обновляется
        +--> другие программные задачи стоят
```

С FSM:

```text
Кормушка открылась
        |
        v
Состояние = FEEDER_WAITING
        |
        v
Функция завершилась
        |
        v
Главный цикл продолжает работать
```

Поэтому FSM особенно важна в системах, где несколько задач должны выполняться одновременно.

Конечно, на одном ядре AVR они не обязательно выполняются физически одновременно.

Но программа быстро переключается между короткими задачами:

```text
Проверить кнопку
Обновить кормушку
Проверить расписание
Обновить интерфейс
Повторить
```

Для пользователя всё выглядит так, будто устройство делает всё сразу.

# FSM и switch

Когда состояний становится больше, удобно использовать `switch`.

Например:

```c
void Feeder_Update(void)
{
    switch (feederState)
    {
        case FEEDER_IDLE:
            break;

        case FEEDER_WAITING:
            if (Timer_HasElapsed(stateStartTime, FEEDER_WAIT_TICKS))
            {
                Servo_SetAngle(FEEDER_CLOSED_ANGLE);
                feederState = FEEDER_IDLE;
            }
            break;
    }
}
```

Для двух состояний обычный `if` ещё вполне читаем.

Но представим более сложное устройство:

```text
FEEDER_IDLE
FEEDER_OPENING
FEEDER_WAITING
FEEDER_CLOSING
FEEDER_ERROR
```

Тогда `switch` становится естественной структурой:

```c
switch (feederState)
{
    case FEEDER_IDLE:
        break;

    case FEEDER_OPENING:
        break;

    case FEEDER_WAITING:
        break;

    case FEEDER_CLOSING:
        break;

    case FEEDER_ERROR:
        break;
}
```

Каждый `case` описывает поведение одного состояния.

# Состояние и событие — не одно и то же

Это важный момент.

Состояние отвечает на вопрос:

> В каком режиме устройство находится сейчас?

Например:

```text
FEEDER_IDLE
FEEDER_WAITING
```

Событие отвечает на вопрос:

> Что произошло?

Например:

```text
Нажата кнопка.
Наступило время кормления.
Прошла одна секунда.
Получен байт по UART.
Произошла ошибка.
```

Например:

```text
Состояние:
FEEDER_IDLE

Событие:
Feeder_Request()

Результат:
Переход в FEEDER_WAITING
```

Или:

```text
Состояние:
FEEDER_WAITING

Событие:
Истекло заданное время

Результат:
Переход в FEEDER_IDLE
```

Событие может ничего не изменить.

Например:

```text
Состояние:
FEEDER_WAITING

Событие:
Новый Feeder_Request()

Результат:
Ничего не происходит
```

Потому что такой переход мы не разрешили.

---

# Не каждая переменная — это FSM

Важно не начать видеть конечный автомат в любой переменной.

Например:

```c
uint8_t temperature;
```

Это просто значение температуры.

Или:

```c
uint16_t adcValue;
```

Это просто результат ADC.

FSM появляется тогда, когда поведение системы зависит от её текущего режима.

Например:

```text
Кнопка отпущена.
Кнопка нажата.
Кнопка удерживается.
```

Или:

```text
Меню просмотра.
Меню редактирования часов.
Меню редактирования минут.
```

Или:

```text
Wi-Fi отключён.
Подключение.
Подключён.
Ошибка.
```

В каждом случае устройство ведёт себя по-разному в зависимости от текущего состояния.

---

# Почему FSM называется конечным автоматом

Слово `Finite` означает:

```text
конечный
```

То есть количество возможных состояний заранее ограничено.

Например:

```text
FEEDER_IDLE
FEEDER_WAITING
```

Всего два состояния.

Программа не может внезапно оказаться в состоянии:

```text
FEEDER_FLYING_TO_MOON
```

если такого состояния мы не предусмотрели.

Слово `State` означает:

```text
состояние
```

А `Machine` в данном контексте означает систему, которая:

```text
имеет состояния
получает события
выполняет переходы
```

Поэтому:

```text
Finite State Machine
```

можно понимать как:

> Система с конечным набором состояний и определёнными правилами перехода между ними.

---

# FSM в реальной жизни

Конечные автоматы встречаются практически везде.

## Светофор

```text
Красный
   |
   v
Красный + жёлтый
   |
   v
Зелёный
   |
   v
Жёлтый
   |
```

## UART-протокол

Представим, что устройство принимает пакет:

```text
START | COMMAND | DATA | CHECKSUM
```

Парсер может иметь состояния:

```text
WAIT_START
WAIT_COMMAND
WAIT_DATA
WAIT_CHECKSUM
```

FSM — это не отдельная технология только для кормушки.

Это один из основных способов организации поведения программы.

# Разбор архитектуры нашей кормушки

В нашей архитектуре можно условно выделить несколько уровней:

```text
main.c
   |
   v
Application
   |
   +--> Feeder
   +--> Scheduler
   |
   v
Drivers
   |
   +--> Servo
   +--> Timer
   +--> RTC
```

Модуль `Servo` не должен знать, зачем вращается сервопривод.

Он просто выполняет команду:

```c
Servo_SetAngle(180);
```

Модуль `Timer` не должен знать, что мы ждём закрытия кормушки.

Он просто отвечает:

```text
Сколько сейчас тиков?
```

или:

```text
Прошёл ли заданный интервал?
```

А модуль `Feeder` объединяет эти возможности в поведение:

```text
Открыть.
Подождать.
Закрыть.
```

И для организации этого поведения использует FSM.

Получается:

```text
Servo
    управляет железом

Timer
    предоставляет время

Feeder
    хранит состояние и принимает решения
```

Это и есть разделение ответственности.

# Почему состояние делается static

Внутри модуля может быть объявлено:

```c
static FeederState feederState;
```

Почему `static`?

Потому что состояние кормушки является внутренней деталью реализации модуля `feeder.c`.

Другим модулям не нужно напрямую писать:

```c
feederState = FEEDER_WAITING;
```

Иначе любой участок программы сможет сломать автомат.

Например:

```c
feederState = FEEDER_IDLE;
```

Но физически заслонка при этом останется открыта.

Поэтому лучше управлять автоматом через публичный интерфейс:

```c
Feeder_Init();
Feeder_Request();
Feeder_Update();
```

А внутренние данные скрыть:

```c
static FeederState feederState;
static uint32_t stateStartTime;
```

Так модуль сам контролирует правила переходов.

---

# Правильные переходы между состояниями

Хорошая FSM должна чётко определять допустимые переходы.

Для нашей кормушки:

```text
FEEDER_IDLE
    |
    | запрос
    v
FEEDER_WAITING
    |
    | время истекло
    v
FEEDER_IDLE
```

Нежелательные переходы:

```text
FEEDER_WAITING
    |
    | новый запрос
    v
FEEDER_WAITING
```

Поэтому мы проверяем состояние:

```c
if (feederState != FEEDER_IDLE)
{
    return;
}
```

Можно сказать, что FSM сама становится защитой архитектуры.

Она не просто хранит значение.

Она определяет:

```text
Что сейчас разрешено?
Что запрещено?
Что должно произойти дальше?
```

# Типичные ошибки

## Ошибка 1. FSM есть только на бумаге

Программист объявляет:

```c
typedef enum
{
    IDLE,
    WORKING
} State;
```

Но затем состояние почти нигде не используется, а логика всё равно строится на случайных флагах:

```c
bool started;
bool waiting;
bool ready;
bool finished;
```

Очень быстро появляются невозможные комбинации:

```text
started = false
waiting = true
finished = true
```

Что это вообще означает?

Хорошая FSM обычно имеет одно основное состояние:

```c
State currentState;
```

Именно оно определяет режим работы системы.

---

## Ошибка 2. Слишком много bool-переменных вместо состояний

Допустим:

```c
bool isOpening;
bool isWaiting;
bool isClosing;
bool hasError;
```

Получается множество возможных комбинаций.

Например:

```text
isOpening = true
isWaiting = true
isClosing = true
```

Может ли устройство одновременно открываться, ждать и закрываться?

Нет.

С `enum`:

```c
typedef enum
{
    FEEDER_OPENING,
    FEEDER_WAITING,
    FEEDER_CLOSING
} FeederState;
```

устройство может находиться только в одном состоянии одновременно.

---

## Ошибка 3. Состояние меняется из разных частей проекта

Например:

```text
main.c меняет feederState
Scheduler меняет feederState
Button меняет feederState
Feeder меняет feederState
```

В таком проекте становится сложно понять:

> Кто и почему перевёл устройство в это состояние?

Лучше:

```text
Button
    |
    v
Feeder_Request()

Scheduler
    |
    v
Feeder_Request()

Feeder
    |
    v
Сам управляет feederState
```

То есть внешний код отправляет запросы, но не изменяет внутреннее состояние напрямую.

---

## Ошибка 4. Блокирующее ожидание внутри состояния

Плохо:

```c
case FEEDER_WAITING:
    _delay_ms(1000);
    feederState = FEEDER_IDLE;
    break;
```

Формально `enum` есть.

Но главная проблема никуда не исчезла.

Процессор всё равно блокируется.

FSM должна проверять условия перехода и быстро возвращать управление главному циклу.

---

## Ошибка 5. Не определено начальное состояние

После запуска программы автомат должен находиться в известном состоянии.

Нельзя надеяться на случайность.

Нужно явно выполнять:

```c
feederState = FEEDER_IDLE;
```

И желательно приводить физическое устройство к соответствующему состоянию:

```c
Servo_SetAngle(FEEDER_CLOSED_ANGLE);
```

---

## Ошибка 6. Слишком много состояний

Иногда программист пытается превратить в состояние каждый маленький шаг:

```text
STATE_ENTER_FUNCTION
STATE_READ_TIMER
STATE_COMPARE_TIMER
STATE_CALL_SERVO
STATE_CHANGE_VARIABLE
```

Это бессмысленно.

Состояние должно отражать значимый режим работы устройства.

Например:

```text
IDLE
WAITING
ERROR
```

Хороший вопрос:

> Ведёт ли устройство себя принципиально по-разному в этих режимах?

Если да, возможно, это разные состояния.

---

# Практическое применение

FSM полезна там, где система имеет несколько режимов поведения.

Например:

```text
Автоматическая кормушка
Робот
Умный замок
Лифт
Термостат
Меню
Дисплей
Стиральная машина
Дрон
Сетевой протокол
UART-парсер
Wi-Fi подключение
Bluetooth-соединение
Загрузчик прошивки
```

Рассмотрим простой умный замок:

```text
LOCKED
UNLOCKING
UNLOCKED
LOCKING
ERROR
```

Или подключение к сети:

```text
DISCONNECTED
CONNECTING
CONNECTED
RECONNECTING
ERROR
```

Или меню:

```text
MAIN_SCREEN
SETTINGS
EDIT_HOUR
EDIT_MINUTE
SAVE
```

Везде идея одна:

```text
У системы есть текущее состояние.

Происходит событие.

FSM решает:

    остаться в текущем состоянии

или

    перейти в другое состояние.
```

# Как инженер приходит к FSM

Важно понять: FSM появляется не потому, что программист решил использовать красивый паттерн.

Она появляется из проблемы.

Сначала задача кажется простой:

```c
Open();
Delay();
Close();
```

Потом устройство получает новые функции:

```text
кнопка
дисплей
RTC
расписание
EEPROM
меню
UART
Wi-Fi
```

И внезапно становится понятно:

> Мы больше не можем останавливать всю программу ради одной операции.

Тогда появляется идея:

```text
Не ждать действие целиком.

Запустить его.

Запомнить состояние.

Вернуться в главный цикл.

Позже проверить, пора ли переходить дальше.
```

И только после этого возникает FSM.

Так инженер и должен мыслить:

```text
Не искать паттерн заранее.

Сначала понять проблему.

Затем выбрать структуру, которая эту проблему решает.
```

---

# Что должен уметь инженер

После изучения FSM инженер должен уметь:

* определить, есть ли в задаче несколько состояний;
* описать смысл каждого состояния словами;
* определить события, вызывающие переходы;
* нарисовать схему переходов до написания кода;
* представить состояния через `enum`;
* хранить текущее состояние;
* выполнять неблокирующее обновление автомата;
* не использовать `delay` для длинных последовательностей действий;
* отделять состояние от события;
* скрывать внутреннее состояние внутри модуля;
* запрещать недопустимые переходы;
* синхронизировать программное состояние с физическим состоянием устройства.

Главный навык здесь не в знании слова `FSM`.

Главный навык — способность посмотреть на поведение устройства и увидеть:

```text
В каком состоянии оно сейчас?

Что может произойти?

Куда оно должно перейти после этого?
```

# Практическое задание

Спроектируйте FSM для автоматической двери.

У двери есть следующие требования:

```text
Изначально дверь закрыта.

При нажатии кнопки:
    дверь начинает открываться.

После полного открытия:
    дверь остаётся открытой 5 секунд.

После этого:
    дверь начинает закрываться.

После полного закрытия:
    система возвращается в исходное состояние.
```

Попробуйте определить состояния самостоятельно.

Один из возможных вариантов:

```text
DOOR_CLOSED
DOOR_OPENING
DOOR_OPEN
DOOR_CLOSING
```

Нарисуйте переходы:

```text
DOOR_CLOSED
      |
      | нажатие кнопки
      v
DOOR_OPENING
      |
      | концевик открытия
      v
DOOR_OPEN
      |
      | прошло 5 секунд
      v
DOOR_CLOSING
      |
      | концевик закрытия
      v
DOOR_CLOSED
```

Затем подумайте:

```text
Что произойдёт, если кнопку нажать во время закрытия?

Что произойдёт при ошибке концевика?

Нужно ли отдельное состояние ERROR?

Кто должен иметь право менять состояние двери?
```

Именно с таких вопросов начинается проектирование настоящей системы.

# Главное

FSM — это не просто `enum` и не просто `switch`.

Это способ организовать поведение системы.

Мы перестаём писать:

```text
Сделай всё от начала до конца прямо сейчас.
```

И начинаем писать:

```text
Начни действие.
Запомни текущее состояние.
Верни управление главному циклу.
Позже проверь, пора ли двигаться дальше.
```

Именно благодаря этому наше устройство может одновременно:

```text
следить за кнопками,
проверять время,
управлять сервоприводом,
обновлять экран,
работать с меню,
выполнять расписание.
```

А кормушка при этом просто помнит:

```text
Я свободна.

или

Я уже открылась и сейчас жду.
```

С этого момента программа перестаёт быть последовательностью команд.

Она начинает описывать поведение устройства.

И именно здесь начинается настоящая архитектура Embedded-систем.
