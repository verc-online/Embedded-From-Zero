# 03. Архитектура проекта

## История

Когда мы только начинаем писать прошивку, почти всё помещается в `main.c`.

Например:

```c
int main(void)
{
    DDRB |= (1 << PB0);

    while (1)
    {
        PORTB ^= (1 << PB0);
        _delay_ms(500);
    }
}
```

Такой проект прост.

В нём легко понять:

```text
что происходит;
где происходит;
когда происходит.
```

Но затем проект начинает расти.

Появляется кнопка.

Потом таймер.

Потом сервопривод.

Потом RTC.

Потом EEPROM.

Потом LCD.

Потом меню.

Потом Scheduler.

И `main.c` начинает выглядеть примерно так:

```text
Настройка GPIO
Настройка Timer0
Настройка Timer1
Настройка PWM
Настройка TWI
Настройка RTC
Чтение EEPROM
Работа кнопок
Работа сервы
Проверка времени
Кормление
Вывод на дисплей
Меню
Сохранение настроек
```

Проект всё ещё может работать.

Но инженер постепенно теряет главное:

> Где находится ответственность за конкретное поведение?

Если сервопривод работает неправильно — куда смотреть?

Если кормушка открывается не вовремя — виноват Scheduler, RTC, Feeder или main?

Если меню показывает старое время — проблема в LCD, Menu, Settings или EEPROM?

Чем больше проект, тем важнее не просто написать работающий код, а организовать его так, чтобы было понятно:

```text
кто получает данные;
кто принимает решения;
кто управляет железом;
кто хранит состояние;
кто отвечает за время;
кто связывает всё вместе.
```

Именно это и есть архитектура проекта.

---

# Постановка задачи

Нам нужно было создать автоматическую кормушку.

Она должна:

```text
читать текущее время;
хранить расписание;
проверять момент кормления;
открывать заслонку;
ждать;
закрывать заслонку;
обрабатывать кнопку;
сохранять настройки;
выводить информацию на LCD.
```

Можно было бы написать всё в `main.c`.

Например:

```c
int main(void)
{
    while (1)
    {
        if (buttonPressed)
        {
            OCR1A = 250;
        }

        if (hour == 8 && minute == 30)
        {
            OCR1A = 250;
        }

        if (someTimeElapsed)
        {
            OCR1A = 125;
        }
    }
}
```

Но очень быстро возникли бы вопросы:

```text
Кто управляет сервой?

Кто хранит состояние кормушки?

Кто определяет, наступило ли время кормления?

Кто читает RTC?

Кто знает адреса EEPROM?

Кто отвечает за меню?

Кто должен вызывать кого?
```

Если на эти вопросы нет чётких ответов, проект постепенно превращается в набор связанных между собой переменных и условий.

Нам нужна архитектура.

---

# Простое объяснение

Архитектура проекта — это способ разделить систему на части и определить правила их взаимодействия.

Можно представить ресторан.

Есть:

```text
официант;
повар;
кладовщик;
кассир;
администратор.
```

Если официант сам начинает готовить еду, повар принимает оплату, а кладовщик отвечает на телефонные звонки, работа быстро превращается в хаос.

То же самое происходит в прошивке.

Если:

```text
Scheduler напрямую управляет OCR1A;

LCD читает EEPROM;

Servo изменяет feederState;

main.c знает регистры всех устройств;
```

то модули теряют границы ответственности.

Хорошая архитектура говорит:

```text
Ты отвечаешь за это.

Ты отвечаешь за это.

Ты можешь использовать вот этот интерфейс.

Но не должен знать внутренности другого модуля.
```

---

# Главный принцип

Архитектура должна отвечать минимум на четыре вопроса:

```text
1. Какие части есть в системе?

2. За что отвечает каждая часть?

3. Кто от кого зависит?

4. Как данные и команды проходят через систему?
```

В нашем проекте это можно представить так:

```text
+------------------------------+
|            main.c            |
+------------------------------+
               |
               v
+------------------------------+
|      Логика приложения       |
|                              |
| Feeder Scheduler Menu        |
| Settings                     |
+------------------------------+
               |
               v
+------------------------------+
|      Драйверы устройств      |
|                              |
| Servo DS3231 LCD1602         |
+------------------------------+
               |
               v
+------------------------------+
|    Драйверы периферии MCU    |
|                              |
| Timer TWI EEPROM GPIO        |
+------------------------------+
               |
               v
+------------------------------+
|           Регистры           |
+------------------------------+
               |
               v
+------------------------------+
|            Железо            |
+------------------------------+
```

Это не просто красивые уровни.

Каждый из них отвечает на свой вопрос.

---

# Уровень 1. Железо

В самом низу находится физический мир.

Например:

```text
сервопривод;
кнопка;
LCD1602;
DS3231;
EEPROM;
выводы микроконтроллера.
```

Железо ничего не знает о нашей программе.

Сервопривод не знает:

```text
что он открывает кормушку;
почему он должен повернуться;
какое сейчас время.
```

Он только реагирует на электрический сигнал.

DS3231 не знает:

```text
когда нужно кормить животное.
```

Он просто хранит время.

LCD не знает:

```text
что именно означает отображаемая строка.
```

Он просто показывает символы.

---

# Уровень 2. Регистры

Следующий уровень — регистры микроконтроллера.

Например:

```c
PORTB;
DDRB;
TCCR1A;
TCCR1B;
OCR1A;
TWCR;
TWDR;
EECR;
EEDR;
```

Это самый прямой программный доступ к железу.

Если мы пишем:

```c
PORTB |= (1 << PB0);
```

мы управляем физическим выводом.

Если пишем:

```c
OCR1A = 188;
```

мы изменяем параметр PWM.

Если пишем:

```c
TWCR = (1 << TWINT) | (1 << TWSTA) | (1 << TWEN);
```

мы запускаем операцию TWI.

Регистры дают полный контроль.

Но они слишком низкоуровневые для логики приложения.

---

# Уровень 3. Драйверы периферии

Драйверы периферии скрывают работу с регистрами.

Например:

```text
Timer
TWI
EEPROM
GPIO
```

Модуль `Timer` знает:

```text
как настроить Timer0;
как считать системные тики;
как читать uint32_t безопасно;
как проверить истечение интервала.
```

И предоставляет:

```c
Timer_Init();
Timer_GetTicks();
Timer_HasElapsed();
```

Модуль `TWI` знает:

```text
как сформировать START;
как отправить адрес;
как передать байт;
как принять ACK;
как сформировать STOP.
```

И предоставляет:

```c
TWI_Start();
TWI_Write();
TWI_ReadAck();
TWI_ReadNack();
TWI_Stop();
```

Остальная программа не должна повторять эту работу.

---

# Уровень 4. Драйверы устройств

Над периферией находятся драйверы конкретных устройств.

Например:

```text
Servo
DS3231
LCD1602
```

Они уже говорят на языке конкретного устройства.

Например:

```c
Servo_SetAngle(90);
```

вместо:

```c
OCR1A = 188;
```

Или:

```c
RTC_GetTime(&hour, &minute, &second);
```

вместо длинной TWI-последовательности.

Или:

```c
LCD_Print("Settings");
```

вместо ручной отправки полубайтов и импульсов Enable.

---

# Уровень 5. Логика приложения

Это самое важное отличие между драйвером и приложением.

Драйвер отвечает:

> Как выполнить действие?

Приложение отвечает:

> Зачем и когда его выполнять?

Например:

```text
Feeder
Scheduler
Menu
Settings
```

Модуль `Feeder` знает:

```text
когда кормушка свободна;
когда открыта;
когда нужно закрыться;
можно ли принять новый запрос.
```

Но не знает:

```text
как устроен PWM;
какой OCR используется;
какой prescaler выбран.
```

Модуль `Scheduler` знает:

```text
какое сейчас время;
когда запланировано кормление;
наступила ли нужная минута.
```

Но не знает:

```text
как поворачивается Servo;
какие значения записываются в OCR1A.
```

Модуль `Menu` знает:

```text
какой экран открыт;
какой пункт выбран;
редактируется ли значение.
```

Но не должен напрямую управлять портами LCD.

---

# Уровень 6. main.c

`main.c` связывает систему.

Его задача не в том, чтобы знать всё.

Его задача:

```text
инициализировать модули;
запустить главный цикл;
регулярно обновлять части системы.
```

Например:

```c
int main(void)
{
    Timer_Init();
    Button_Init();
    Servo_Init();
    TWI_Init();
    RTC_Init();
    EEPROM_Init();
    LCD_Init();

    Feeder_Init();
    Scheduler_Init();
    Menu_Init();

    sei();

    while (1)
    {
        Button_Update();
        Scheduler_Update();
        Feeder_Update();
        Menu_Update();
    }
}
```

Этот код хорошо читается.

Мы сразу понимаем структуру системы.

Но не видим аппаратных деталей.

И это хорошо.

---

# Что значит «main связывает систему»

Представим, что кнопка запускает кормление.

Можно написать:

```c
if (Button_WasPressed())
{
    Feeder_Request();
}
```

Здесь `main` связывает два независимых модуля:

```text
Button
    |
    v
main
    |
    v
Feeder
```

Кнопка не знает про кормушку.

Кормушка не знает про кнопку.

`main` решает:

```text
Если произошло это событие,
передай команду вот этому модулю.
```

Это очень важный принцип.

Низкоуровневые модули не должны неожиданно вызывать высокоуровневую логику без архитектурной причины.

---

# Поток команды

Рассмотрим обычное ручное кормление.

Пользователь нажимает кнопку.

Путь выглядит так:

```text
Физическая кнопка
       |
       v
GPIO / Button driver
       |
       v
Button_WasPressed()
       |
       v
main или Controller
       |
       v
Feeder_Request()
       |
       v
Feeder FSM
       |
       v
Servo_SetAngle()
       |
       v
Timer1 / OCR1A
       |
       v
Физический сервопривод
```

Каждый уровень выполняет свою часть.

Кнопка не знает про Servo.

Servo не знает про кнопку.

Feeder не знает про GPIO.

Именно поэтому части системы остаются независимыми.

---

# Поток автоматического кормления

Теперь рассмотрим кормление по расписанию.

```text
DS3231
    |
    v
RTC_GetTime()
    |
    v
Scheduler_Update()
    |
    v
Время совпало?
    |
    v
Feeder_Request()
    |
    v
Feeder FSM
    |
    v
Servo_SetAngle()
```

Здесь Scheduler принимает решение:

```text
Наступило время кормления.
```

Но сам не управляет железом.

Он вызывает Feeder.

Почему не Servo напрямую?

Потому что Scheduler должен просить:

```text
Выполнить кормление.
```

А не:

```text
Повернуть серву на 180 градусов.
```

Это разные уровни смысла.

---

# Почему Scheduler не должен вызывать Servo

Плохой вариант:

```c
if (hour == feedingHour && minute == feedingMinute)
{
    Servo_SetAngle(180);
}
```

Что здесь потеряно?

Scheduler теперь знает, что кормление означает:

```text
повернуть серву на 180 градусов.
```

Но завтра логика изменится.

Например:

```text
открыть заслонку;
подождать;
включить мотор;
проверить датчик;
закрыть заслонку.
```

Scheduler придётся менять.

Правильнее:

```c
if (feedingTimeReached)
{
    Feeder_Request();
}
```

Теперь Scheduler знает только:

```text
Нужно запустить кормление.
```

А Feeder сам решает, как оно выполняется.

---

# Архитектура через ответственность

Можно построить простую таблицу ответственности.

```text
Timer
    отвечает за системное время и интервалы.

Button
    отвечает за чтение и обработку кнопки.

Servo
    отвечает за управление углом.

TWI
    отвечает за обмен по I2C.

DS3231
    отвечает за чтение и запись времени RTC.

EEPROM
    отвечает за чтение и запись энергонезависимой памяти.

LCD1602
    отвечает за вывод символов.

Feeder
    отвечает за поведение кормушки.

Scheduler
    отвечает за расписание.

Menu
    отвечает за состояние интерфейса.

Settings
    отвечает за хранение настроек.

main
    связывает модули.
```

Если функция не соответствует ответственности модуля, вероятно, она находится не там.

---

# Как понять, куда поместить функцию

Представим функцию:

```c
void SaveFeedingTime(uint8_t hour, uint8_t minute);
```

Куда её поместить?

Можно спросить:

> О чём она знает?

Она знает:

```text
что существует настройка времени кормления;
какие данные нужно сохранить.
```

Это не просто EEPROM.

EEPROM умеет:

```c
EEPROM_WriteByte(address, value);
```

Но она не знает, что байт означает час кормления.

Значит:

```text
Settings
    знает смысл данных.

EEPROM
    знает способ хранения.
```

И архитектура может выглядеть так:

```text
Menu
   |
   v
Settings_SaveFeedingTime()
   |
   v
EEPROM_UpdateByte()
   |
   v
EECR / EEDR / EEAR
```

---

# Как понять, куда поместить константу

Рассмотрим:

```c
#define FEEDER_OPEN_ANGLE 180
```

Куда её поместить?

В `servo.c`?

Нет.

Servo не знает, что 180 градусов означает открытие кормушки.

Эта константа принадлежит `Feeder`.

Теперь:

```c
#define SERVO_MIN_TICKS 125
```

Куда?

Она относится к реализации Servo.

Значит:

```text
servo.c
```

или конфигурации Servo.

Главное правило:

> Константа должна находиться там, где живёт её смысл.

---

# Архитектура зависимостей

Очень полезно смотреть на направление зависимостей.

Хорошая схема:

```text
main
   |
   v
Application
   |
   v
Device Drivers
   |
   v
Peripheral Drivers
   |
   v
Registers
```

Зависимости идут сверху вниз.

Например:

```text
Feeder -> Servo
Servo -> Timer1
```

Это нормально.

Плохо:

```text
Timer -> Feeder
```

Почему?

Потому что низкоуровневый модуль времени начинает знать о конкретной бизнес-логике.

Timer должен оставаться универсальным.

---

# Что плохого в обратных зависимостях

Представим:

```c
ISR(TIMER0_OVF_vect)
{
    Feeder_Update();
}
```

На первый взгляд кажется удобно.

Но теперь Timer знает про Feeder.

Если завтра Timer понадобится в другом проекте, он уже связан с кормушкой.

Лучше:

```c
ISR(TIMER0_OVF_vect)
{
    systemTicks++;
}
```

А выше:

```c
while (1)
{
    Feeder_Update();
}
```

Timer предоставляет время.

Feeder использует время.

Это правильное направление зависимости.

---

# Связанность модулей

Есть понятие связности.

Чем больше один модуль знает о внутренностях другого, тем сильнее они связаны.

Например:

```c
feederState = FEEDER_WAITING;
OCR1A = 250;
systemTicks = 0;
```

Если один модуль напрямую изменяет чужие внутренние переменные, связность высокая.

Лучше:

```c
Feeder_Request();
Servo_SetAngle(180);
Timer_GetTicks();
```

Тогда взаимодействие идёт через интерфейсы.

Это снижает связанность.

---

# Сильная внутренняя связность и слабая внешняя

Хороший модуль должен иметь высокую внутреннюю связность.

Это означает:

> Всё внутри модуля связано одной задачей.

Например, `servo.c` содержит:

```text
инициализацию PWM для Servo;
преобразование угла;
запись OCR.
```

Всё относится к сервоприводу.

Плохо, если там же находятся:

```text
чтение RTC;
отрисовка меню;
работа кнопки.
```

Снаружи модуль должен быть слабо связан с другими.

Например:

```c
Servo_SetAngle(90);
```

Простой интерфейс.

Внешний код не знает деталей.

---

# Архитектура и FSM

FSM хорошо вписывается в архитектуру проекта.

Например, `Feeder` имеет собственное состояние:

```c
typedef enum
{
    FEEDER_IDLE,
    FEEDER_WAITING
} FeederState;
```

Это состояние принадлежит только `Feeder`.

Другие модули не должны делать:

```c
feederState = FEEDER_IDLE;
```

Они вызывают:

```c
Feeder_Request();
```

А `Feeder` сам контролирует переходы.

То же самое позже произойдёт с `Menu`.

Меню будет иметь собственное состояние:

```text
MAIN_SCREEN
SETTINGS
EDIT_HOUR
EDIT_MINUTE
```

Каждый модуль может иметь свою FSM.

Но они остаются независимыми.

---

# Архитектура и Scheduler

Scheduler отвечает за время выполнения задач.

Но важно не превращать его в центр всей программы.

Плохой Scheduler:

```text
проверяет время;
управляет Servo;
рисует LCD;
сохраняет EEPROM;
читает кнопки.
```

Хороший Scheduler:

```text
получает время;
проверяет расписание;
создаёт событие или запрос.
```

Например:

```c
if (Scheduler_ShouldFeed())
{
    Feeder_Request();
}
```

Или внутри самого Scheduler:

```c
Feeder_Request();
```

если такая зависимость осознанно выбрана.

Но он всё равно не должен напрямую писать в OCR или управлять LCD.

---

# Кто должен вызывать кого

Для каждого взаимодействия полезно спрашивать:

> Кто знает достаточно, чтобы принять это решение?

Например:

```text
Кто решает, когда кормить?
```

Scheduler.

```text
Кто знает, как выполнить кормление?
```

Feeder.

```text
Кто знает, как повернуть серву?
```

Servo.

```text
Кто знает, как создать PWM?
```

Timer1 и его регистры.

Получается цепочка:

```text
Scheduler
   |
   v
Feeder
   |
   v
Servo
   |
   v
Timer1
   |
   v
Hardware
```

Каждый уровень добавляет свой смысл.

---

# Почему main.c не должен быть умным

Иногда `main.c` превращают в гигантский контроллер:

```c
while (1)
{
    if (...)
    {
        ...
    }

    if (...)
    {
        ...
    }

    switch (...)
    {
        ...
    }

    if (...)
    {
        ...
    }
}
```

В итоге `main` знает всю логику.

Лучше, когда он выглядит как список обновлений:

```c
while (1)
{
    Input_Update();
    Scheduler_Update();
    Feeder_Update();
    Menu_Update();
}
```

Тогда логика распределена по соответствующим модулям.

`main` остаётся точкой сборки системы.

---

# Но слишком пустой main тоже не всегда цель

Не нужно стремиться к магии:

```c
int main(void)
{
    App_Run();
}
```

если `App_Run()` скрывает тысячу строк и ничего не объясняет.

Хорошая архитектура — не в минимальном количестве строк.

Она в ясности ответственности.

Иногда такой `main` вполне хорош:

```c
int main(void)
{
    App_Init();

    while (1)
    {
        App_Update();
    }
}
```

Но только если `App` действительно является осознанным верхним уровнем архитектуры.

---

# Инициализация проекта

Инициализация тоже должна иметь порядок.

Например:

```text
1. Настроить низкоуровневую периферию.
2. Настроить устройства.
3. Настроить логику приложения.
4. Разрешить прерывания.
5. Запустить главный цикл.
```

Схематично:

```c
int main(void)
{
    Timer_Init();
    TWI_Init();
    EEPROM_Init();

    Servo_Init();
    RTC_Init();
    LCD_Init();

    Feeder_Init();
    Scheduler_Init();
    Menu_Init();

    sei();

    while (1)
    {
        ...
    }
}
```

Почему порядок важен?

Потому что высокий уровень может зависеть от низкого.

Например:

```text
Feeder_Init()
    использует Servo.

Значит Servo должен быть готов раньше.
```

Или:

```text
Scheduler_Init()
    может читать RTC.

Значит TWI и RTC должны быть готовы.
```

# Жизненный цикл модуля

Очень полезный шаблон:

```text
Init
Update
Public actions
Getters
```

Например, Feeder:

```c
Feeder_Init();
Feeder_Update();
Feeder_Request();
Feeder_IsBusy();
```

Menu:

```c
Menu_Init();
Menu_Update();
Menu_OnButtonPressed();
```

Scheduler:

```c
Scheduler_Init();
Scheduler_Update();
```

Такой интерфейс хорошо показывает жизненный цикл модуля.

---

# Init

Функция `Init` приводит модуль в начальное состояние.

Например:

```c
void Feeder_Init(void)
{
    Servo_SetAngle(FEEDER_CLOSED_ANGLE);
    feederState = FEEDER_IDLE;
}
```

После `Init` модуль должен быть готов к работе.

---

# Update

`Update` выполняет неблокирующую работу модуля.

Например:

```c
void Feeder_Update(void)
{
    if (feederState == FEEDER_WAITING)
    {
        if (Timer_HasElapsed(stateStartTime, FEEDER_WAIT_TICKS))
        {
            Servo_SetAngle(FEEDER_CLOSED_ANGLE);
            feederState = FEEDER_IDLE;
        }
    }
}
```

Важно:

```text
Update должен быстро завершаться.
```

Он не должен блокировать весь проект длинным `delay`.

---

# Public actions

Это команды извне.

Например:

```c
Feeder_Request();
```

или:

```c
Servo_SetAngle(90);
```

или:

```c
Settings_Save();
```

Они выражают намерение.

---

# Getters

Иногда другим модулям нужно узнать состояние.

Например:

```c
bool Feeder_IsBusy(void);
```

Лучше так, чем выдавать наружу:

```c
extern FeederState feederState;
```

Getter позволяет сохранить контроль над внутренними данными.

---

# Данные принадлежат модулю

Это важный принцип.

Например:

```c
static FeederState feederState;
```

принадлежит `Feeder`.

```c
static uint32_t systemTicks;
```

принадлежит `Timer`.

```c
static MenuState menuState;
```

принадлежит `Menu`.

Другие модули не должны напрямую изменять эти данные.

Они используют интерфейс.

---

# Почему глобальные переменные опасны

Представим:

```c
uint32_t systemTicks;
FeederState feederState;
uint8_t hour;
uint8_t minute;
bool menuEditing;
```

Все доступны всему проекту.

Любой код может написать:

```c
systemTicks = 0;
```

или:

```c
feederState = FEEDER_IDLE;
```

или:

```c
hour = 99;
```

И найти источник ошибки будет сложно.

Если данные скрыты внутри модуля, количество мест, которые могут их изменить, резко уменьшается.

Это делает проект предсказуемее.

---

# Прямой доступ против интерфейса

Сравним.

Плохо:

```c
extern FeederState feederState;

if (feederState == FEEDER_IDLE)
{
}
```

Лучше:

```c
if (!Feeder_IsBusy())
{
}
```

Почему?

Потому что внешний код спрашивает смысл:

```text
Кормушка занята?
```

а не внутреннюю реализацию:

```text
Равно ли внутреннее поле конкретному enum?
```

Позже внутреннее устройство Feeder может измениться.

Интерфейс останется прежним.

# Архитектура и тестируемость

Даже в маленьком Embedded-проекте хорошая архитектура помогает тестировать систему.

Например, если `Feeder` зависит только от:

```text
Servo
Timer
```

мы можем отдельно проверить:

```text
при запросе серва открывается;
при повторном запросе ничего не происходит;
после времени серва закрывается.
```

Если вся логика смешана в `main.c`, тестировать отдельное поведение сложнее.

# Архитектура и замена железа

Представим, что мы меняем Servo.

Было:

```text
Servo через Timer1 PWM.
```

Стало:

```text
Servo через внешний PWM-контроллер по I2C.
```

При хорошей архитектуре меняется:

```text
servo.c
```

А Feeder продолжает вызывать:

```c
Servo_SetAngle(FEEDER_OPEN_ANGLE);
```

То же самое с RTC.

Было:

```text
DS3231
```

Стало:

```text
другой RTC
```

Scheduler всё равно хочет получить:

```text
hour
minute
second
```

Если интерфейс спроектирован правильно, верхний уровень почти не меняется.

Потом:

Это важный принцип.

Архитектура должна соответствовать размеру задачи.

# Команда и данные

Важно различать два типа взаимодействия.

Команда:

```c
Feeder_Request();
```

Она говорит:

> Сделай действие.

Данные:

```c
RTC_GetTime(&hour, &minute, &second);
```

Они отвечают:

> Вот текущее значение.

Иногда архитектура становится яснее, если разделять:

```text
кто отдаёт команды;
кто предоставляет данные.
```

# Кто владеет временем

В нашем проекте есть несколько представлений времени.

Например:

```text
системные тики Timer;
реальное время DS3231;
расписание кормления.
```

Это разные сущности.

`Timer` отвечает:

```text
сколько прошло времени.
```

`DS3231` отвечает:

```text
который сейчас час.
```

`Scheduler` отвечает:

```text
пора ли выполнять задачу.
```

Не нужно смешивать их в один модуль.

# Ошибка: один модуль знает слишком много

Плохо:

```text
Scheduler:
    читает DS3231;
    управляет Servo;
    пишет в LCD;
    сохраняет EEPROM;
    читает кнопки.
```

Такой модуль становится центром системы.

Любое изменение затрагивает его.

Лучше разделить:

```text
Scheduler
    решает, когда.

Feeder
    решает, как кормить.

Servo
    управляет приводом.

Menu
    управляет интерфейсом.

Settings
    хранит настройки.
```

---

# Ошибка: слишком много маленьких модулей

Можно зайти слишком далеко.

Например:

```text
HourComparator
MinuteComparator
FeedingTimeChecker
ScheduleMatchService
FeedingDecisionManager
```

для простой проверки:

```c
if (hour == feedingHour && minute == feedingMinute)
{
}
```

Это переусложнение.

Модуль нужен, когда у него есть самостоятельная ответственность.

---

# Ошибка: циклические зависимости

Очень опасная ситуация:

```text
Feeder включает Scheduler
Scheduler вызывает Feeder
```

или:

```text
Menu вызывает Settings
Settings вызывает Menu
```

Возникает цикл.

Это усложняет понимание и компиляцию.

Лучше определить направление:

```text
Menu -> Settings
```

Но:

```text
Settings -X-> Menu
```

Settings не должен знать о пользовательском интерфейсе.

---

# Ошибка: include всех файлов везде

Плохо:

```c
#include "timer.h"
#include "servo.h"
#include "twi.h"
#include "rtc.h"
#include "lcd.h"
#include "eeprom.h"
#include "feeder.h"
#include "scheduler.h"
#include "menu.h"
```

в каждом модуле.

Файл должен подключать только то, что реально использует.

Например, `feeder.c`:

```c
#include "feeder.h"
#include "servo.h"
#include "timer.h"
```

И всё.

Это помогает видеть зависимости.

---

# Ошибка: публично выставлять всё подряд

Плохой `feeder.h`:

```c
extern FeederState feederState;
extern uint32_t stateStartTime;
extern uint8_t openAngle;
extern uint8_t closeAngle;
```

Теперь внутренности модуля открыты всему проекту.

Лучше:

```c
void Feeder_Init(void);
void Feeder_Request(void);
void Feeder_Update(void);
bool Feeder_IsBusy(void);
```

Остальное скрыто.

---

# Ошибка: слишком умный драйвер

Например:

```c
void Servo_SetAngle(uint8_t angle)
{
    if (RTC_GetHour() == 8)
    {
        ...
    }
}
```

Servo не должен знать время.

Или:

```c
void LCD_Print(const char* text)
{
    if (Feeder_IsBusy())
    {
        ...
    }
}
```

LCD не должен знать состояние кормушки.

Драйвер должен оставаться узким.

---

# Ошибка: логика в ISR

Прерывание должно быть коротким.

Плохо:

```c
ISR(TIMER0_OVF_vect)
{
    RTC_GetTime(...);
    Scheduler_Update();
    Feeder_Update();
    LCD_Print("...");
}
```

Это слишком много логики внутри ISR.

Лучше:

```c
ISR(TIMER0_OVF_vect)
{
    systemTicks++;
}
```

А вся основная логика выполняется в главном цикле.

---

# Архитектура и неблокирующий код

Наша архитектура хорошо работает только тогда, когда модули быстро возвращают управление.

Например:

```c
while (1)
{
    Button_Update();
    Scheduler_Update();
    Feeder_Update();
    Menu_Update();
}
```

Если `Menu_Update()` зависнет на секунду, все остальные модули тоже перестанут обновляться.

Поэтому важное правило:

```text
Update должен быть коротким и неблокирующим.
```

# Главный цикл как кооперативная система

Можно представить главный цикл так:

```text
Button получает немного процессорного времени.
Scheduler получает немного процессорного времени.
Feeder получает немного процессорного времени.
Menu получает немного процессорного времени.
```

Затем всё повторяется.

```text
Button
  |
  v
Scheduler
  |
  v
Feeder
  |
  v
Menu
  |
  +------> снова Button
```

Каждый модуль добровольно возвращает управление.

Поэтому такую архитектуру можно воспринимать как простую кооперативную модель выполнения.

---

# Что происходит, если один модуль блокируется

Допустим:

```c
void Feeder_Update(void)
{
    _delay_ms(1000);
}
```

Тогда:

```text
Button не обновляется.
Scheduler не обновляется.
Menu не обновляется.
LCD может не обновляться.
```

Один модуль остановил всю систему.

Поэтому FSM и неблокирующие таймеры так важны для архитектуры.

# Где находится бизнес-логика

В Embedded иногда термин «бизнес-логика» звучит странно.

Но смысл простой:

```text
правила поведения устройства.
```

Например:

```text
если наступило 08:30 — покормить;
если кормушка занята — игнорировать новый запрос;
если пользователь изменил время — сохранить настройку.
```

Это не драйвер.

Это логика приложения.

# Как инженер проектирует архитектуру

Хороший порядок:

```text
1. Описать поведение устройства словами.

2. Выделить отдельные ответственности.

3. Определить данные каждого модуля.

4. Определить публичный интерфейс.

5. Определить зависимости.

6. Только потом писать код.
```

Например:

```text
Нужно кормить по расписанию.
```

Выделяем:

```text
RTC
Scheduler
Feeder
Servo
Timer
```

Затем спрашиваем:

```text
Кто знает текущее время?
RTC.

Кто знает расписание?
Scheduler.

Кто выполняет кормление?
Feeder.

Кто управляет углом?
Servo.

Кто даёт интервалы?
Timer.
```

Архитектура начинает появляться сама.

# Как понять, что архитектура хорошая

Нет универсальной формулы.

Но есть полезные признаки.

Хорошая архитектура позволяет быстро ответить:

```text
Где находится логика кормления?

Где меняется угол сервы?

Где читается RTC?

Где сохраняются настройки?

Где хранится состояние меню?

Кто отвечает за системные тики?
```

Если ответы ясны — это хороший знак.

Если ответ:

```text
Ну, понемногу везде.
```

# Архитектура не равна папкам

Можно создать идеальную структуру:

```text
drivers/
services/
managers/
controllers/
core/
domain/
application/
```

Но если внутри всё связано со всем, архитектура плохая.

И наоборот.

Можно иметь всего несколько файлов, но чётко разделить ответственность.

Архитектура — это не названия папок.

Это правила взаимодействия.

---

# Архитектура не должна скрывать понимание

Очень важно для обучения.

Мы сначала изучаем:

```text
регистры;
биты;
протоколы;
таймеры;
PWM;
TWI;
EEPROM.
```

И только потом скрываем их за драйверами.

Если сразу написать:

```c
Servo_SetAngle(90);
```

не понимая `OCR1A`, архитектура превращается в магию.

Наш подход другой:

```text
Сначала понять низкий уровень.

Потом создать абстракцию.

Потом использовать её.
```

Это и есть инженерный путь.

# Архитектура не высечена в камне

Проект развивается.

Сначала может быть:

```text
main
Timer
Servo
Feeder
```

Потом появится:

```text
Scheduler
RTC
EEPROM
LCD
Menu
Settings
```

В какой-то момент может понадобиться рефакторинг.

Это нормально.

Плохая архитектура — не та, которую пришлось изменить.

Плохая архитектура — та, которую боятся менять, потому что всё связано со всем.

# Практическое применение

Представим умную теплицу.

Есть:

```text
датчик температуры;
датчик влажности;
насос;
вентилятор;
LCD;
RTC;
кнопки;
EEPROM.
```

Можно построить архитектуру:

```text
main
   |
   +--> ClimateController
   +--> WateringScheduler
   +--> Menu
   |
   +--> TemperatureSensor
   +--> HumiditySensor
   +--> Pump
   +--> Fan
   +--> LCD
   +--> RTC
   |
   +--> ADC
   +--> TWI
   +--> GPIO
   +--> Timer
```

Ответственность:

```text
ClimateController
    решает, когда включать вентилятор.

TemperatureSensor
    предоставляет температуру.

ADC
    получает цифровое значение.

Fan
    управляет выводом.

Menu
    редактирует настройки.

Settings
    сохраняет их в EEPROM.
```

Такой подход масштабируется.

# Что должен уметь инженер

После этой главы инженер должен уметь:

* смотреть на проект как на систему модулей;
* выделять ответственность;
* разделять железо, драйверы и логику приложения;
* понимать направление зависимостей;
* не смешивать высокоуровневую логику с регистрами;
* определять владельца данных;
* скрывать внутреннее состояние;
* проектировать публичные интерфейсы;
* понимать поток команд и данных;
* не создавать циклические зависимости;
* не перегружать `main.c`;
* не перегружать отдельные модули;
* избегать блокирующих `Update`;
* понимать роль главного цикла;
* проектировать архитектуру до написания большого количества кода;
* не переусложнять маленькие задачи.

Главный вопрос:

> Кто должен знать об этом и кто должен принимать это решение?

# Практическое задание

Спроектируйте архитектуру электронного замка.

Есть:

```text
клавиатура;
LCD;
электромагнитный замок;
EEPROM;
таймер;
зуммер.
```

Поведение:

```text
Пользователь вводит PIN.

Если PIN верный:
    открыть замок на 5 секунд.

Если неверный:
    показать ошибку.

После трёх ошибок:
    заблокировать ввод на 30 секунд.

PIN должен сохраняться в EEPROM.
```

Попробуйте выделить модули.

Например:

```text
Keypad
LCD
Lock
Buzzer
EEPROM
Timer
Auth
Security
Menu
Settings
```

Теперь ответьте:

```text
Кто знает правильный PIN?

Кто проверяет введённый PIN?

Кто считает количество ошибок?

Кто решает блокировать ввод?

Кто управляет физическим замком?

Кто хранит PIN в памяти?

Должен ли EEPROM знать, что хранит PIN?

Должен ли Lock знать, почему его открывают?
```

Из ответов начнёт формироваться архитектура.

# Главное

Архитектура проекта начинается не с папок.

Она начинается с вопросов:

```text
Кто за что отвечает?

Кто чем владеет?

Кто кого вызывает?

Кто принимает решение?

Кто управляет железом?
```

Хорошая система выглядит не так:

```text
Все знают обо всём.
```

А так:

```text
Timer знает время.

Servo знает угол.

RTC знает текущее время.

Scheduler знает расписание.

Feeder знает поведение кормушки.

Menu знает состояние интерфейса.

main связывает всё вместе.
```

Когда пользователь нажимает кнопку, команда проходит через систему:

```text
Button
   |
   v
Feeder
   |
   v
Servo
   |
   v
Timer1
   |
   v
Hardware
```

Когда приходит время автоматического кормления:

```text
DS3231
   |
   v
Scheduler
   |
   v
Feeder
   |
   v
Servo
```

Каждый модуль знает только то, что действительно должен знать.

Именно это позволяет проекту расти без хаоса.

Хорошая архитектура не убирает сложность.

Она распределяет её по правильным местам.

И если инженер может открыть проект и быстро понять:

```text
где находится поведение;
где находится железо;
где принимаются решения;
где хранятся данные;
```

значит архитектура уже выполняет свою главную задачу.
