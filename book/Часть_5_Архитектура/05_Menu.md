# 05. Menu

## История

Пока устройство умеет только включать светодиод или открывать заслонку, пользовательский интерфейс может быть очень простым.

Например:

```text
Нажал кнопку
    |
    v
Произошло действие
```

Но затем в проекте появляется LCD1602.

Мы хотим показывать:

```text
текущее время;
следующее кормление;
состояние кормушки;
настройки;
редактирование часов;
редактирование минут.
```

Появляются кнопки:

```text
Вверх
Вниз
OK
Назад
```

И очень быстро код может превратиться в такое:

```c
if (buttonUp)
{
    if (screen == 0)
    {
        ...
    }
    else if (screen == 1)
    {
        ...
    }
    else if (screen == 2)
    {
        ...
    }
}

if (buttonDown)
{
    ...
}

if (buttonOk)
{
    ...
}
```

Чем больше экранов, тем больше условий.

Потом появляется редактирование.

Теперь одной переменной `screen` недостаточно.

Нужно знать:

```text
какой экран открыт;
какой пункт выбран;
редактируются ли часы;
редактируются ли минуты;
изменено ли значение;
нужно ли сохранить его;
нужно ли вернуться назад.
```

Меню начинает становиться отдельной системой поведения.

А значит, к нему естественно применяется FSM.

---

# Постановка задачи

Представим меню нашей кормушки.

На главном экране мы показываем:

```text
12:45
Next: 19:00
```

Пользователь нажимает `OK`.

Открывается меню:

```text
> Feeding time
  Set clock
```

Он выбирает:

```text
Feeding time
```

Нажимает `OK`.

Появляется:

```text
Hour: 08
Minute: 30
```

Потом он редактирует час.

Затем минуты.

После этого сохраняет настройки.

Нам нужно организовать всю эту логику так, чтобы программа понимала:

```text
Где сейчас находится пользователь?

Какие кнопки сейчас допустимы?

Что делает кнопка OK именно в этом состоянии?

Что рисовать на LCD?

Какие данные можно изменять?
```

Это задача Menu.

---

# Простое объяснение

Меню можно представить как набор комнат.

Пользователь находится только в одной комнате одновременно.

Например:

```text
MAIN_SCREEN
SETTINGS_MENU
EDIT_FEEDING_HOUR
EDIT_FEEDING_MINUTE
```

Кнопка переводит его из одной комнаты в другую.

Например:

```text
MAIN_SCREEN
    |
    | OK
    v
SETTINGS_MENU
```

Затем:

```text
SETTINGS_MENU
    |
    | выбран Feeding Time + OK
    v
EDIT_FEEDING_HOUR
```

После подтверждения:

```text
EDIT_FEEDING_HOUR
    |
    | OK
    v
EDIT_FEEDING_MINUTE
```

И после сохранения:

```text
EDIT_FEEDING_MINUTE
    |
    | OK
    v
SETTINGS_MENU
```

Это уже знакомая нам FSM.

---

# Menu как FSM

Можно объявить:

```c
typedef enum
{
    MENU_MAIN_SCREEN,
    MENU_SETTINGS,
    MENU_EDIT_FEEDING_HOUR,
    MENU_EDIT_FEEDING_MINUTE
} MenuState;
```

И хранить текущее состояние:

```c
static MenuState menuState;
```

Теперь программа всегда знает:

```text
Где находится пользователь прямо сейчас?
```

Например:

```c
menuState == MENU_MAIN_SCREEN
```

означает:

> Показываем основной экран.

А:

```c
menuState == MENU_EDIT_FEEDING_HOUR
```

означает:

> Пользователь сейчас изменяет час кормления.

---

# Состояние определяет поведение кнопок

Одна и та же кнопка может делать разные вещи.

Например, кнопка `UP`.

На главном экране:

```text
ничего
```

В списке меню:

```text
перейти на предыдущий пункт
```

При редактировании часа:

```text
увеличить час
```

При редактировании минуты:

```text
увеличить минуту
```

То есть нельзя написать просто:

```c
if (Button_UpPressed())
{
    value++;
}
```

Нужно сначала понять состояние:

```c
switch (menuState)
{
    case MENU_MAIN_SCREEN:
        break;

    case MENU_SETTINGS:
        Menu_SelectPreviousItem();
        break;

    case MENU_EDIT_FEEDING_HOUR:
        editedHour++;
        break;

    case MENU_EDIT_FEEDING_MINUTE:
        editedMinute++;
        break;
}
```

Состояние определяет смысл события.

---

# Событие и состояние

Как и в любой FSM, важно различать:

```text
Состояние:
    MENU_EDIT_FEEDING_HOUR

Событие:
    нажата кнопка UP
```

Результат:

```text
увеличить час
```

Другой пример:

```text
Состояние:
    MENU_EDIT_FEEDING_HOUR

Событие:
    нажата кнопка OK
```

Результат:

```text
перейти к редактированию минут
```

Одно и то же состояние по-разному реагирует на разные события.

---

# Схема меню

Простейшая структура может выглядеть так:

```text
+----------------------+
|   MENU_MAIN_SCREEN   |
+----------------------+
           |
           | OK
           v
+----------------------+
|    MENU_SETTINGS     |
+----------------------+
           |
           | выбран Feeding Time
           | OK
           v
+--------------------------+
| MENU_EDIT_FEEDING_HOUR   |
+--------------------------+
           |
           | OK
           v
+----------------------------+
| MENU_EDIT_FEEDING_MINUTE   |
+----------------------------+
           |
           | OK
           v
+----------------------+
|    MENU_SETTINGS     |
+----------------------+
```

Кнопка `BACK` может возвращать назад:

```text
EDIT_FEEDING_MINUTE -> EDIT_FEEDING_HOUR
EDIT_FEEDING_HOUR   -> SETTINGS
SETTINGS            -> MAIN_SCREEN
```

---

# Почему Menu не должен знать про регистры LCD

Плохо:

```c
PORTD |= (1 << LCD_RS_PIN);
PORTD &= ~(1 << LCD_E_PIN);
```

внутри логики меню.

Menu должен говорить:

```c
LCD_Clear();
LCD_SetCursor(0, 0);
LCD_Print("Settings");
```

Почему?

Потому что Menu отвечает за:

```text
что показать;
когда показать;
какой экран активен.
```

LCD отвечает за:

```text
как физически отправить символы на дисплей.
```

Это разные уровни.

---

# Menu и LCD

Связь выглядит так:

```text
Menu
   |
   v
LCD1602
   |
   v
GPIO
   |
   v
Физический дисплей
```

Menu говорит:

```text
Покажи строку "Settings".
```

LCD решает:

```text
как разбить байт на два полубайта;
как установить RS;
как создать импульс Enable;
как выбрать строку.
```

---

# Menu и Button

Аналогично:

```text
Физическая кнопка
       |
       v
Button driver
       |
       v
Button_WasPressed()
       |
       v
Menu
```

Menu не должен читать:

```c
PIND & (1 << PD2)
```

Он должен получать событие:

```c
Button_WasPressed(BUTTON_OK)
```

или, в более простой реализации:

```c
Button_OK_WasPressed();
```

Драйвер Button отвечает за:

```text
чтение GPIO;
pull-up;
антидребезг;
определение нажатия.
```

Menu отвечает за смысл нажатия.

---

# Почему важен фронт нажатия

Допустим, пользователь удерживает кнопку `UP`.

Если мы постоянно проверяем:

```c
if (Button_IsPressed())
{
    editedHour++;
}
```

главный цикл может выполнить это тысячи раз.

Получим:

```text
08
09
10
11
12
13
...
```

за доли секунды.

Поэтому обычно Menu реагирует не просто на состояние:

```text
кнопка нажата
```

а на событие:

```text
кнопка только что была нажата
```

То есть на фронт.

Например:

```text
previous = false
current  = true
```

Именно переход:

```text
0 -> 1
```

означает новое нажатие.

---

# Обработка кнопок

Можно представить событие отдельным enum:

```c
typedef enum
{
    MENU_EVENT_NONE,
    MENU_EVENT_UP,
    MENU_EVENT_DOWN,
    MENU_EVENT_OK,
    MENU_EVENT_BACK
} MenuEvent;
```

Тогда Menu может получать:

```c
Menu_HandleEvent(MENU_EVENT_UP);
```

Или:

```c
Menu_HandleEvent(MENU_EVENT_OK);
```

Это хороший архитектурный подход.

Menu больше не знает, какая именно физическая кнопка или GPIO создали событие.

---

# Почему это полезно

Сегодня управление может быть через кнопки.

Завтра:

```text
энкодер;
UART;
Bluetooth;
сенсорный экран.
```

Но Menu всё равно может получать:

```text
UP
DOWN
OK
BACK
```

То есть интерфейс меню становится независимее от физического ввода.

---

# Простейшая обработка события

Например:

```c
void Menu_HandleEvent(MenuEvent event)
{
    switch (menuState)
    {
        case MENU_MAIN_SCREEN:
            Menu_HandleMainScreen(event);
            break;

        case MENU_SETTINGS:
            Menu_HandleSettings(event);
            break;

        case MENU_EDIT_FEEDING_HOUR:
            Menu_HandleEditHour(event);
            break;

        case MENU_EDIT_FEEDING_MINUTE:
            Menu_HandleEditMinute(event);
            break;
    }
}
```

Теперь каждая функция отвечает только за одно состояние.

---

# Обработка главного экрана

Например:

```c
static void Menu_HandleMainScreen(MenuEvent event)
{
    if (event == MENU_EVENT_OK)
    {
        menuState = MENU_SETTINGS;
        Menu_RequestRedraw();
    }
}
```

Логика читается просто:

```text
Если мы на главном экране
и нажата OK,
перейти в настройки.
```

---

# Обработка списка настроек

Внутри меню может быть выбранный пункт:

```c
static uint8_t selectedItem;
```

Например:

```text
0 -> Feeding Time
1 -> Set Clock
2 -> Back
```

При `UP`:

```c
selectedItem--;
```

При `DOWN`:

```c
selectedItem++;
```

При `OK`:

```text
если выбран Feeding Time:
    перейти в EDIT_FEEDING_HOUR

если выбран Set Clock:
    перейти в EDIT_CLOCK_HOUR

если выбран Back:
    перейти в MAIN_SCREEN
```

---

# Ограничение выбранного пункта

Нельзя позволять:

```text
selectedItem = 255
```

или:

```text
selectedItem = 100
```

если пунктов всего три.

Можно сделать циклический переход:

```text
0 -> 1 -> 2 -> 0
```

Например:

```c
selectedItem++;

if (selectedItem >= MENU_ITEMS_COUNT)
{
    selectedItem = 0;
}
```

И обратно:

```c
if (selectedItem == 0)
{
    selectedItem = MENU_ITEMS_COUNT - 1;
}
else
{
    selectedItem--;
}
```

---

# Редактирование значения

Представим, что пользователь хочет изменить время кормления.

Сейчас в настройках:

```text
08:30
```

При входе в редактирование мы не обязаны сразу менять настоящую настройку.

Лучше создать временные значения:

```c
static uint8_t editedHour;
static uint8_t editedMinute;
```

При входе:

```c
editedHour = currentHour;
editedMinute = currentMinute;
```

Теперь пользователь редактирует копию.

---

# Почему нужна временная копия

Допустим, пользователь меняет:

```text
08:30
```

на:

```text
12:45
```

Но потом нажимает `BACK`.

Если мы изменяли настоящие данные сразу, отменить изменения будет сложнее.

С временной копией:

```text
Настоящие настройки:
08:30

Временные:
12:45
```

При `BACK`:

```text
временные значения просто отбрасываются
```

При `OK`:

```text
временные значения сохраняются
```

Это хороший принцип интерфейса.

---

# Сценарий редактирования

Например:

```text
Текущее значение:
08:30
```

Пользователь входит в меню:

```text
editedHour = 8
editedMinute = 30
```

Изменяет:

```text
editedHour = 9
editedMinute = 45
```

Если нажал `OK`:

```text
Settings_SaveFeedingTime(9, 45)
```

Если нажал `BACK`:

```text
ничего не сохранять
```

---

# Ограничение часа

Часы должны находиться:

```text
0..23
```

При увеличении:

```c
editedHour++;

if (editedHour > 23)
{
    editedHour = 0;
}
```

Получается:

```text
22 -> 23 -> 0 -> 1
```

При уменьшении:

```text
1 -> 0 -> 23 -> 22
```

---

# Ограничение минут

Минуты:

```text
0..59
```

При увеличении:

```text
58 -> 59 -> 0 -> 1
```

Важно, чтобы Menu отвечал за редактирование значения, но не обязательно за физическое хранение в EEPROM.

---

# Menu и Settings

Хорошая связь:

```text
Menu
   |
   v
Settings
   |
   v
EEPROM
```

Menu знает:

```text
Пользователь выбрал новое время:
09:45.
```

Settings знает:

```text
Где и как хранить время кормления.
```

EEPROM знает:

```text
Как физически записать байт.
```

---

# Плохая связь с EEPROM

Плохо:

```c
EEPROM_UpdateByte(10, editedHour);
EEPROM_UpdateByte(11, editedMinute);
```

прямо внутри Menu.

Почему?

Теперь Menu знает:

```text
что адрес 10 хранит часы;
что адрес 11 хранит минуты.
```

Это не ответственность интерфейса.

Лучше:

```c
Settings_SaveFeedingTime(editedHour, editedMinute);
```

---

# Menu и Scheduler

После изменения времени кормления Scheduler должен использовать новые значения.

Но Menu не должен разбираться во внутренней реализации Scheduler.

Возможные варианты:

```text
Menu
   |
   v
Settings_SaveFeedingTime()
   |
   v
Scheduler позже читает актуальные настройки
```

Или:

```text
Menu
   |
   v
Settings
   |
   v
Scheduler_SetSchedule()
```

Выбор зависит от архитектуры проекта.

Главное:

```text
Menu не должен напрямую менять внутренние static-переменные Scheduler.
```

---

# Menu и RTC

Если пользователь редактирует текущее время часов:

```text
12:45
```

после подтверждения Menu может вызвать:

```c
RTC_SetTime(hour, minute, second);
```

Но Menu не должен выполнять TWI-транзакции сам.

То есть:

```text
Menu
   |
   v
RTC_SetTime()
   |
   v
DS3231
   |
   v
TWI
```

---

# Кто должен рисовать экран

Есть несколько подходов.

Для простого проекта Menu может сам вызывать:

```c
LCD_Clear();
LCD_Print();
```

Например:

```c
static void Menu_DrawMainScreen(void);
static void Menu_DrawSettings(void);
static void Menu_DrawEditHour(void);
```

Это нормально для небольшого проекта.

Схема:

```text
Menu state
    |
    v
Draw function
    |
    v
LCD driver
```

---

# Рисование главного экрана

Например:

```text
12:45
Next 19:00
```

Функция может выглядеть концептуально так:

```c
static void Menu_DrawMainScreen(void)
{
    LCD_Clear();

    LCD_SetCursor(0, 0);
    LCD_Print(...);

    LCD_SetCursor(0, 1);
    LCD_Print(...);
}
```

Menu решает, какие данные показать.

LCD решает, как показать символы.

---

# Почему нельзя перерисовывать LCD постоянно

Можно написать:

```c
while (1)
{
    Menu_Draw();
}
```

Но тогда LCD будет обновляться постоянно.

Это может:

```text
создавать мерцание;
тратить процессорное время;
создавать лишние задержки;
усложнять логику.
```

Лучше перерисовывать только тогда, когда что-то изменилось.

---

# Флаг redraw

Можно использовать:

```c
static bool redrawRequired;
```

Когда состояние изменилось:

```c
menuState = MENU_SETTINGS;
redrawRequired = true;
```

В `Menu_Update()`:

```c
if (redrawRequired)
{
    Menu_DrawCurrentScreen();
    redrawRequired = false;
}
```

Теперь экран обновляется только при необходимости.

---

# Когда нужен redraw

Например:

```text
переход на другой экран;
изменение выбранного пункта;
изменение часа;
изменение минуты;
изменение отображаемых данных.
```

Не нужно очищать LCD на каждом проходе главного цикла.

---

# Архитектура Menu_Update

Можно построить:

```c
void Menu_Update(void)
{
    MenuEvent event = Menu_ReadEvent();

    if (event != MENU_EVENT_NONE)
    {
        Menu_HandleEvent(event);
    }

    if (redrawRequired)
    {
        Menu_DrawCurrentScreen();
        redrawRequired = false;
    }
}
```

Логика:

```text
Получить событие.
Обработать событие.
При необходимости обновить экран.
Вернуть управление.
```

---

# Menu_Update должен быть неблокирующим

Плохо:

```c
void Menu_Update(void)
{
    while (!Button_OK_WasPressed())
    {
    }
}
```

Теперь весь главный цикл остановлен.

Не работают:

```text
Feeder;
Scheduler;
другие кнопки;
обновление времени.
```

Правильно:

```text
проверить кнопку;
если события нет — выйти.
```

---

# Главный цикл

Например:

```c
while (1)
{
    Button_Update();
    Scheduler_Update();
    Feeder_Update();
    Menu_Update();
}
```

Menu получает немного процессорного времени.

Проверяет события.

Возвращает управление.

Никого не блокирует.

---

# Menu и FSM кормушки

Важно понимать, что в одном проекте может быть несколько FSM.

Например:

```text
Feeder FSM
```

состояния:

```text
FEEDER_IDLE
FEEDER_WAITING
```

И отдельно:

```text
Menu FSM
```

состояния:

```text
MENU_MAIN_SCREEN
MENU_SETTINGS
MENU_EDIT_FEEDING_HOUR
MENU_EDIT_FEEDING_MINUTE
```

Они независимы.

Пользователь может находиться в:

```text
MENU_SETTINGS
```

пока кормушка находится в:

```text
FEEDER_WAITING
```

Это нормально.

---

# Несколько FSM одновременно

Состояние всей системы можно представить как комбинацию:

```text
Feeder:
    FEEDER_WAITING

Menu:
    MENU_EDIT_FEEDING_MINUTE

Scheduler:
    ACTIVE

Button:
    RELEASED
```

Каждый модуль хранит собственное состояние.

Это намного лучше, чем один огромный:

```c
uint8_t globalState;
```

который пытается описать весь проект.

---

# Почему один глобальный FSM может быть плохим

Представим:

```text
STATE_MAIN_SCREEN_FEEDER_IDLE
STATE_MAIN_SCREEN_FEEDER_WAITING
STATE_SETTINGS_FEEDER_IDLE
STATE_SETTINGS_FEEDER_WAITING
STATE_EDIT_HOUR_FEEDER_IDLE
STATE_EDIT_HOUR_FEEDER_WAITING
```

Количество комбинаций начинает расти.

Если есть:

```text
4 состояния Menu
2 состояния Feeder
3 состояния связи
```

получаем потенциально:

```text
4 × 2 × 3 = 24 комбинации
```

Лучше хранить независимые FSM отдельно.

---

# Состояние экрана и выбранный пункт — не одно и то же

Допустим:

```c
menuState = MENU_SETTINGS;
```

Это означает:

> Мы на экране настроек.

Но внутри экрана может быть выбран:

```text
0 -> Feeding time
1 -> Clock
2 -> Back
```

Для этого нужна отдельная переменная:

```c
static uint8_t selectedItem;
```

Не нужно создавать состояния:

```text
MENU_SETTINGS_ITEM_0
MENU_SETTINGS_ITEM_1
MENU_SETTINGS_ITEM_2
```

если поведение экрана остаётся одинаковым.

Это было бы лишним усложнением.

---

# Когда создавать отдельное состояние

Полезный вопрос:

> Меняется ли поведение системы принципиально?

Например:

```text
Просмотр списка
```

и:

```text
Редактирование часа
```

ведут себя по-разному.

Значит, это разумные отдельные состояния.

Но:

```text
Выбран первый пункт
```

и:

```text
Выбран второй пункт
```

могут оставаться одним состоянием с разным `selectedItem`.

---

# Иерархия меню

Меню часто можно представить деревом:

```text
Main Screen
    |
    v
Settings
    |
    +--> Feeding Time
    |
    +--> Clock
    |
    +--> Back
```

Feeding Time:

```text
Edit Hour
    |
    v
Edit Minute
    |
    v
Save
```

Clock:

```text
Edit Hour
    |
    v
Edit Minute
    |
    v
Save
```

Для небольшого меню простой FSM достаточен.

# Когда меню становится большим

Если экранов становится очень много:

```text
20;
30;
50;
```

огромный `switch` может стать неудобным.

Тогда можно использовать:

```text
таблицы экранов;
callbacks;
указатели на функции;
иерархические FSM.
```

Но для учебной кормушки это преждевременно.

Нам важнее сначала понять базовую механику.

# Пример простого состояния Menu

Например:

```c
typedef enum
{
    MENU_MAIN,
    MENU_SETTINGS,
    MENU_EDIT_HOUR,
    MENU_EDIT_MINUTE
} MenuState;
```

И внутренние данные:

```c
static MenuState menuState;
static uint8_t selectedItem;
static uint8_t editedHour;
static uint8_t editedMinute;
static bool redrawRequired;
```

Каждая переменная имеет понятный смысл.

---

# Инициализация Menu

Например:

```c
void Menu_Init(void)
{
    menuState = MENU_MAIN;
    selectedItem = 0;
    redrawRequired = true;
}
```

После старта:

```text
Меню находится на главном экране.
Выбран первый пункт по умолчанию.
Экран нужно нарисовать.
```

---

# Рисование текущего состояния

Например:

```c
static void Menu_DrawCurrentScreen(void)
{
    switch (menuState)
    {
        case MENU_MAIN:
            Menu_DrawMain();
            break;

        case MENU_SETTINGS:
            Menu_DrawSettings();
            break;

        case MENU_EDIT_HOUR:
            Menu_DrawEditHour();
            break;

        case MENU_EDIT_MINUTE:
            Menu_DrawEditMinute();
            break;
    }
}
```

Здесь `switch` отражает архитектуру состояний.

---

# Обработка UP

Пример:

```c
static void Menu_HandleUp(void)
{
    switch (menuState)
    {
        case MENU_MAIN:
            break;

        case MENU_SETTINGS:
            Menu_SelectPrevious();
            break;

        case MENU_EDIT_HOUR:
            Menu_IncreaseHour();
            break;

        case MENU_EDIT_MINUTE:
            Menu_IncreaseMinute();
            break;
    }

    redrawRequired = true;
}
```

---

# Обработка OK

Например:

```c
static void Menu_HandleOk(void)
{
    switch (menuState)
    {
        case MENU_MAIN:
            menuState = MENU_SETTINGS;
            break;

        case MENU_SETTINGS:
            Menu_OpenSelectedItem();
            break;

        case MENU_EDIT_HOUR:
            menuState = MENU_EDIT_MINUTE;
            break;

        case MENU_EDIT_MINUTE:
            Settings_SaveFeedingTime(editedHour, editedMinute);
            menuState = MENU_SETTINGS;
            break;
    }

    redrawRequired = true;
}
```

Смысл читается напрямую из состояний.

---

# Обработка BACK

Например:

```text
MAIN:
    ничего

SETTINGS:
    вернуться в MAIN

EDIT_HOUR:
    отменить и вернуться в SETTINGS

EDIT_MINUTE:
    вернуться в EDIT_HOUR
```

Это тоже переходы FSM.

---

# Отмена изменений

Очень важно решить:

> Что делает BACK при редактировании?

Например:

```text
Было:
08:30

Пользователь изменил:
12:45

Нажал BACK.
```

Возможное поведение:

```text
не сохранять изменения
```

Именно для этого удобны:

```c
editedHour;
editedMinute;
```

---

# Сохранение изменений

После подтверждения:

```c
Settings_SaveFeedingTime(editedHour, editedMinute);
```

Затем:

```text
EEPROM обновляется;
Scheduler получает новые настройки;
Menu возвращается назад.
```

Важно, чтобы сохранение происходило только в определённый момент.

---

# Когда сохранять EEPROM

Плохой вариант:

```c
editedMinute++;
EEPROM_UpdateByte(...);
```

при каждом нажатии кнопки.

Если пользователь нажал `UP` 50 раз, будет 50 операций записи.

EEPROM имеет ограниченный ресурс перезаписи.

Лучше:

```text
пользователь редактирует временную копию;
```

и только после подтверждения:

```text
однократно сохранить результат.
```

---

# Меню и ресурс EEPROM

Это хороший пример взаимодействия архитектуры и физического мира.

На уровне UI кажется:

```text
Пользователь просто меняет число.
```

Но под ним находится EEPROM с ограниченным ресурсом записи.

Поэтому архитектурное решение:

```text
редактировать в RAM;
сохранять только после подтверждения.
```

защищает реальное железо.

---

# Обновление текущего времени на главном экране

Главный экран может показывать:

```text
12:45
```

Но время меняется.

Значит, иногда экран нужно обновлять даже без нажатий кнопок.

Например:

```text
каждую новую минуту
```

Menu может получить событие:

```text
MENU_EVENT_TIME_CHANGED
```

Или внешний код может вызвать:

```c
Menu_RequestRedraw();
```

Важно не обязательно обновлять дисплей тысячи раз в секунду.

---

# Кто должен сообщить Menu об изменении времени

Возможны варианты.

Например:

```text
Scheduler обнаружил новую минуту
        |
        v
Menu_RequestRedraw()
```

Но это создаёт зависимость Scheduler -> Menu.

Можно вместо этого внутри Menu периодически проверять отображаемые данные.

Или верхний уровень может связать события.

Например:

```c
if (Scheduler_MinuteChanged())
{
    Menu_RequestRedraw();
}
```

Для маленького проекта допустимы разные решения.

Главное — понимать направление зависимости.

---

# Не связывать всё со всем

Плохо:

```text
Scheduler знает Menu.
Menu знает Scheduler.
Feeder знает Menu.
Menu знает Feeder.
```

Так появляется паутина зависимостей.

Лучше, чтобы модули общались через узкие интерфейсы или через верхний уровень.

Например:

```text
main
   |
   +--> получает событие
   |
   +--> передаёт другому модулю
```

---

# Menu может отображать состояние Feeder

Например:

```text
Feeding...
```

Для этого Menu может спросить:

```c
Feeder_IsBusy();
```

Это лучше, чем читать:

```c
extern FeederState feederState;
```

Menu интересует смысл:

```text
Кормушка занята?
```

а не внутренняя реализация FSM.

---

# Отображение статуса

Например:

```text
12:45
Feeding...
```

или:

```text
12:45
Next 19:00
```

Menu может выбирать отображение:

```c
if (Feeder_IsBusy())
{
    LCD_Print("Feeding...");
}
else
{
    LCD_Print("Next 19:00");
}
```

Но важно следить, чтобы Menu не превращался в центр всей логики проекта.

---

# Menu должен отображать, а не управлять кормлением

Плохо:

```c
if (menuState == MENU_MAIN && hour == 8)
{
    Feeder_Request();
}
```

Menu не должен решать, когда кормить.

Это ответственность Scheduler.

Menu может запустить ручное кормление только если пользователь выбрал соответствующую команду:

```text
Manual Feed
```

Тогда:

```c
Feeder_Request();
```

логично.

---

# Ручное кормление через меню

Например:

```text
Main Menu
    |
    +--> Feed now
```

При выборе:

```c
Feeder_Request();
```

Почему это нормально?

Потому что Menu передаёт намерение пользователя:

```text
Покормить сейчас.
```

Но сам не управляет Servo.

---

# Хорошая цепочка ручного кормления

```text
Пользователь
    |
    v
Button
    |
    v
Menu
    |
    v
Feeder_Request()
    |
    v
Feeder FSM
    |
    v
Servo
```

Menu не знает:

```text
какой угол;
какой Timer;
какой OCR;
сколько ждать.
```

---

# Ошибка: всё меню в main.c

Плохо:

```c
while (1)
{
    if (buttonUp)
    {
        ...
    }

    if (buttonDown)
    {
        ...
    }

    if (screen == 1)
    {
        ...
    }

    if (editing)
    {
        ...
    }
}
```

Очень быстро `main.c` становится огромным.

Лучше:

```c
Menu_Update();
```

А логика меню находится внутри собственного модуля.

---

# Ошибка: один bool editing

Можно написать:

```c
bool editing;
```

Но скоро появляются вопросы:

```text
Что именно редактируется?

Часы?

Минуты?

Расписание?

Текущее время?
```

Часто отдельные состояния яснее:

```text
MENU_EDIT_FEEDING_HOUR
MENU_EDIT_FEEDING_MINUTE
MENU_EDIT_CLOCK_HOUR
MENU_EDIT_CLOCK_MINUTE
```

---

# Ошибка: слишком много bool

Например:

```c
bool inSettings;
bool editingHour;
bool editingMinute;
bool editingClock;
bool editingFeeding;
```

Могут возникнуть невозможные комбинации:

```text
editingHour = true
editingMinute = true
editingClock = true
editingFeeding = true
```

Что это значит?

FSM позволяет хранить одно определённое состояние.

---

# Ошибка: нет отдельной временной копии

Если менять настоящие настройки сразу:

```text
пользователь нажал UP;
настройка изменилась;
EEPROM записалась.
```

Тогда сложно:

```text
отменить изменение;
уменьшить количество записей;
реализовать подтверждение.
```

---

# Ошибка: LCD обновляется в каждом проходе

Плохо:

```c
while (1)
{
    LCD_Clear();
    LCD_Print(...);
}
```

Это лишняя работа.

Лучше использовать:

```text
redrawRequired
```

---

# Ошибка: Menu блокирует программу

Плохо:

```c
while (!Button_OK_WasPressed())
{
}
```

Меню ждёт пользователя и останавливает всё устройство.

Но пользователь может думать несколько минут.

В это время Scheduler и Feeder должны продолжать работать.

---

# Ошибка: ожидание пользователя

Очень важный принцип.

Устройство никогда не должно делать:

```text
Ждать, пока пользователь что-нибудь нажмёт.
```

Оно должно:

```text
показать экран;
запомнить состояние;
вернуться в главный цикл;
позже обработать событие.
```

Это и есть FSM.

---

# Пример без FSM

Плохо:

```c
LCD_Print("Set hour");

while (!Button_OK_WasPressed())
{
    if (Button_UpPressed())
    {
        hour++;
    }
}
```

Пока пользователь редактирует час:

```text
Scheduler остановлен;
Feeder_Update не вызывается;
другие задачи не выполняются.
```

---

# Пример с FSM

Вместо этого:

```text
menuState = MENU_EDIT_HOUR
```

И функция заканчивается.

Следующий проход:

```text
проверить кнопки;
обработать событие;
вернуть управление.
```

Пользователь может думать хоть десять минут.

Устройство продолжает работать.

---

# Связь с первой главой FSM

В кормушке мы говорили:

```text
Не ждать, пока закончится открытие.

Запомнить состояние.
```

В Menu то же самое:

```text
Не ждать, пока пользователь завершит настройку.

Запомнить текущий экран.
```

Это один и тот же архитектурный принцип.

---

# FSM кормушки

```text
FEEDER_IDLE
    |
    v
FEEDER_WAITING
```

FSM меню:

```text
MAIN
    |
    v
SETTINGS
    |
    v
EDIT_HOUR
    |
    v
EDIT_MINUTE
```

Разные задачи.

Один и тот же способ мышления.

# Menu и Scheduler работают одновременно

Представим:

```text
Пользователь редактирует время.
```

Текущее состояние:

```text
MENU_EDIT_FEEDING_HOUR
```

В этот момент наступает время автоматического кормления.

Scheduler вызывает:

```c
Feeder_Request();
```

Кормушка открывается.

Menu продолжает редактирование.

Потому что:

```text
Menu FSM
Feeder FSM
Scheduler
```

работают независимо.

---

# Почему неблокирующее Menu так важно

Если Menu ждёт пользователя через `while`, автоматическое кормление может не произойти.

Например:

```text
08:29:50
```

Пользователь вошёл в настройки.

Код завис в:

```c
while (!Button_OK_WasPressed())
```

Наступает:

```text
08:30:00
```

Но Scheduler не вызывается.

Кормление пропущено.

Это реальная архитектурная ошибка.

# Жизненный цикл Menu

Хороший интерфейс модуля может выглядеть так:

```c
void Menu_Init(void);
void Menu_Update(void);
void Menu_HandleEvent(MenuEvent event);
void Menu_RequestRedraw(void);
```

Не обязательно использовать все функции.

Но смысл понятен.

---

# Menu_Init

Приводит модуль к известному состоянию:

```text
главный экран;
первый пункт выбран;
нужна перерисовка.
```

---

# Menu_Update

Регулярно вызывается:

```text
проверяет события;
обрабатывает переходы;
рисует экран при необходимости.
```

---

# Menu_HandleEvent

Обрабатывает конкретное событие:

```text
UP
DOWN
OK
BACK
```

---

# Menu_RequestRedraw

Сообщает:

```text
Данные изменились.
Нужно обновить дисплей.
```

---

# Кто владеет состоянием Menu

Только сам Menu.

Например:

```c
static MenuState menuState;
```

Другие модули не должны писать:

```c
menuState = MENU_SETTINGS;
```

Лучше предоставить осмысленную функцию, если внешнему коду действительно нужен такой переход.

Например:

```c
Menu_OpenMainScreen();
```

Но даже это нужно только при реальной необходимости.

---

# Почему menuState должен быть static

Потому что это внутренняя деталь модуля.

Если любой файл может менять её:

```text
Scheduler меняет menuState.
Feeder меняет menuState.
main меняет menuState.
```

мы теряем контроль над переходами.

Menu должен сам защищать свою FSM.

---

# Разделение обработки и отображения

Полезно разделять:

```text
Что произошло?
```

и:

```text
Что нужно показать?
```

Например:

```c
Menu_HandleEvent(event);
```

меняет состояние.

Затем:

```c
Menu_DrawCurrentScreen();
```

отображает его.

Это упрощает код.

---

# Сначала изменить состояние, потом нарисовать

Например:

```text
Было:
MENU_MAIN

Событие:
OK

Новое состояние:
MENU_SETTINGS

После этого:
нарисовать SETTINGS.
```

То есть:

```text
Event
   |
   v
State transition
   |
   v
Redraw
```

---

# Модель состояния экрана

Можно мыслить так:

```text
menuState определяет:
    какой экран показывается.

selectedItem определяет:
    какой пункт выбран.

editedHour определяет:
    временное редактируемое значение.

redrawRequired определяет:
    нужно ли перерисовать LCD.
```

Каждая переменная отвечает на один вопрос.

---

# Курсор и выделение

LCD1602 не имеет сложного графического интерфейса.

Но можно использовать:

```text
>
```

для выбранного пункта.

Например:

```text
> Feeding time
  Set clock
```

После `DOWN`:

```text
  Feeding time
> Set clock
```

Menu меняет:

```c
selectedItem;
```

и запрашивает перерисовку.

---

# Ограничение LCD1602

У нас всего:

```text
16 символов × 2 строки
```

Поэтому интерфейс должен быть простым.

Это хороший пример того, как железо влияет на архитектуру UI.

Мы не можем показать десятки пунктов одновременно.

Нужна навигация.

---

# Прокрутка списка

Если пунктов больше двух:

```text
Feeding time
Set clock
Feed now
About
Back
```

можно хранить:

```c
selectedItem;
```

и:

```c
firstVisibleItem;
```

Тогда LCD показывает только два текущих пункта.

Но для небольшого меню можно обойтись проще.

---

# Не усложнять заранее

Для нашей учебной кормушки не нужен:

```text
UI framework;
виджеты;
динамические экраны;
иерархический router;
MVC;
MVVM.
```

Нам достаточно:

```text
enum состояния;
несколько переменных;
обработка событий;
функции отрисовки.
```

Главное — понять архитектурную идею.

# Когда нужен отдельный Display-модуль

В маленьком проекте:

```text
Menu -> LCD
```

достаточно.

Если UI становится сложнее, можно создать:

```text
Menu
   |
   v
View
   |
   v
LCD
```

Но это нужно только при реальном росте проекта.

---

# Menu и форматирование чисел

LCD_Print принимает строку.

Но время хранится как:

```c
uint8_t hour;
uint8_t minute;
```

Нужно превратить:

```text
8
30
```

в:

```text
08:30
```

Это может делать вспомогательная функция UI.

Например:

```text
08
09
10
```

Важно не смешивать форматирование интерфейса с драйвером DS3231.

---

# Кто отвечает за BCD

DS3231 может хранить время в BCD.

Например:

```text
0x30
```

означает:

```text
30
```

Но Menu не должен знать про BCD.

DS3231-драйвер должен вернуть обычные значения:

```c
hour = 8;
minute = 30;
```

А Menu уже форматирует:

```text
08:30
```

# Архитектура потока данных

Например, главный экран:

```text
DS3231
   |
   v
RTC driver
   |
   v
обычные hour/minute
   |
   v
Menu
   |
   v
форматирование строки
   |
   v
LCD1602
```

Каждый уровень решает свою задачу.

# Редактирование текущего времени

Допустим, есть пункт:

```text
Set clock
```

FSM может быть:

```text
MENU_SETTINGS
    |
    v
MENU_EDIT_CLOCK_HOUR
    |
    v
MENU_EDIT_CLOCK_MINUTE
    |
    v
RTC_SetTime()
    |
    v
MENU_SETTINGS
```

Почти та же схема, что и для времени кормления.

---

# Нужно ли создавать отдельные состояния для каждого поля

Для небольшого проекта — да, это часто самый понятный вариант.

Например:

```text
EDIT_HOUR
EDIT_MINUTE
```

Для очень больших форм можно хранить:

```c
editField;
```

Но в учебном проекте явные состояния проще читать.

---

# Как инженер выбирает между state и field

Вопрос:

> Меняется ли поведение существенно?

Если да:

```text
отдельное состояние.
```

Если различается только выбранный элемент:

```text
отдельная переменная.
```

Пример:

```text
Редактирование часа
и
Редактирование минут
```

могут быть отдельными состояниями.

А:

```text
выбран пункт 0
и
выбран пункт 1
```

обычно просто `selectedItem`.

---

# Ошибка: состояние содержит слишком много деталей

Плохо:

```text
MENU_SETTINGS_ITEM_0_HOUR_08_NOT_CHANGED
MENU_SETTINGS_ITEM_0_HOUR_09_CHANGED
```

FSM становится огромной.

Не нужно превращать каждое значение в состояние.

Состояние описывает режим поведения, а данные хранят конкретные значения.

---

# State и Data

Например:

```text
State:
MENU_EDIT_FEEDING_HOUR

Data:
editedHour = 12
```

Это правильное разделение.

Не нужно создавать:

```text
MENU_EDIT_FEEDING_HOUR_12
```

---

# Menu как отдельный модуль

Структура:

```text
app/
    menu.c
    menu.h
```

Внутри:

```text
MenuState
selectedItem
editedHour
editedMinute
redrawRequired
```

Публичный интерфейс:

```c
void Menu_Init(void);
void Menu_Update(void);
```

И, возможно:

```c
void Menu_HandleEvent(MenuEvent event);
```

---

# Пример архитектуры проекта с Menu

```text
                       +----------------+
                       |     main.c     |
                       +--------+-------+
                                |
          +---------------------+---------------------+
          |                     |                     |
          v                     v                     v
      Scheduler              Feeder                 Menu
          |                     |                 /   |   \
          v                     v                v    v    v
       DS3231                 Servo           Button LCD Settings
          |                     |                       |
          v                     v                       v
         TWI                  Timer1                  EEPROM
```

Menu становится ещё одним самостоятельным модулем приложения.

---

# События Menu

Хороший набор:

```c
typedef enum
{
    MENU_EVENT_NONE,
    MENU_EVENT_UP,
    MENU_EVENT_DOWN,
    MENU_EVENT_OK,
    MENU_EVENT_BACK
} MenuEvent;
```

Можно позже добавить:

```text
MENU_EVENT_TIME_CHANGED
MENU_EVENT_FEEDER_STATE_CHANGED
```

Но только если это действительно нужно.

---

# Получение события

Например:

```c
static MenuEvent Menu_ReadEvent(void)
{
    if (Button_UpWasPressed())
    {
        return MENU_EVENT_UP;
    }

    if (Button_DownWasPressed())
    {
        return MENU_EVENT_DOWN;
    }

    if (Button_OkWasPressed())
    {
        return MENU_EVENT_OK;
    }

    if (Button_BackWasPressed())
    {
        return MENU_EVENT_BACK;
    }

    return MENU_EVENT_NONE;
}
```

Для учебного проекта это понятный вариант.

---

# Что делать при двух одновременных нажатиях

Нужно заранее определить поведение.

Например:

```text
обработать только одно;
игнорировать комбинацию;
использовать комбинацию как отдельную команду.
```

Для простого меню можно обрабатывать первое найденное событие.

---

# Приоритет событий

Например:

```text
BACK имеет высший приоритет
```

или:

```text
OK раньше UP/DOWN.
```

Но это должно быть осознанное решение.

---

# Автоповтор при удержании кнопки

Иногда удобно:

```text
короткое нажатие -> +1
удержание -> быстро увеличивать
```

Тогда Button или Input-модуль может создавать события:

```text
PRESSED
REPEAT
RELEASED
```

Но это следующий уровень сложности.

Для первого меню достаточно фронта нажатия.

# Как инженер приходит к Menu FSM

Сначала код выглядит так:

```c
if (button)
{
    LCD_Print("Settings");
}
```

Потом появляются два экрана.

Затем пять.

Потом редактирование.

Потом кнопка Back.

И внезапно возникает вопрос:

> Как программа вообще понимает, где сейчас находится пользователь?

Ответ:

```text
Нужно хранить состояние интерфейса.
```

Так появляется Menu FSM.

---

# Практическое применение

FSM меню встречается практически в любом Embedded-устройстве с интерфейсом.

Например:

```text
3D-принтер;
термостат;
лабораторный блок питания;
мультиметр;
осциллограф;
кофемашина;
стиральная машина;
медицинское оборудование;
автомобильная панель;
умный дом.
```

У каждого есть состояния интерфейса.

# Пример термостата

```text
MAIN_SCREEN
    |

SETTINGS
    |
    +--> EDIT_TARGET_TEMP
```

Те же идеи:

# Типичные ошибки

## Ошибка 1. Огромный набор if

```c
if (buttonUp)
{
    if (screen == ...)
    {
        ...
    }
}
```

Код быстро становится нечитаемым.

---

## Ошибка 2. Несколько bool вместо состояния

```c
bool editing;
bool inSettings;
bool editingHour;
bool editingMinute;
```

Возможны противоречивые комбинации.

---

## Ошибка 3. Блокирующее ожидание пользователя

```c
while (!Button_OK_WasPressed())
{
}
```

Останавливает весь проект.

---

## Ошибка 4. Прямой доступ к LCD-регистрам

Menu не должен управлять GPIO дисплея.

---

## Ошибка 5. Прямая запись EEPROM при каждом изменении

Снижает ресурс памяти.

---

## Ошибка 6. Отсутствие временной копии

Нельзя удобно отменить изменения.

---

## Ошибка 7. Перерисовка экрана постоянно

Создаёт лишнюю нагрузку и может вызывать мерцание.

---

## Ошибка 8. Menu управляет чужой логикой

Например:

```text
Menu само решает время автоматического кормления.
```

Это задача Scheduler.

---

## Ошибка 9. Чужие модули меняют menuState

FSM теряет контроль над переходами.

---

## Ошибка 10. Слишком много состояний

Каждый выбранный пункт или число не должен становиться отдельным состоянием.

# Практическое задание

Спроектируйте меню для умной теплицы.

Главный экран:

```text
Temp: 24 C
Hum: 60 %
```

Меню:

```text
> Temperature
  Watering
  Clock
  Back
```

Настройка температуры:

```text
Target: 25 C
```

Настройка полива:

```text
Hour: 07
Minute: 30
```

Нужно определить состояния.

Например:

```text
MENU_MAIN
MENU_SETTINGS
MENU_EDIT_TARGET_TEMP
MENU_EDIT_WATER_HOUR
MENU_EDIT_WATER_MINUTE
```

Затем ответить:

```text
Что делает UP в каждом состоянии?

Что делает OK?

Что делает BACK?

Какие значения редактируются во временных переменных?

Когда происходит запись EEPROM?

Кто управляет насосом?

Должен ли Menu напрямую включать GPIO насоса?

Как обновлять текущую температуру на экране без постоянной очистки LCD?
```

# Главное

Menu — это не просто текст на LCD.

И не набор кнопок.

Menu — это отдельная система поведения.

Она должна помнить:

```text
Где сейчас находится пользователь?

Что он выбрал?

Что он редактирует?

Какие действия разрешены?

Что должно произойти после события?
```

Поэтому меню естественно превращается в FSM.

Например:

```text
MAIN_SCREEN
    |
    v
SETTINGS
    |
    v
EDIT_HOUR
    |
    v
EDIT_MINUTE
    |
    v
SAVE
```

Одна и та же кнопка получает разный смысл в разных состояниях.

Например:

```text
UP в SETTINGS:
    выбрать предыдущий пункт.

UP в EDIT_HOUR:
    увеличить час.

UP в EDIT_MINUTE:
    увеличить минуту.
```

Menu не должно ждать пользователя.

Оно должно:

```text
показать экран;
запомнить состояние;
вернуться в главный цикл;
обработать следующее событие позже.
```

Именно поэтому пользователь может спокойно редактировать настройки, пока одновременно:

```text
Scheduler проверяет расписание;
Feeder управляет заслонкой;
Timer считает интервалы;
RTC хранит время.
```

Потому что каждый модуль имеет свою ответственность и своё состояние.

В итоге вся пятая часть складывается в единую систему:

```text
FSM
    учит программу помнить своё состояние.

Архитектура драйверов
    отделяет железо от смысла.

Архитектура проекта
    разделяет ответственности модулей.

Scheduler
    запускает задачи в нужный момент.

Menu
    управляет взаимодействием с пользователем через собственную FSM.
```

Теперь программа уже не выглядит как один огромный `while (1)` с десятками условий.

Она становится системой независимых модулей:

```text
каждый знает свою задачу;
каждый хранит своё состояние;
каждый предоставляет понятный интерфейс;
каждый быстро возвращает управление.
```

Именно в этот момент Embedded-проект начинает превращаться из набора работающего кода в настоящую архитектуру.
