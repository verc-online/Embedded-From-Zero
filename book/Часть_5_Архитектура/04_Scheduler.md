# 04. Scheduler

## История

Представим, что автоматическая кормушка должна выдавать корм каждый день в 08:30 и 19:00.

На первый взгляд задача кажется простой.

Можно написать:

```c
if (hour == 8 && minute == 30)
{
    Feeder_Request();
}
```

И ещё:

```c
if (hour == 19 && minute == 0)
{
    Feeder_Request();
}
```

Но сразу появляется проблема.

Главный цикл выполняется очень быстро.

За одну минуту условие:

```c
hour == 8 && minute == 30
```

будет истинно не один раз, а тысячи или даже миллионы раз.

Значит, программа может многократно вызывать:

```c
Feeder_Request();
```

Нам нужен механизм, который умеет не просто смотреть на часы, а понимать:

> Наступил ли новый момент времени, в который нужно выполнить задачу?

Именно эту задачу решает Scheduler.

---

# Постановка задачи

Наша кормушка должна:

```text
читать текущее время;
знать расписание;
проверять наступление нужной минуты;
запускать кормление только один раз;
не блокировать главный цикл.
```

Важно, чтобы всё это происходило внутри обычного:

```c
while (1)
{
    Scheduler_Update();
    Feeder_Update();
}
```

То есть Scheduler не должен сидеть и ждать:

```c
while (hour != 8 || minute != 30)
{
}
```

Потому что тогда вся остальная система остановится.

Scheduler должен быстро проверять состояние времени и возвращать управление.

---

# Простое объяснение

Scheduler можно представить как диспетчера.

У него есть:

```text
текущее время;
список задач;
правила запуска.
```

Он регулярно спрашивает:

```text
Наступило ли время выполнить что-то?
```

Если нет — ничего не делает.

Если да — создаёт действие.

Например:

```text
08:30 -> покормить
19:00 -> покормить
```

Схема:

```text
DS3231
   |
   v
Текущее время
   |
   v
Scheduler
   |
   +--> Совпало с расписанием?
              |
              +--> Нет -> ничего
              |
              +--> Да
                     |
                     v
              Feeder_Request()
```

Главная идея:

**Scheduler не ждёт нужного времени. Он периодически проверяет, наступило ли оно.**

---

# Timer, RTC и Scheduler — не одно и то же

Это очень важно.

## Timer

Timer отвечает на вопрос:

> Сколько времени прошло?

Например:

```c
Timer_HasElapsed(startTime, 1000);
```

Он полезен для интервалов:

```text
подождать 1 секунду;
закрыть заслонку через 500 мс;
обновить дисплей раз в 100 мс.
```

---

## RTC

RTC отвечает на вопрос:

> Который сейчас час?

Например:

```text
08:30:15
19:00:00
23:59:42
```

DS3231 хранит реальное время независимо от микроконтроллера.

---

## Scheduler

Scheduler отвечает на вопрос:

> Пора ли сейчас выполнить задачу?

Например:

```text
В 08:30 покормить.

В 19:00 покормить.
```

Схема:

```text
Timer
    |
    +--> интервалы

RTC
    |
    +--> текущее время

Scheduler
    |
    +--> решение о запуске задачи
```

---

# Почему одного RTC недостаточно

Можно подумать:

> У нас есть DS3231, значит Scheduler не нужен.

Но RTC только сообщает время.

Например:

```text
08:30:00
```

Он не знает:

```text
что в 08:30 нужно кормить;
сколько раз это делать;
какие задачи есть в расписании.
```

Эти правила принадлежат Scheduler.

То есть:

```text
RTC
    знает время.

Scheduler
    знает расписание.
```

---

# Почему одного Timer недостаточно

Timer умеет считать интервалы.

Но если питание отключили и включили снова, он начинает отсчёт заново.

Например:

```text
0 мс
1 мс
2 мс
...
```

Он не знает:

```text
сейчас 08:30 утра
или
19:00 вечера.
```

Поэтому для календарного расписания нужен RTC.

---

# Архитектура Scheduler

В нашем проекте Scheduler может выглядеть примерно так:

```text
Scheduler
    |
    +--> получает время
    +--> отслеживает смену секунды
    +--> определяет смену минуты
    +--> проверяет расписание
    +--> создаёт запрос на кормление
```

Схема:

```text
RTC
   |
   v
Scheduler_Update()
   |
   v
Изменилась секунда?
   |
   +--> Нет -> выйти
   |
   +--> Да
          |
          v
     Изменилась минута?
          |
          +--> Нет -> выйти
          |
          +--> Да
                 |
                 v
          Проверить расписание
                 |
                 v
          Feeder_Request()
```

---

# Почему не нужно проверять расписание постоянно

Можно написать:

```c
while (1)
{
    RTC_GetTime(&hour, &minute, &second);

    Scheduler_CheckFeedingTime();
}
```

Это технически возможно.

Но бессмысленно проверять расписание миллионы раз в секунду.

Если расписание задано с точностью до минуты, достаточно реагировать на изменение минуты.

Например:

```text
08:29:59
        |
        v
08:30:00
        |
        v
Новая минута
        |
        v
Проверить расписание
```

После этого повторная проверка в:

```text
08:30:01
08:30:02
08:30:03
```

уже не нужна.

---

# Отслеживание смены секунды

Можно хранить предыдущее значение:

```c
static uint8_t previousSecond;
```

И при каждом обновлении получать текущее:

```c
uint8_t currentSecond;
```

Проверка:

```c
if (currentSecond != previousSecond)
{
    previousSecond = currentSecond;
}
```

Это означает:

> Произошла новая секунда.

Аналогично можно отслеживать минуту.

---

# Отслеживание новой минуты

Представим:

```text
08:29:59
```

Затем:

```text
08:30:00
```

Мы видим:

```text
minute changed
```

Именно в этот момент нужно проверить расписание.

Логика:

```c
if (minuteChanged)
{
    Scheduler_CheckFeedingTime();
}
```

Это намного эффективнее, чем проверять расписание при каждом проходе главного цикла.

---

# Почему нельзя просто проверять секунду на ноль

Можно написать:

```c
if (second == 0)
{
    Scheduler_CheckFeedingTime();
}
```

Но это опасно.

Главный цикл может пройти тысячи раз, пока `second == 0`.

Получится:

```text
08:30:00
08:30:00
08:30:00
08:30:00
...
```

И Scheduler многократно выполнит одну и ту же задачу.

Поэтому нужно отслеживать переход:

```text
59 -> 00
```

или просто изменение значения.

---

# Событие важнее состояния

Сравним:

```text
Состояние:
    сейчас minute == 30
```

и:

```text
Событие:
    минута только что изменилась на 30
```

Это не одно и то же.

Scheduler обычно должен реагировать именно на событие.

Схема:

```text
Было:
08:29

Стало:
08:30

Событие:
наступила новая минута
```

---

# Пример структуры расписания

Вместо отдельных переменных:

```c
uint8_t feedingHour1;
uint8_t feedingMinute1;

uint8_t feedingHour2;
uint8_t feedingMinute2;
```

удобнее использовать структуру:

```c
typedef struct
{
    uint8_t hour;
    uint8_t minute;
} FeedingTime;
```

И массив:

```c
static FeedingTime feedingSchedule[] =
{
    {8, 30},
    {19, 0}
};
```

Теперь Scheduler может пройти по расписанию:

```c
for (uint8_t i = 0; i < scheduleCount; i++)
{
    if (hour == feedingSchedule[i].hour &&
        minute == feedingSchedule[i].minute)
    {
        Feeder_Request();
    }
}
```

Это масштабируется лучше.

---

# Почему Scheduler не должен знать про Servo

Плохо:

```c
if (hour == feedingHour &&
    minute == feedingMinute)
{
    Servo_SetAngle(180);
}
```

Scheduler теперь знает:

```text
что кормление реализуется сервой;
какой угол открывает заслонку.
```

Это не его задача.

Правильно:

```c
Feeder_Request();
```

Scheduler только говорит:

> Пора выполнить кормление.

Feeder уже решает, как именно это сделать.

---

# Scheduler и FSM

Scheduler и FSM хорошо работают вместе.

Scheduler отвечает:

```text
Когда нужно начать действие?
```

FSM отвечает:

```text
Как действие развивается во времени?
```

Например:

```text
08:30
   |
   v
Scheduler
   |
   v
Feeder_Request()
   |
   v
FEEDER_IDLE -> FEEDER_WAITING
   |
   v
Прошло время
   |
   v
FEEDER_WAITING -> FEEDER_IDLE
```

То есть Scheduler запускает процесс, а FSM управляет его дальнейшим поведением.

---

# Scheduler и главный цикл

Главный цикл может выглядеть так:

```c
while (1)
{
    Scheduler_Update();
    Feeder_Update();
    Menu_Update();
}
```

Каждый модуль быстро выполняет свою работу.

Scheduler:

```text
проверил время;
при необходимости создал запрос;
вернул управление.
```

Feeder:

```text
проверил состояние;
при необходимости сменил состояние;
вернул управление.
```

Menu:

```text
проверил ввод;
обновил экран;
вернул управление.
```

---

# Пример Scheduler_Update

Упрощённо:

```c
void Scheduler_Update(void)
{
    uint8_t hour;
    uint8_t minute;
    uint8_t second;

    RTC_GetTime(&hour, &minute, &second);

    if (second != previousSecond)
    {
        previousSecond = second;

        if (minute != previousMinute)
        {
            previousMinute = minute;

            Scheduler_CheckFeedingTime(hour, minute);
        }
    }
}
```

Здесь есть важная идея.

Мы не проверяем расписание постоянно.

Только когда реально наступила новая минута.

---

# Почему можно отслеживать минуту напрямую

Можно упростить:

```c
if (minute != previousMinute)
{
    previousMinute = minute;

    Scheduler_CheckFeedingTime(hour, minute);
}
```

Но есть нюанс.

Если RTC читается не каждую секунду или в системе есть другая логика времени, иногда удобнее сначала отслеживать секунду, а уже потом минуту.

Выбор зависит от архитектуры проекта.

Главное — событие новой минуты должно фиксироваться один раз.

---

# Инициализация Scheduler

Scheduler должен знать начальное значение времени.

Например:

```c
void Scheduler_Init(void)
{
    RTC_GetTime(&currentHour,
                &currentMinute,
                &currentSecond);

    previousMinute = currentMinute;
    previousSecond = currentSecond;
}
```

Зачем?

Чтобы при первом вызове `Scheduler_Update()` программа не решила ошибочно, что произошло изменение времени.

---

# Что происходит после перезапуска

Допустим, устройство включили в 08:30.

Вопрос:

> Нужно ли сразу выполнять кормление?

Это уже архитектурное решение.

Можно выбрать два варианта.

## Вариант 1. Не выполнять

Scheduler начинает отслеживать изменения с текущего момента.

Если включили в 08:30, кормление не запускается автоматически.

---

## Вариант 2. Выполнять

При старте Scheduler сразу проверяет расписание.

Тогда:

```text
включение в 08:30
        |
        v
совпадение расписания
        |
        v
Feeder_Request()
```

Оба варианта возможны.

Главное — выбрать поведение сознательно.

---

# Защита от повторного запуска

Представим, что Scheduler вызвал:

```c
Feeder_Request();
```

Но кормушка уже занята.

Feeder должен сам проверить своё состояние:

```c
if (feederState != FEEDER_IDLE)
{
    return;
}
```

Это хороший архитектурный принцип.

Scheduler не обязан знать внутреннее состояние Feeder.

Он отправляет запрос.

Feeder сам решает, может ли его принять.

---

# Что делать, если совпали несколько задач

Представим:

```text
08:30 -> кормление
08:30 -> сохранить статистику
08:30 -> обновить экран
```

Scheduler может вызвать несколько действий.

Например:

```c
if (isFeedingTime)
{
    Feeder_Request();
}

if (isStatisticsTime)
{
    Statistics_Save();
}

if (isDisplayUpdateTime)
{
    Display_RequestRefresh();
}
```

Но если задач становится много, архитектура может потребовать более общего планировщика.

Для нашей кормушки это пока не обязательно.

---

# Простой Scheduler и общий Scheduler

Важно различать два уровня.

## Простой Scheduler приложения

Он знает конкретные задачи:

```text
проверить кормление;
запустить Feeder.
```

Например:

```c
Scheduler_CheckFeedingTime();
```

---

## Общий Scheduler задач

Он может хранить:

```text
функцию;
период;
время следующего запуска.
```

Например:

```text
Task A -> каждые 100 мс
Task B -> каждую 1 секунду
Task C -> каждые 5 секунд
```

Такой Scheduler сложнее.

Для нашего проекта простой вариант достаточен.

---

# Не нужно усложнять заранее

Можно было бы сразу построить:

```text
очередь задач;
приоритеты;
динамическую регистрацию;
callbacks;
deadline scheduler.
```

Но для простой кормушки это было бы переусложнением.

Нам нужно решить реальную задачу:

```text
проверить время;
сопоставить с расписанием;
вызвать Feeder_Request().
```

Архитектура должна соответствовать масштабу проекта.

---

# Scheduler и точность

Допустим, Scheduler_Update вызывается редко.

Например:

```text
08:29:59
```

Следующий вызов только в:

```text
08:30:02
```

Если мы проверяем просто:

```c
minute != previousMinute
```

то новую минуту всё равно обнаружим.

Но если программа зависнет на несколько минут, можно пропустить несколько событий.

Например:

```text
08:29
        |
        | программа зависла
        v
08:33
```

Тогда Scheduler увидит только новое текущее значение.

Он не узнает автоматически, что были пропущены:

```text
08:30
08:31
08:32
```

Для кормушки нужно решить:

> Нужно ли выполнять пропущенное кормление после восстановления?

Это уже часть требований к системе.

---

# Пропущенные события

Есть два подхода.

## Подход 1. Не выполнять пропущенное

Если время прошло, задача потеряна.

Например:

```text
Кормление было в 08:30.

Устройство включилось в 08:35.

Кормление не выполняется.
```

---

## Подход 2. Выполнить ближайшую пропущенную задачу

Программа проверяет:

```text
Было ли запланированное событие между прошлым и текущим временем?
```

Это сложнее.

Для учебной кормушки первый вариант проще и понятнее.

---

# Scheduler и EEPROM

Расписание может храниться в EEPROM.

Например:

```text
08:30
19:00
```

После включения:

```text
EEPROM
   |
   v
Settings
   |
   v
feedingSchedule[]
   |
   v
Scheduler
```

Scheduler не должен сам знать адреса EEPROM.

Плохо:

```c
feedingHour = EEPROM_ReadByte(10);
feedingMinute = EEPROM_ReadByte(11);
```

внутри Scheduler.

Лучше:

```c
Settings_GetFeedingTime(...);
```

или передать расписание при инициализации.

---

# Scheduler и Settings

Хорошее разделение:

```text
Settings
    хранит настройки.

Scheduler
    использует настройки.
```

Например:

```text
Menu
   |
   v
Settings_SaveFeedingTime()
   |
   v
EEPROM
```

А Scheduler читает уже готовые значения.

---

# Scheduler и Menu

Menu может изменять расписание.

Например:

```text
Пользователь изменил 08:30 на 09:00.
```

После сохранения:

```text
Menu
   |
   v
Settings
   |
   v
Scheduler
```

Но Menu не должен напрямую запускать кормление по расписанию.

У него другая ответственность.

---

# Один раз на минуту

Ключевой принцип нашего Scheduler:

```text
Проверять расписание только при смене минуты.
```

Схема:

```text
08:29:58
    |
    v
ничего

08:29:59
    |
    v
ничего

08:30:00
    |
    v
новая минута
    |
    v
проверка расписания
    |
    v
совпадение
    |
    v
Feeder_Request()

08:30:01
    |
    v
ничего

08:30:02
    |
    v
ничего
```

Так мы избегаем повторного запуска.

---

# Почему не нужен delay до следующей минуты

Плохо:

```c
RTC_GetTime(...);

_delay_ms(60000);

Scheduler_CheckFeedingTime();
```

Это блокирует всю программу.

Кроме того, задержка на 60 секунд не гарантирует точного совпадения с календарной минутой.

Лучше регулярно читать время и отслеживать изменения.

---

# Scheduler не обязан быть точным до микросекунды

Для кормушки расписание работает с точностью до минуты.

Поэтому нет смысла строить систему с микросекундной точностью.

Это тоже важный инженерный принцип.

Точность должна соответствовать задаче.

Для:

```text
PWM
UART
SPI
```

важны микросекунды.

Для:

```text
кормление в 08:30
```

достаточно минут.

---

# Что должен хранить Scheduler

Минимально:

```text
предыдущее значение времени;
расписание;
возможно, текущее время.
```

Например:

```c
static uint8_t currentHour;
static uint8_t currentMinute;
static uint8_t currentSecond;

static uint8_t previousSecond;
static uint8_t previousMinute;
```

Но нужно избегать дублирования без необходимости.

Если текущее время нужно только внутри одной функции, можно использовать локальные переменные.

---

# Локальные или static переменные

Если значение нужно только во время одного вызова:

```c
uint8_t hour;
uint8_t minute;
uint8_t second;
```

лучше оставить его локальным.

Если нужно помнить значение между вызовами:

```c
static uint8_t previousMinute;
```

тогда `static` оправдан.

Это хорошо показывает смысл `static`:

> Сохранить состояние между вызовами функции или внутри модуля.

---

# Scheduler как FSM?

Иногда Scheduler тоже можно представить как конечный автомат.

Но для нашей простой задачи это не обязательно.

У него нет сложного набора режимов поведения.

Он просто:

```text
читает время;
отслеживает изменение;
проверяет расписание.
```

Не нужно использовать FSM там, где обычной логики достаточно.

---

# Когда Scheduler сам становится сложным

Если появляются:

```text
пауза расписания;
ручной режим;
режим отпуска;
ошибка RTC;
синхронизация с сервером;
летнее время;
несколько типов задач;
приоритеты;
```

тогда Scheduler может получить собственные состояния.

Например:

```text
SCHEDULER_DISABLED
SCHEDULER_ACTIVE
SCHEDULER_ERROR
```

Но это появляется только при реальной необходимости.

---

# Обработка ошибки RTC

Представим, что DS3231 не отвечает.

Тогда Scheduler не может доверять времени.

Возможны варианты:

```text
ничего не делать;
перейти в ERROR;
показать ошибку;
использовать последнее известное время.
```

Для простого проекта можно выбрать:

```text
нет корректного времени -> не выполнять автоматическое кормление.
```

Но это должно быть осознанное решение.

---

# Почему Scheduler не должен зависать при ошибке

Плохо:

```c
while (!RTC_IsAvailable())
{
}
```

Теперь весь проект остановлен.

Лучше:

```c
if (!RTC_GetTime(...))
{
    return;
}
```

Scheduler завершает обновление, а другие модули продолжают работать.

---

# Архитектура нашего Scheduler

Можно представить так:

```text
+---------------------------+
|       Scheduler_Init      |
+---------------------------+
             |
             v
    Считать начальное время
             |
             v
   Запомнить секунду/минуту
```

Затем:

```text
+---------------------------+
|      Scheduler_Update     |
+---------------------------+
             |
             v
       Прочитать RTC
             |
             v
       Новая секунда?
             |
        +----+----+
        |         |
       Нет       Да
        |         |
        v         v
      Выход   Новая минута?
                  |
             +----+----+
             |         |
            Нет       Да
             |         |
             v         v
           Выход   Проверить расписание
                          |
                          v
                    Совпадение?
                          |
                     +----+----+
                     |         |
                    Нет       Да
                     |         |
                     v         v
                   Выход   Feeder_Request()
```

---

# Пример Scheduler_CheckFeedingTime

Упрощённо:

```c
static void Scheduler_CheckFeedingTime(uint8_t hour,
                                       uint8_t minute)
{
    for (uint8_t i = 0; i < FEEDING_SCHEDULE_COUNT; i++)
    {
        if (hour == feedingSchedule[i].hour &&
            minute == feedingSchedule[i].minute)
        {
            Feeder_Request();
        }
    }
}
```

Функция ничего не знает о Servo.

Она только сравнивает время.

---

# Почему проверка должна быть отдельной функцией

Можно было написать всё в `Scheduler_Update`.

Но отдельная функция:

```c
Scheduler_CheckFeedingTime();
```

улучшает читаемость.

Мы видим этапы:

```text
Получить время.
Обнаружить новую минуту.
Проверить расписание.
```

Это отражает структуру задачи.

---

# Что делать с несколькими совпадениями

Допустим, в массиве случайно два одинаковых времени:

```text
08:30
08:30
```

Тогда `Feeder_Request()` будет вызван дважды.

Но если Feeder правильно защищён:

```c
if (feederState != FEEDER_IDLE)
{
    return;
}
```

второй запрос будет проигнорирован.

Тем не менее лучше не хранить дубли в расписании.

---

# Что делать, если кормушка занята

Допустим:

```text
08:30 -> началось кормление.

08:31 -> новое кормление.
```

Но предыдущее ещё не завершилось.

Scheduler вызывает:

```c
Feeder_Request();
```

Feeder проверяет состояние и решает:

```text
занят -> отклонить запрос.
```

Это хорошее разделение ответственности.

---

# Должен ли Scheduler проверять Feeder_IsBusy

Можно написать:

```c
if (!Feeder_IsBusy())
{
    Feeder_Request();
}
```

Но в простом проекте это не обязательно.

Лучше, чтобы `Feeder_Request()` сам защищал свои инварианты.

То есть модуль сам отвечает за допустимость операции.

---

# Инвариант

Инвариант — это правило, которое всегда должно оставаться истинным.

Для Feeder:

```text
Нельзя повторно начать кормление,
если кормушка уже занята.
```

Feeder обязан сам защищать это правило.

Нельзя полагаться на то, что все внешние модули всегда правильно проверят состояние.

---

# Scheduler и тестирование

Scheduler удобно проверять отдельно.

Например:

```text
08:29 -> ничего
08:30 -> один вызов Feeder_Request
08:30 повторно -> ничего
19:00 -> один вызов
```

Полезные тестовые случаи:

```text
смена часа;
смена суток;
23:59 -> 00:00;
пустое расписание;
дубликаты;
ошибка RTC.
```

---

# Переход через полночь

Например:

```text
23:59
    |
    v
00:00
```

Если Scheduler сравнивает текущее значение минуты с предыдущим, он увидит изменение:

```text
59 -> 0
```

И корректно проверит расписание.

То же самое с часами:

```text
23 -> 0
```

---

# Дни недели

Позже можно расширить расписание:

```c
typedef struct
{
    uint8_t hour;
    uint8_t minute;
    uint8_t daysMask;
} ScheduleEntry;
```

Например:

```text
Понедельник-Пятница -> 08:00
Суббота-Воскресенье -> 09:30
```

Но для первого проекта это не обязательно.

---

# Маска дней недели

Например:

```text
bit 0 -> Monday
bit 1 -> Tuesday
bit 2 -> Wednesday
...
```

Тогда можно хранить несколько дней в одном байте.

Но такие усложнения стоит добавлять только после того, как базовый Scheduler полностью понятен.

---

# Периодические задачи без RTC

Scheduler можно использовать не только с календарным временем.

Например:

```text
каждые 100 мс -> обновить кнопки;
каждую секунду -> обновить экран;
каждые 10 секунд -> сохранить статистику.
```

Тогда Scheduler может использовать Timer.

Схема:

```text
Timer
   |
   v
Scheduler
   |
   v
Периодические задачи
```

---

# Календарные и интервальные задачи

Полезно различать.

## Интервальная задача

```text
Через 500 мс закрыть заслонку.
```

Используем:

```text
Timer + FSM
```

---

## Календарная задача

```text
В 08:30 выполнить кормление.
```

Используем:

```text
RTC + Scheduler
```

Это разные задачи времени.

---

# Почему закрытие заслонки — не задача Scheduler

Можно было бы написать:

```text
Открыли заслонку в 08:30:00.

Scheduler должен закрыть в 08:30:01.
```

Но это плохое разделение.

Закрытие заслонки — часть поведения Feeder.

Поэтому:

```text
Scheduler
    запускает кормление.

Feeder FSM
    управляет открытием и закрытием.
```

---

# Scheduler не управляет процессом

Это ключевой момент.

Scheduler решает:

```text
когда стартовать.
```

Но после старта управление принимает другой модуль.

Например:

```text
Scheduler -> Feeder_Request()
```

Дальше Scheduler уже не должен контролировать:

```text
открылась ли заслонка;
сколько ждать;
когда закрыть.
```

Это ответственность Feeder.

---

# Типичные ошибки

## Ошибка 1. Проверять условие постоянно без защиты

Плохо:

```c
if (hour == 8 && minute == 30)
{
    Feeder_Request();
}
```

Условие будет истинно всю минуту.

---

## Ошибка 2. Проверять `second == 0`

Плохо:

```c
if (second == 0)
{
    Scheduler_CheckFeedingTime();
}
```

Это условие также истинно многократно.

Нужно реагировать на изменение.

---

## Ошибка 3. Использовать delay

Плохо:

```c
_delay_ms(60000);
```

Scheduler блокирует систему.

---

## Ошибка 4. Scheduler управляет железом

Плохо:

```c
OCR1A = 250;
```

внутри Scheduler.

Правильно:

```c
Feeder_Request();
```

---

## Ошибка 5. Scheduler знает адреса EEPROM

Плохо:

```c
EEPROM_ReadByte(10);
```

если адрес 10 означает час кормления.

Эти знания должны принадлежать Settings.

---

## Ошибка 6. Не инициализировать прошлое время

Тогда первый вызов может ошибочно восприняться как новое событие.

---

## Ошибка 7. Слишком сложный общий Scheduler

Для двух точек кормления не нужен диспетчер задач уровня RTOS.

---

## Ошибка 8. Не определить поведение после перезапуска

Нужно заранее решить:

```text
выполнять ли задачу, если устройство включилось ровно в момент расписания.
```

---

## Ошибка 9. Не учитывать пропущенные задачи

Если система может долго зависать или отключаться, нужно решить:

```text
нужно ли догонять пропущенное событие.
```

---

# Практическое применение

Scheduler встречается во множестве устройств.

Например:

```text
автоматический полив;
кормушка;
термостат;
будильник;
умный свет;
система вентиляции;
медицинский дозатор;
логгер данных;
умная теплица;
зарядная станция.
```

Примеры:

```text
Каждый день в 07:00 включить свет.

Каждые 15 минут измерить температуру.

Каждое воскресенье в 12:00 выполнить обслуживание.

Через 5 секунд закрыть клапан.
```

Но для разных типов времени используются разные механизмы.

---

# Как инженер приходит к Scheduler

Сначала инженер пишет:

```c
if (hour == 8 && minute == 30)
{
    Feeder_Request();
}
```

Потом замечает, что это вызывается многократно.

Добавляет флаг:

```c
bool alreadyFed;
```

Потом появляется второе время.

Третье.

Перезапуск устройства.

Несколько задач.

И становится понятно:

> Нужно отдельно управлять расписанием и событиями времени.

Так появляется Scheduler.

---

# Когда Scheduler действительно нужен

Scheduler полезен, если есть:

```text
несколько задач;
повторяющиеся события;
календарное расписание;
разные периоды;
неблокирующая работа.
```

Если задача одна:

```text
через 500 мс закрыть заслонку.
```

Scheduler не обязателен.

FSM и Timer достаточно.

---

# Что должен уметь инженер

После этой главы инженер должен уметь:

* отличать Timer от RTC;
* отличать RTC от Scheduler;
* понимать разницу между состоянием времени и событием изменения;
* отслеживать новую секунду или минуту;
* избегать многократного запуска одной задачи;
* хранить расписание в структурах;
* отделять Scheduler от железа;
* запускать высокоуровневые действия через интерфейсы;
* понимать роль `Init` и `Update`;
* проектировать неблокирующий Scheduler;
* определять поведение после перезапуска;
* учитывать пропущенные события;
* не переусложнять простой проект;
* понимать взаимодействие Scheduler и FSM.

Главный вопрос:

> Как понять, что нужный момент времени наступил именно сейчас, и выполнить задачу ровно один раз?

# Главное

Scheduler — это не часы.

И не таймер.

Он не считает миллисекунды сам и не хранит календарное время сам.

Он использует время, чтобы ответить на вопрос:

```text
Пора ли сейчас выполнить задачу?
```

Timer говорит:

```text
Прошло 500 миллисекунд.
```

RTC говорит:

```text
Сейчас 08:30.
```

Scheduler говорит:

```text
В 08:30 нужно покормить.
```

А Feeder говорит:

```text
Хорошо. Я сам знаю, как выполнить кормление.
```

Получается:

```text
RTC
   |
   v
Scheduler
   |
   v
Feeder
   |
   v
FSM
   |
   v
Servo
```

Каждый модуль отвечает только за свою часть.

Scheduler не ждёт.

Не блокирует программу.

Не управляет железом напрямую.

Он регулярно получает текущее время, обнаруживает нужное событие и запускает действие ровно тогда, когда это требуется.

Именно так устройство начинает работать не просто как набор функций, а как система, способная выполнять задачи во времени.
